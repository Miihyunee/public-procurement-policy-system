# 1. 목적

이 문서가 답하려는 질문은 하나다.

> **고객이 보유한 구매실적의 사업자등록번호를 기준으로 기업정보·인증정보를 연결하여
> 정책 달성률을 계산할 수 있는가?**

새 기능을 추가하는 것이 아니라, **실제 데이터를 넣었을 때 어디에서 막히는지**를
사전에 파악하는 것이 목적이다.

## 1.1 현재 결론 (요약)

**계산 엔진 자체는 동작한다.** 최소 Fixture로 아래 흐름 전체가 통과함을 확인했다
(`tests/test_end_to_end_chain.py`, 10건 통과).

```
구매데이터 → 사업자번호 → 기업 → 인증 → 정책 판정 → 구매금액 → 달성률 → Dashboard
```

**단, 실제 데이터를 넣기 위한 앞단이 비어 있다.** 상세는 7장 참조.

# 3. 검증 절차 (Flow)와 단계별 실패 가능성

```
[1] 고객 구매데이터 수신
      ↓
[2] 컬럼 매핑
      ↓
[3] 사업자등록번호 정규화
      ↓
[4] 기본 데이터 품질검사
      ↓
[5] Company 연결 가능 여부 확인
      ↓
[6] Certification 연결 가능 여부 확인
      ↓
[7] 판정 기준일 결정
      ↓
[8] 정책별 인증 유효성 판단
      ↓
[9] 구매금액 집계
      ↓
[10] 달성률 Calculator
      ↓
[11] Dashboard
```

## 3.1 단계별 상세

| 단계 | 하는 일 | 실패 가능성 | 실패 시 영향 | 대응 |
|---|---|---|---|---|
| **1. 수신** | 원본 보관 | 인코딩 깨짐(CP949/UTF-8), 시트 다수 | 읽기 불가 | 인코딩 자동 판별, 대상 시트 지정 |
| **2. 컬럼 매핑** | 헤더 → 시스템 필드 | **필수 5개 중 누락** | 해당 정책 계산 불가 | 고객 재요청 (4.1 판정 기준) |
| **3. 정규화** | 하이픈 제거, 날짜·금액 파싱 | **정규화 로직 미구현** | **매칭 대량 실패** | ⚠️ 구현 필요 (7장 G-2) |
| **4. 품질검사** | 결측·형식·중복 점검 | 결측률 과다 | 달성률이 실제보다 낮아짐 | 리포트 후 고객 협의 |
| **5. Company 연결** | `business_no` → 기업 | **Company 데이터가 없음** | **매칭률 0%** | ⚠️ 공급 경로 필요 (7장 G-1) |
| **6. Certification 연결** | 기업 → 정책 인증 | **인증 데이터가 없음** | 모든 정책 실적 0 | ⚠️ 외부 API 필요 (7장 G-1) |
| **7. 기준일 결정** | `evaluation_basis` 로 선택 | 해당 날짜 컬럼 결측 | 그 정책만 계산 불가 | ✅ 구현됨 |
| **8. 유효성 판단** | `valid_from ≤ 기준일 ≤ valid_to` | 인증 기간 정보 부재 | 판정 불가 | ✅ 구현됨 (경계 포함) |
| **9. 집계** | 정책별 합산 | 음수 금액 저장 거부 | 취소분 반영 불가 | ⚠️ Sprint B 완화 |
| **10. 달성률** | 목표 대비 계산 | **목표율 미설정** | `TARGET_RATE_NOT_SET` 표시 | ✅ 구현됨(계산 제외) |
| **11. Dashboard** | JSON 응답 | — | — | ✅ 구현됨 |

> ✅ = 검증 완료(테스트 통과), ⚠️ = 미구현·조치 필요

## 3.2 매칭 실패의 파급 효과 (중요)

매칭에 실패한 구매는 **버려지지 않고 전체 구매액(분모)에는 포함**된다.
따라서 **매칭률이 낮으면 달성률이 실제보다 낮게 나온다.**

실측 예시 (`test_unmatched_purchase_lowers_achievement_rate`):

| 상황 | 정책 구매액 | 달성률 |
|---|---|---|
| 하이픈 2,000,000원 매칭 실패 | 3,000,000 (30%) | **60.00%** |
| 정규화하여 매칭 성공했다면 | 5,000,000 (50%) | 100.00% |

→ **매칭률은 달성률과 함께 반드시 보고해야 하는 지표다.**

# 4. 사업자등록번호 중심 검증 (핵심 결합키)

## 4.1 검증 항목과 판정 기준

| # | 검증 항목 | 확인 방법 | 판정 |
|---|---|---|---|
| 1 | 사업자등록번호 컬럼 존재 | 헤더 확인 | **없으면 즉시 중단** |
| 2 | 하이픈 제거 가능 | `-`·공백 제거 후 숫자만 남는가 | 불가 행은 오류 |
| 3 | 10자리 정규화 | 제거 후 길이 = 10 | 미달 시 오류 |
| 4 | NULL·빈 값 비율 | 결측 건수 / 전체 | 비율 기록, 과다 시 협의 |
| 5 | 중복 사업자번호 | 값별 건수 분포 | **정상**(한 업체 다건 거래). 건수만 기록 |
| 6 | 형식 오류 비율 | 자릿수·문자 포함 | 건수 기록 |
| 7 | 금액과의 연결 | 사업자번호별 금액 합계 산출 | 산출 가능해야 함 |
| 8 | 계약일·지급일 존재 | 결측 건수 | 정책별 계산 가능 여부 결정 |

**체크섬(V-013)**: PM 결정대로 **Warning 처리**. 검증 실패해도 탈락·거부하지 않고 리포트에만 기록한다.

## 4.2 ⚠️ 정규화 미구현 — 실측 확인됨

현재 시스템에는 **사업자번호 정규화 코드가 없다.**

```
Company 저장값 : 1234567890
구매데이터     : 123-45-67890   → 매칭 실패 (동일 사업자인데 연결 안 됨)
```

`test_hyphenated_business_no_fails_to_match` 로 재현했다.
고객 데이터가 하이픈 형식이면 **전량 매칭 실패**할 수 있는 위험이 있다.

**정규화가 필요한 지점**: Import 단계(구매데이터) **와** 수집 단계(인증데이터) **양쪽**.
한쪽만 정규화하면 형식이 어긋나 여전히 실패한다.

## 4.3 데이터 연결 구조

```
Purchase.business_no
      │  (CompanyMatcher — 완전 일치 비교)
      ▼
Company.company_id
      │
      ▼
Certification (company_id + policy_id)
      │  valid_from ≤ 판정기준일 ≤ valid_to
      ▼
Policy.evaluation_basis 로 판정 기준일 선택
      │  PAYMENT_DATE → payment_date
      │  CONTRACT_DATE → contract_date
      ▼
정책별 구매금액 집계 → 달성률
```

- 비교는 **완전 일치(exact match)** 다. 부분 일치·유사도 매칭은 없다.
- 한 기업이 같은 정책 인증을 여러 건 보유하면 **하나라도 만족 시 인정**한다.

## 5.1 데이터가 부족할 때 어디까지 계산 가능한가

| 부족한 데이터 | 계산 가능 범위 |
|---|---|

## 7.1 G-1 상세 — 가장 중요한 제약

구매데이터를 아무리 잘 넣어도, **기업·인증 데이터가 없으면 모든 정책 실적은 0** 이다.

```
Purchase (고객 제공)  ─── 있음
Company     (외부 수집) ─── ❌ 공급 경로 없음
Certification (외부 수집) ─ ❌ 공급 경로 없음
```

인증 데이터는 외부 API에서 와야 하며, **현재 인증키가 하나도 발급되지 않았다**
(`EXTERNAL_API_ONBOARDING.md`). 즉 **API 신청이 실질적인 선행 조건**이다.

## 8.1 응답 필드 확정 / 추정 / 미확정 구분

> 실제 API 응답을 확인하지 않은 항목은 **확정으로 표기하지 않는다.**

| 데이터 | 확정 (검증됨) | 추정 (공개정보 기반) | 미확정 (확인 필요) |
|---|---|---|---|
| **여성기업 / 장애인기업** (SMPP) | 데이터셋 존재, **사업자번호+기준일자 조회** | 확인서 상세 제공 | **유효기간 필드**, 대표자명, 인증번호, 호출 한도, 미인증 시 응답 |
| **창업기업** (창업진흥원) | 데이터셋 존재 | 확인서 발급기업 목록 제공 | **사업자번호 제공 여부**, **유효기간 필드**, 조회 방식 |
| **중소기업** (중소벤처24) | API 존재, **인증키 심사제** | 증명서 정보 제공 | 신청 가능 대상, 응답 필드 전체, 사업자번호 조회 지원 여부 |
| **녹색제품** | 파일 데이터 존재 | 제품 단위(EL번호·모델명) | **판정 단위(기업/제품)**, 사업자번호 제공 여부 |

**공통 미확정**: 이용약관상 **수집 데이터 저장(캐싱) 허용 여부**.
저장이 제한되면 매 계산 시 조회하는 구조로 바꿔야 하므로 설계에 영향이 크다.

# 9. 실제 구매데이터가 들어온 후 첫 번째 작업

**순서대로** 수행한다. 코드를 먼저 짜지 않는다.

| 순서 | 작업 | 목적 |
|---|---|---|
| **1** | 원본 보관 + 컬럼 목록·행 수 파악 | 이후 모든 대조의 기준 |
| **2** | **필수 5개 컬럼 대응 확인** | 없으면 즉시 고객 재요청 (그 뒤 작업 무의미) |
| **3** | **사업자번호 형식 실태 조사** | 하이픈 여부·자릿수·결측률 → 정규화 규칙 확정 |
| **4** | 날짜·금액 형식 조사 | 파싱 규칙 확정, 음수 존재 여부 확인 |
| **5** | 품질 리포트 작성 | 결측·중복·오류 건수 산출 |
| **6** | 컬럼 매핑표 확정 | `PURCHASE_DATA_SPEC.md` v1.0 확정 |
| **7** | 정책별 계산 가능 여부 판정 | 어디까지 산출 가능한지 결정 |

> **3번이 가장 중요하다.** 사업자번호 형식이 확인되어야 정규화 규칙이 정해지고,
> 그래야 매칭률을 예측할 수 있다.

  지금 진행할 수 있다.
