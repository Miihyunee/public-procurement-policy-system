# 원본 행 추적 설계 — 업로드에서 검토 화면까지

## 문서 정보

| 항목 | 내용 |
|---|---|
| 목적 | 원본 파일의 행이 지금 어디에 있는지 담당자가 설명할 수 있게 한다 |
| 범위 | 업로드 → 검증 → 적재 → 미적재 기록 → 화면 → CSV |
| 작성 | STEP 12(기록 구조) · STEP 13(가시화·CSV) |
| 상태 | ✅ 구현 완료. ⛔ **업무규칙은 미확정** (Q5-8) |

> ⛔ **이 문서는 업무규칙을 정하지 않습니다.**
>
> 여기 적힌 것은 "현재 시스템이 이렇게 동작한다" 는 **기술적 사실**뿐입니다.
> 금액이 0 이하인 행을 실적으로 인정할지, 검토 대상에 넣을지는 고객 확인
> 사항입니다(`CUSTOMER_DATA_QUESTIONS.md` Q5-8). 이 구현을 근거로 "제외하기로
> 했다" 고 읽으면 안 됩니다.

# 1. 왜 만들었나

STEP 11 실데이터 리허설에서 다음이 확인되었습니다.

```
원본 2,292행  →  검토 화면 2,162행
                 130행이 아무 안내 없이 사라짐
```

담당자가 목록을 끝까지 보고 "전체를 검토했다" 고 판단해도, 실제로는 보지 못한
행이 남습니다. 적재 실패 사실은 업로드 응답에만 잠깐 담겼다가 화면을 닫는
순간 사라졌습니다.

**고쳐야 할 것은 "130행을 어떻게 처리할지" 가 아니라 "130행이 설명 없이
사라지는 것"** 입니다. 앞의 것은 고객 확인 사항이고, 뒤의 것은 지금 고칠 수
있습니다.

# 2. 데이터 흐름

```
원본 Excel
   │
   ├─ ① 업로드 검증 (uploads/validation.py)
   │     금액 ≤ 0 → ⚠️ 경고 (오류 아님)
   │     ⛔ 여기서 오류로 단정하면 확정되지 않은 업무규칙을 만드는 셈
   │
   ├─ ② 행 적재 (importers/purchase_importer.py)
   │     │
   │     ├─ 성공 → purchase (DB-1)          → 검토 목록 · 검토 CSV · 계산
   │     │
   │     └─ 실패 → ImportStatus.FAILED
   │           └─ ③ 기록 (importers/rejection_trace.py)
   │                 → import_rejection      → /imports/trace · /imports/trace.csv
   │
   └─ ④ 결과 (BatchImportResult.trace)
         원본 = 적재 + 미적재 · 설명되지 않는 행 0
```

## 2.1 어디서 걸러지는가

| 단계 | 조건 | 코드 |
|---|---|---|
| 검증 | 필수값 누락 · 형식 오류 → **오류**(전체 저장 중단) | `uploads/validation.py` |
| 검증 | 금액 ≤ 0 → **경고**(저장 진행) | `uploads/validation.py` 금액 분기 |
| 저장 | 금액 ≤ 0 → **거부** `구매금액은 0 보다 커야 합니다` | `database/purchase_repository.py` `_validate` |
| 적재 | 예외를 잡아 그 행만 실패 처리, 나머지는 계속 | `importers/purchase_importer.py` |

⚠️ `amount > 0` 규칙은 **음수 상계가 계산에 아직 연결되지 않았기 때문**에
있습니다(`core/offsetting.py`). STEP 12·13 에서 이 규칙을 바꾸지 않았습니다.

# 3. 저장 구조

```
import_rejection
  rejection_id · batch_id · row_number · reason · message
  business_no · company_name · description · budget_account
  amount(원본 그대로 — 음수도 그대로) · resolution_date · issue_date · created_at
```

| 원칙 | 지킨 방법 |
|---|---|
| DB-1 불변 | `purchase` 테이블·컬럼을 건드리지 않음. 신규 테이블만 추가 |
| 계산 무영향 | Calculator 는 `purchase` 만 읽음 |
| 업무 판단 없음 | "제외" 를 뜻하는 상태값이 없음. 사유 코드는 **무슨 일이 있었는지**만 적음 |
| 하위 호환 | `BatchImportService` 의 저장소 인자는 **선택** |
| 원본 되짚기 | `row_number` 로 원본 파일의 같은 행을 찾음 |

## 3.1 사유 코드

| 코드 | 표시 | 언제 |
|---|---|---|
| `NON_POSITIVE_AMOUNT` | 금액이 0 이하 (처리 방식 확인 필요) | 저장 규칙에 걸림 |
| `MISSING_REQUIRED` | 필수값 누락 | 사업자번호 등이 빔 |
| `UNPARSABLE` | 값을 해석하지 못함 | 날짜·금액 형식 |
| `OTHER` | 기타 | 아는 표지가 없음 — **버리지 않고 원문을 함께 남김** |

⛔ 표시 문구에 "제외" · "부적합" · "무시" 를 쓰지 않습니다(테스트로 고정).

## 3.2 같은 기간을 다시 올리면

같은 기간을 다시 올리면 이전 배치가 `SUPERSEDED` 가 되고 그 배치의 `purchase`
행은 계산·검토에서 빠집니다. **미적재 기록도 같은 규칙을 따릅니다.**

| 메서드 | 무엇을 돌려주나 |
|---|---|
| `find_current()` | 지금 유효한 기록만 — 화면·CSV·집계가 씁니다 |
| `find_all()` | 대체된 배치까지 포함 — 과거를 되짚을 때만 |

⛔ 대체된 기록을 **지우지 않습니다.** 조회에서 빠질 뿐입니다.

> 🔴 **STEP 12 에서 실제로 틀렸던 부분입니다.** 적재 행은 대체된 배치를 빼고
> 세는데 미적재 기록은 전부 세어, 같은 기간을 다시 올리면 미적재 건수만 계속
> 불어났습니다. STEP 13 에서 두 쪽을 같은 기준으로 맞췄습니다.

# 4. 숫자 대조

```
원본 행 수 = 적재된 행 수 + 사유와 함께 기록된 행 수
```

`ImportTrace.source_rows` 는 Importer 에 넘긴 행을 **세어서** 기록한 값이며,
적재/미적재 합계로 계산한 값이 아닙니다 — 그래야 둘을 맞대어 볼 수 있습니다.
`ImportTrace.unexplained` 가 0 이 아니면 **어딘가에서 행이 사라진 것**입니다.

# 5. API

| 엔드포인트 | 무엇 |
|---|---|
| `GET /imports/trace` | 원본·적재·미적재 건수, 사유별 집계, 배치별 대조, 미적재 행 목록 |
| `GET /imports/trace.csv` | 미적재 행 CSV (스트리밍) |
| `POST /uploads/purchases` (기존) | 응답에 `rejected_rows` · `rejection_reasons` 추가 |

## 5.1 미적재 CSV 사양

| 항목 | 값 |
|---|---|
| 열 | 12개 (아래) · **고정 순서** |
| 인코딩 | UTF-8 **BOM** |
| 줄바꿈 | **CRLF** |
| 수식 인젝션 | `=` `+` `-` `@` `\t` `\r` 로 시작하는 **자유 입력**에 `'` 를 앞에 붙임 |
| 금액 | 지수 표기 없음 · **음수 부호 보존** · ⛔ 따옴표를 붙이지 않음 |
| 빈 값 | 빈 칸 |
| 전송 | generator 기반 스트리밍 (`StreamingResponse`) |
| 파일명 | `import-rejections.csv` |

열 순서 — 앞 여덟 개는 원본 엑셀 컬럼 순서를 따릅니다(눈으로 대조하기 위해).

```
원본 행 번호 · 신고기준일 · 적요 · 거래처명 · 사업자번호 · 금액 · 결의일자 ·
예산과목 · 미적재 사유 코드 · 미적재 사유 · 원문 메시지 · 업로드 배치 ID
```

⚠️ **금액 칸에는 수식 방어를 걸지 않습니다.** 음수 금액은 `-` 로 시작하지만
숫자로 읽혀야 하고, 따옴표를 붙이면 엑셀에서 합계를 낼 수 없습니다. 금액은
숫자 전용 칸이라 자유 입력이 들어오지 않습니다.

⚠️ **사업자번호는 시스템이 정규화한 형태**(하이픈 없는 10자리)로 실립니다.
업로드 검증 단계에서 이미 정규화되기 때문이며, **적재된 행이 DB-1 에 저장되는
형태와 같습니다.** 원본 표기 그대로를 남기려면 업로드 파이프라인에 원문 컬럼을
더해야 하고, 이는 별도 안건입니다.

# 6. 화면

## 6.1 업로드 결과

```
8 총 행 | 8 정상 | 0 오류 행 | 6 저장 | #1 배치

원본 행 8건 · 검토 대상 적재 6건 · 미적재 2건
미적재 행 2건 확인 — 원본에는 있으나 현재 검토 대상 DB 에 적재되지
않았습니다. 사유와 원본 값을 확인해 주세요.
- 금액이 0 이하 (처리 방식 확인 필요): 2건

[미적재 행 확인]  [미적재 CSV 내려받기]
```

* 저장하지 않았으면(검증만) 적재/미적재를 말하지 않습니다.
* 미적재 0건이면 "미적재 행 없음 — 원본 행이 모두 검토 대상에 들어왔습니다"
  라고 적고 버튼을 숨깁니다.
* 사유 이름은 **백엔드가 준 라벨**을 그대로 씁니다. 화면이 새로 만들지 않습니다.
* CSV 는 서버 스트리밍입니다. ⛔ 브라우저에서 데이터를 받아 JS 로 만들지
  않습니다.

## 6.2 검토 화면

상단에 같은 안내가 나오고, 미적재 행 표는 **업로드 화면과 같은 함수**
(`renderRejectionTable`)로 그립니다. 모두 보이는 상태에서는 자리를 차지하지
않습니다.

## 6.3 ⛔ 쓰지 않는 표현

* 제외되었습니다 · 실적에서 제외합니다 · 검토할 필요가 없습니다
* 정상적으로 제외되었습니다 · 부적합 데이터입니다

고객이 Q5-8 에 답하기 전이므로 전부 사실이 아닙니다. 화면 문구 · API 응답 ·
CSV 열 이름 · 사유 라벨 네 곳 모두 테스트로 막았습니다.

# 9. 현재 사실 / 고객 결정 대기

## 9.1 ✅ 현재 구현으로 확정된 기술적 사실

* 원본 행이 적재되지 않으면 **사유와 원본 값이 DB 에 영구 기록**된다
* 원본 = 적재 + 미적재 가 항상 성립하며, 깨지면 `unexplained` 로 드러난다
* 업로드 직후 화면에서 세 숫자를 함께 볼 수 있다
* 미적재 행을 CSV 로 내려받아 원본 엑셀과 대조할 수 있다
* 같은 기간을 다시 올려도 숫자가 어긋나지 않고, 이전 기록은 보존된다

## 9.2 🔴 고객 확인이 필요한 업무규칙

* 금액 ≤ 0 행을 **검토 대상에 포함**할지 (Q5-8)
* 실적으로 **인정**할지
* DB-1 에 **저장**할지 (현재 저장 규칙 변경 · PM 승인 사항)
* **계산**에 포함할지 (DB-3 · Calculator — 미착수)

⛔ 어느 것도 코드에 확정해 두지 않았습니다.

# 10. 월별 운영에서의 추적 (STEP 14)

매월 파일을 올리는 운영 방식과 업로드 이력은 `MONTHLY_UPLOAD_OPERATIONS.md`
로 옮겼습니다. 여기서는 추적 구조에 더해진 것만 적습니다.

## 10.1 ✅ `import_batch.source_row_count` 추가

원본 행 수를 **배치에 기록**합니다(기존 `ALTER TABLE ADD COLUMN` 방식).
이전에는 배치 단위 "설명되지 않는 행" 을 적재+미적재 합계로 되계산할 수밖에
없어 늘 0 이 나왔고, 그래서 아무것도 검증하지 못했습니다.

| 값 | 뜻 |
|---|---|
| 숫자 | Importer 에 넘긴 원본 행 수 |
| `null` | STEP 14 이전에 만들어진 배치 — **모른다**(0 이 아님) |

⛔ `purchase` 테이블은 이번에도 건드리지 않았습니다.

## 10.2 ✅ 조회 API 세 가지

| 엔드포인트 | 무엇 |
|---|---|
| `GET /imports/batches` | 업로드 이력(대체된 배치 포함) |
| `GET /imports/batches/{id}` | 업로드 한 건의 원본·적재·미적재·사유별 건수 |
| `GET /imports/rejections` | 미적재 행 검색·필터·정렬·페이지 |

`GET /imports/trace` 와 `GET /imports/trace.csv` 는 **그대로**입니다.

## 10.3 ✅ 정렬 기준 — 배치를 앞세운다

원본 행 번호는 **파일마다 1부터** 다시 시작합니다. 여러 달을 올려 두면 번호만
으로는 순서가 정해지지 않아, 목록과 CSV 의 순서가 어긋났습니다(실데이터 8개
배치에서 확인). 기본 정렬을 `(배치, 원본 행 번호)` 로 맞추고 화면 표에도
업로드 배치를 함께 보여 줍니다. 이제 목록과 CSV 가 **순서까지 일치**합니다.

## 10.4 🔴 이번에도 정하지 않은 것

Q5-1 ~ Q5-9 · 금액 ≤ 0 행의 처리 · 분석 방법 · 자동확정 · 임계값 · 그룹핑 키 ·
DB-3 · Calculator — **전부 미정**입니다.
