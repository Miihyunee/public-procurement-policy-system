# 2. Parser 설계 요구사항

> ⛔ **최종 Parser 를 구현하지 않는다.** 아래는 "Parser 가 최소한 이 처리를 지원해야 한다"는
> 요구사항 수준의 정리다.

## 2.1 처리 흐름

```text
원본 파일
   ↓  ① 파일 형식 확인        (확장자·인코딩·시트)
   ↓  ② 헤더/컬럼 구조 확인    (컬럼 수·컬럼명·순서)
   ↓  ③ 행 유형 판별           (데이터행 / 집계행 / 빈 행)
   ↓  ④ 집계행 식별            (알려진 표기 대조, 미지 표기는 경고)
   ↓  ⑤ 거래 구분 확인         (매출 / 매입 / 미분류)
   ↓  ⑥ 사업자번호 정규화      (기존 규칙 그대로)
   ↓  ⑦ 날짜 파싱              (형식만. 어느 필드에 넣을지는 미확정)
   ↓  ⑧ 금액 파싱              (형식만. 어느 금액을 쓸지는 미확정)
   ↓  ⑨ Validation
   ↓  ⑩ Import
```

## 2.2 각 단계 요구사항

| 단계 | 요구사항 | 확정 여부 |
|---|---|---|
| ① 파일 형식 | `.xls` 읽기. `.txt` 는 **거부하거나 경고** (따옴표 없어 안전하게 못 읽음) | ✅ 확정 |
| ② 컬럼 구조 | **컬럼명 기반 접근**. 위치(index) 고정 금지 — 컬럼 순서가 바뀔 수 있다 | ✅ 확정 |
| ② 컬럼 검증 | 필수 컬럼 존재 확인. 없으면 **행 단위가 아니라 파일 단위로 실패** | ✅ 확정 |
| ③ 행 유형 | 데이터행/집계행/빈 행 구분 | ✅ 확정 |
| ④ 집계행 | **비교용 문자열 정규화 후** 알려진 표기 대조 (3장) | ✅ 확정 |
| ⑤ 거래 구분 | `세무구분` 문자열로 판정. **미지 값은 미분류 + 경고** | ✅ 확정 |
| ⑥ 사업자번호 | 기존 `normalize_business_no()` 그대로 사용 | ✅ 확정 |
| ⑦ 날짜 | `YYYY/MM/DD` 파싱은 확정. **`payment_date`·`contract_date` 매핑은 미확정** | 🔴 부분 |
| ⑧ 금액 | 숫자·쉼표 파싱은 확정. **`amount` 에 어느 금액을 넣을지는 미확정** | 🔴 부분 |
| ⑨ Validation | 6장 | 🔴 부분 |
| ⑩ Import | 기존 `PurchaseImporter` 재사용 | ✅ 확정 |

> **⑦·⑧이 미확정인 상태로 Parser 를 완성하면 매핑을 추측으로 박게 된다.**
> 형식 처리(파싱)와 의미 매핑을 분리해 설계하고, **매핑은 나중에 주입**하는 형태가 안전하다.

## 2.3 컬럼 접근 방식 — **위치가 아니라 이름**

샘플의 88개 컬럼 중 21개는 전 행이 비어 있고, 실제 운영데이터에서 컬럼이 추가·삭제될 수 있다.
따라서 **컬럼명 기반 접근**을 요구사항으로 둔다. (`row[7]` 이 아니라 `row["사업자번호"]`)

# 3. 집계행 처리 설계

## 3.1 문제

샘플에서 `[소    계]` · `[누    계]` · `[분 기 계]` · `합계` 가 데이터 영역에 섞여 있었다.
**`[소    계]` 처럼 내부에 공백이 들어 있어** 단순 문자열 비교로는 놓칠 수 있다.

## 3.2 처리 구조

```text
원본값
  → 비교용 문자열 정규화   (공백 제거 등)
  → 알려진 집계행 표기 대조
  → 판정: 집계행 / 데이터행 / 미지(경고)
```

> ⚠️ **정규화는 "비교용"이며, 원본값은 그대로 보존한다.**

## 3.3 미지 표기 처리 — 3안 비교

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **가** | 알려지지 않은 표기는 **데이터행으로 유지 + 경고** | 조용한 누락 없음. 이상값이 총액에 드러나 발견하기 쉬움 | 집계행이 계산에 섞일 수 있음 |
| 나 | 패턴(`[...계]`)에 맞으면 자동 제외 | 새 표기도 자동 처리 | **거래행을 잘못 제외할 위험**. 조용한 누락 |
| 다 | 미지 표기 발견 시 **파일 전체 처리 중단** | 가장 안전 | 운영이 자주 멈춤 |

> **권장: 가안.** 지시서의 "알려지지 않은 값을 자동으로 삭제하는 방식은 피하라"에 부합한다.
> **누락은 조용하지만 과대 계상은 눈에 띈다.** → **D-18**

# 4. 매출 / 매입 처리 설계

## 4.1 두 개념 분리 — **핵심**

```text
거래 구분(transaction kind)     ≠     정책 계산 대상(eligible)
```

| 구분 | 판정 근거 | 확정 여부 |
|---|---|---|
| 거래 구분 (매출/매입/미분류) | `세무구분` 문자열 | ✅ **샘플로 확정 가능** |
| 정책 계산 대상 여부 | **업무 기준** | 🔴 **[운영-확인필요] W-7** |

> **샘플에서 매입이라고 해서, 실제 운영데이터 전체에서 "매입 = 우선구매 실적"이라고
> 확정하지 않는다.**

## 4.2 판정 규칙

| # | 조건 | 거래 구분 | 계산 대상 |
|---|---|---|---|
| K-1 | 집계행 | — | 제외 |
| K-2 | `세무구분` 에 `매출` 포함 | 매출 | 제외 |
| K-3 | `세무구분` 에 `매입` 포함 | 매입 | **대상 후보** |
| K-4 | 그 외 / 빈값 | **미분류** | **판정 보류 + 경고** |

> K-4 를 임의로 매입·매출로 밀어넣지 않는다 → **D-21**

## 4.3 보고 항목 (필수)

원본 행 수 / 집계행 제외 / 매출 제외 / 미분류 보류 / **계산 대상** — 각 건수와 금액.
**세 단계의 합이 원본과 일치하는지 검증**할 수 있어야 한다.

# 5. Raw / Cleansed / Eligible — 설계안 비교

> ⛔ **샘플만으로 스키마를 확정하지 않는다.** 아래는 **비교안**이며 결정은 PM 몫이다.

## 5.1 개념

```text
① Raw       고객 제공 원본 그대로
② Cleansed  집계행 배제 + 거래 구분 부여
③ Eligible  정책 계산에 투입할 행
```

## 5.2 아직 결정하지 않은 5가지 (지시서 13장)

| # | 미결 사항 |
|---|---|
| 1 | Raw 데이터를 DB 에 저장할 것인가 |
| 2 | 제외 행을 별도 테이블에 저장할 것인가 |
| 3 | `Purchase` 에 상태 필드를 추가할 것인가 |
| 4 | 전처리 결과를 파일/리포트로만 관리할 것인가 |
| 5 | 원본 행 ID 를 어떻게 관리할 것인가 |

## 5.3 설계안 3종 비교

### A안 — 리포트 전용 (DB 무변경)

```text
원본 파일 → [전처리] → 계산 대상 행만 Purchase 에 저장
                └→ 제외 내역은 Import 리포트에만 기록
```

| 항목 | 평가 |
|---|---|
| 스키마 변경 | **없음** ✅ |
| 구현 비용 | 가장 낮음 |
| 사후 추적 | ❌ **리포트를 보관하지 않으면 왜 빠졌는지 알 수 없다** |
| 재판정 | ❌ 기준이 바뀌면 **원본 파일부터 다시 넣어야 함** |
| 원본 행 ID | 리포트 내 행 번호만 |

### B안 — `Purchase` 에 구분 필드 추가

```text
원본 파일 → [전처리] → 전 행을 Purchase 에 저장
                       + 거래 구분 / 계산 대상 여부 필드로 표시
계산 시 → 계산 대상 행만 조회
```

| 항목 | 평가 |
|---|---|
| 스키마 변경 | **필요** (`Purchase` 에 2개 필드) |
| 구현 비용 | 중간 |
| 사후 추적 | ✅ 제외 사유를 행 단위로 확인 가능 |
| 재판정 | ✅ 기준 변경 시 **DB 안에서 재판정 가능** |
| 위험 | 🔴 **매출행까지 `Purchase` 에 저장**된다. 기존 Calculator·Repository 가 "전체 구매액"을 계산할 때 **매출을 빼도록 반드시 수정**해야 하며, 빠뜨리면 조용히 틀린다 |

### C안 — 원본 보관 테이블 분리

```text
원본 파일 → RawPurchase(전 행 그대로) → [전처리] → Purchase(계산 대상만)
```

| 항목 | 평가 |
|---|---|
| 스키마 변경 | **필요** (신규 테이블) |
| 구현 비용 | 가장 높음 |
| 사후 추적 | ✅ 완전 |
| 재판정 | ✅ 원본 재적재 없이 가능 |
| 기존 계층 영향 | ✅ **`Purchase` 는 계산 대상만 담으므로 Calculator 무변경** |
| 원본 행 ID | ✅ 자연스럽게 관리 가능 |

## 5.4 비교 요약

| 기준 | A안 | B안 | C안 |
|---|---|---|---|
| 스키마 변경 | 없음 | `Purchase` 확장 | 신규 테이블 |
| 구현 비용 | 낮음 | 중간 | 높음 |
| 제외 사유 추적 | ❌ | ✅ | ✅ |
| 기준 변경 시 재판정 | ❌ | ✅ | ✅ |
| **기존 Calculator 영향** | ✅ 없음 | 🔴 **있음** | ✅ 없음 |
| 원본 보존 | 파일만 | 부분 | ✅ 완전 |

## 5.5 판단 (권장 아님 — 참고용)

| 상황 | 적합한 안 |
|---|---|
| 실제 데이터를 한 번만 검증해 보는 단계 | **A안** |
| 반복 적재·재판정이 필요한 운영 단계 | **C안** |
| — | **B안은 기존 계산 경로를 건드리므로 신중해야 한다** |

> **결정 시점**: 실제 운영데이터의 규모·적재 주기·재판정 필요성이 확인된 뒤가 적절하다.
> 지금 결정하면 **샘플 기준으로 스키마를 확정**하게 된다 → **D-19**

# 6. Validation 설계

## 6.1 확정 가능한 검증

| # | 검증 | 근거 |
|---|---|---|
| V-1 | 필수 컬럼 존재 (파일 단위) | 컬럼 구조 확정 |
| V-2 | 사업자번호 정규화 결과 (`VALID`/`MISSING`/`INVALID_FORMAT`) | 기존 규칙 |
| V-3 | 체크섬 오류는 **Warning**, 저장 차단 안 함 | 기존 규칙 |
| V-4 | 날짜 **형식** 검증 (`YYYY/MM/DD`) | 형식 확정 |
| V-5 | 금액 **형식** 검증 (숫자·쉼표) | 형식 확정 |
| V-6 | 집계행 식별 | 3장 |
| V-7 | 거래 구분 판정 | 4장 |
| V-8 | 원본/제외/대상 **건수·금액 합 일치** | 정합성 |

## 6.2 아직 정의할 수 없는 검증

| # | 검증 | 미확정 사유 |
|---|---|---|
| X-1 | 지급일 필수 여부 | 어느 컬럼이 지급일인지 모름 (W-1) |
| X-2 | 계약일 필수 여부 | 샘플에 없음 (W-2) |
| X-3 | 금액 부호 규칙 | 음수 의미 미확정 (W-4) |
| X-4 | 구매유형 유효값 | 값 자체가 없음 (W-6) |

> **X-1~X-4 를 임의로 정의하지 않는다.**

# 7. 실제 운영데이터 수신 시 검증 체크리스트

> Parser·Import 테스트의 기준으로 사용한다. 각 항목은 **자동 산출**되어야 한다.

## 7.1 파일

| # | 항목 | 확인 방법 |
|---|---|---|
