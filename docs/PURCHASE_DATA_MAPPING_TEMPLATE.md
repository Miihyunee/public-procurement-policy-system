# 1. 목적과 사용법

## 1.1 목적

고객(공공기관)이 제공한 **실제 구매(지출) 데이터를 분석하고, 시스템 표준 컬럼으로 매핑**하기 위한
작업 템플릿이다.

기관마다 지출 시스템 양식이 다르므로 컬럼명·형식이 제각각이다.
본 템플릿은 **고객 데이터를 받은 담당자가 빈칸을 채워 가며 분석**할 수 있도록 설계되었다.

## 1.2 사용 방법

```
고객 데이터 수신
      ↓
본 템플릿을 복사 → docs/mappings/{고객명}-{연도}.md 로 저장
      ↓
2장 매핑 표 작성 → 3장 품질 체크 → 5장 Validation 확인
      ↓
PM 검토 후 Import 실행 (Sprint B)
```

> ⚠️ **본 문서 자체는 템플릿이므로 직접 수정하지 않는다.** 고객별 사본을 만들어 작성한다.

## 1.3 현재 상태

- 아직 **고객 실제 데이터를 수신하지 않았다.**
- 따라서 2장의 "고객 컬럼"은 **예시(가상)** 이며, 실제 데이터 수신 시 교체한다.
- 실제 데이터 확보 후 `PURCHASE_DATA_SPEC.md`를 v1.0으로 확정한다.

# 2. 컬럼 매핑 표

## 2.1 매핑 표 (작성 양식)

> 고객 파일의 헤더를 **그대로** "고객 컬럼"에 옮겨 적고, 나머지 칸을 채운다.

| 고객 컬럼 | 예상 의미 | 시스템 컬럼 | 필수 여부 | 비고 |
|---|---|---|---|---|
| | | | | |
| | | | | |
| | | | | |

### 작성 규칙

| 칸 | 작성 방법 |
|---|---|
| **고객 컬럼** | 고객 파일의 헤더 원문 (공백·괄호 포함 그대로) |
| **예상 의미** | 담당자가 판단한 의미. 불확실하면 `?` 표기 후 고객 확인 |
| **시스템 컬럼** | `DATA_DICTIONARY.md`의 물리명. 대응 없으면 `-` |
| **필수 여부** | `필수` / `선택` / `미사용` |
| **비고** | 형식 문제, 변환 규칙, 확인 필요 사항 |

## 2.2 작성 예시 (가상 데이터)

> 실제 고객 데이터가 아니라 **작성 방법을 보여주기 위한 예시**다.

| 고객 컬럼 | 예상 의미 | 시스템 컬럼 | 필수 여부 | 비고 |
|---|---|---|---|---|
| 사업자번호 | 사업자등록번호 | `business_no` | **필수** | `123-45-67890` 형식 → 하이픈 제거 필요 |
| 거래처명 | 공급업체 상호 | `company_name` | **필수** | `(주)` 표기 혼재 |
| 계약체결일 | 계약일 | `contract_date` | **필수** | `YYYYMMDD` 문자열 → 날짜 변환 필요 |
| 지출완료일 | 대금 지급일 | `payment_date` | **필수** | 일부 행 공란 — **고객 확인 필요** |
| 지출액 | 구매금액 | `amount` | **필수** | 천단위 콤마 포함, 부가세 포함 여부 확인 필요 |
| 지출건명 | 구매 건명 | `-` | 선택 | 향후 증빙·소명 자료용 |
| 계약번호 | 기관 내부 계약번호 | `-` | 선택 | 원본 대조용 |
| 부서 | 구매 부서 | `-` | 선택 | 향후 부서별 통계 |
| 계약방법 | 수의계약/경쟁입찰 | `-` | 선택 | 향후 판정 세분화 |
| 물품목록번호 | 조달청 물품목록번호 | `-` | 선택 | **녹색제품 분석 결과에 따라 필수 승격 가능** |
| 회계연도 | 회계연도 | `-` | 미사용 | 집계 기간 판단에 참고 |

## 2.3 시스템 필수 컬럼 대응 확인표

> 매핑 작성 후, **필수 5개가 모두 채워졌는지** 반드시 확인한다.

| 시스템 컬럼 | 논리명 | 대응된 고객 컬럼 | 확인 |
|---|---|---|---|
| `business_no` | 사업자등록번호 | | ☐ |
| `company_name` | 업체명 | | ☐ |
| `contract_date` | 계약일 | | ☐ |
| `payment_date` | 지급일 | | ☐ |
| `amount` | 구매금액 | | ☐ |

> **하나라도 대응되지 않으면 Import를 진행하지 않는다.** 고객에게 재요청한다.
> 특히 `payment_date`(지급일)는 실무에서 누락이 가장 잦은 항목이다.

# 3. 데이터 품질 체크리스트

# 4. Import 절차 (Flow)

## 4.1 전체 흐름

```
[1] 파일 수신 · 원본 보관
        ↓
[2] 컬럼 확인 및 매핑 작성          ← 본 문서 2장
        ↓
[3] 데이터 품질 점검                 ← 본 문서 3장
        ↓
[4] 형식 정규화 (사업자번호·날짜·금액)
        ↓
[5] Validation 검증                  ← 본 문서 5장
        ↓  (실패 행은 오류 리포트로 분리)
[6] 기업정보 매칭 (business_no 기준)
        ↓
[7] 인증정보 조회 · 수집             ← 외부 API/파일
        ↓
[8] DB 저장 (Company · Certification · Purchase)
        ↓
[9] 달성률 계산 · Dashboard 확인
        ↓
[10] 결과 검증 및 고객 보고
```

## 4.2 단계별 상세

| 단계 | 작업 | 산출물 | 실패 시 처리 |
|---|---|---|---|
| **1. 파일 수신** | 원본 파일을 그대로 보관 | 원본 사본 | — |
| **2. 컬럼 확인** | 매핑 표 작성, 필수 5개 대응 확인 | 매핑 문서 | 필수 미대응 → **고객 재요청** |
| **3. 품질 점검** | 체크리스트 수행 | 품질 리포트 | 결측률 과다 → 고객 협의 |
| **4. 정규화** | 사업자번호 하이픈 제거, 날짜 파싱, 금액 숫자화 | 정규화 데이터 | 변환 실패 행 분리 |
| **5. Validation** | 5장 규칙 검증 | 오류 리포트 | 오류 행 제외 후 진행 |
| **6. 기업 매칭** | `business_no`로 `Company` 조회 | 매칭률 리포트 | **미매칭도 저장**(전체 구매액 포함) |
| **7. 인증 조회** | 정책별 인증정보 확보 | `Certification` 데이터 | API 실패 시 재시도·수기 보완 |
| **8. DB 저장** | Company / Certification / Purchase 적재 | 적재 건수 | 트랜잭션 롤백 |
| **9. 계산** | 달성률 계산 및 대시보드 확인 | 달성률 결과 | — |
| **10. 검증·보고** | 고객과 수치 대조 | 최종 보고서 | 불일치 시 원인 추적 |

## 4.3 중요 원칙

### 원칙 1 — 원본은 절대 수정하지 않는다
정규화·검증은 **사본**에서 수행한다. 수치 불일치 발생 시 원본 대조가 유일한 근거다.

### 원칙 2 — 매칭 실패 건도 저장한다
`business_no`로 기업을 찾지 못한 구매도 **저장하고 전체 구매액에는 포함**한다.
정책 실적으로만 제외된다.

> ⚠️ 이 때문에 **매칭률이 낮으면 달성률이 실제보다 낮게 나온다.**
> 매칭률은 반드시 고객에게 함께 보고해야 하는 지표다.

### 원칙 3 — 인증 조회는 판정 기준일 기준으로 한다
"지금 인증을 보유했는가"가 아니라 **"판정 기준일에 인증이 유효했는가"** 로 판정한다.
따라서 6~7단계는 구매 건의 날짜를 기준으로 조회해야 한다.

### 원칙 4 — 각 단계 결과를 기록한다
단계별 처리 건수를 남긴다. 최종 수치가 고객 장부와 다를 때 **어느 단계에서 줄었는지**
추적할 수 있어야 한다.

# 5. Validation Rule 초안

## 5.1 필수 항목 검증

| ID | 규칙 | 대상 | 위반 시 |
|---|---|---|---|
| V-001 | 필수 5개 컬럼이 모두 존재 | 파일 | **전체 거부** |
| V-002 | `business_no` NOT NULL | 행 | 오류 행 |
| V-003 | `company_name` NOT NULL | 행 | 오류 행 |
| V-004 | `contract_date` NOT NULL | 행 | 오류 행 |
| V-005 | `payment_date` NOT NULL | 행 | 오류 행 |
| V-006 | `amount` NOT NULL | 행 | 오류 행 |

## 5.2 사업자등록번호 형식

| ID | 규칙 | 상세 | 위반 시 |
|---|---|---|---|
| V-010 | 하이픈 제거 후 **숫자 10자리** | `123-45-67890` → `1234567890` | 오류 행 |
| V-011 | 숫자 외 문자 미포함 | 공백·특수문자 제거 후 검증 | 오류 행 |
| V-012 | 문자열 타입 유지 | 숫자 변환 금지 (앞자리 `0` 보존) | 처리 규칙 |
| V-013 | 사업자번호 **검증식** 적용 여부 | 국세청 체크섬 알고리즘 | **PM 결정 필요** (아래 참조) |

> **V-013 결정 필요**: 사업자등록번호는 마지막 자리로 유효성을 검증하는 체크섬 규칙이 있다.
> 적용하면 오타를 걸러낼 수 있으나, **유효한 번호가 오류로 분류될 위험**도 있다.
> 초기에는 **경고(warning)로만 처리**하고 거부하지 않는 것을 권장한다.

## 5.3 날짜 형식

| ID | 규칙 | 상세 | 위반 시 |
|---|---|---|---|
| V-020 | 파싱 가능한 날짜 | `YYYY-MM-DD`, `YYYYMMDD`, `YYYY/MM/DD`, Excel 날짜 셀 | 오류 행 |
| V-021 | 실존하는 날짜 | `2026-02-30` 등 배제 | 오류 행 |
| V-022 | `contract_date` ≤ `payment_date` | 계약일이 지급일보다 늦지 않음 | **경고**(거부 아님) |
| V-023 | 대상 기간 내 날짜 | 회계연도 범위 | **경고** |

> **V-022를 경고로 두는 이유**: 선지급·정산 등으로 역전이 실제 발생할 수 있다.
> 거부하면 정상 데이터를 잃는다.

## 5.4 금액 검증

| ID | 규칙 | 상세 | 위반 시 |
|---|---|---|---|
| V-030 | 숫자로 변환 가능 | 콤마·통화기호 제거 후 검증 | 오류 행 |
| V-031 | **0보다 큼** | 현재 시스템 제약 | 오류 행 |
| V-032 | `Decimal`로 처리 | 부동소수 사용 금지 | 처리 규칙 |
| V-033 | 음수(취소·반품) 처리 | **PM 결정 필요** (아래 참조) | — |

> **V-033 결정 필요**: 현재 시스템은 금액이 **0보다 커야** 한다.
> 그러나 실무 지출 데이터에는 **취소·반품이 음수로 표기**되는 경우가 있다.
> 대응 후보 — ① 음수 행 제외, ② 상계 처리 후 합산, ③ 고객에게 상계된 데이터 요청.

## 5.5 중복 검증

| ID | 규칙 | 위반 시 |
|---|---|---|
| V-040 | 완전 동일 행 중복 | **경고** + 목록 제시 |
| V-041 | 동일 업체·날짜·금액 | **경고** (분할 지급 가능성) |

> 중복은 **자동 제거하지 않는다.** 정상 거래일 수 있으므로 고객 확인 후 결정한다.

## 5.6 매칭 검증

| ID | 규칙 | 처리 |
|---|---|---|
| V-050 | `business_no`로 `Company` 조회 | 실패 시 `company_id`를 비운 채 저장 |
| V-051 | 매칭률 산출 | 리포트에 필수 포함 |

## 5.7 처리 수준 정의

| 수준 | 의미 | 처리 |
|---|---|---|
| **거부(Reject)** | 파일 전체를 처리할 수 없음 | Import 중단 |
| **오류(Error)** | 해당 행을 처리할 수 없음 | 행 제외 + 리포트 |
| **경고(Warning)** | 처리하되 확인 필요 | 저장 + 리포트 |

# 6. 고객 확인 사항 체크리스트

데이터 수신 후 **고객에게 반드시 확인**해야 하는 항목이다.

| # | 확인 사항 | 이유 | 확인 |
|---|---|---|---|
| 1 | **지급일 컬럼이 존재하는가** | 없으면 MVP 4개 정책 계산 불가 | ☐ |
| 2 | 금액의 **부가세 포함 여부** | 실적 기준 정의에 영향 | ☐ |
| 3 | 취소·반품 표기 방식 | 음수/별도 플래그/제외 여부 | ☐ |
| 4 | 한 계약이 여러 행으로 분할되는가 | 중복 집계 방지 | ☐ |
| 5 | 사업자번호 누락 건의 처리 방침 | 매칭률에 직결 | ☐ |
| 6 | 대상 회계연도·기간 | 집계 범위 확정 | ☐ |
| 7 | 데이터 제공 주기 | 수집·갱신 설계 | ☐ |
| 8 | 기관이 자체 집계한 달성률 수치 보유 여부 | **검증 대조군** | ☐ |

> **8번이 특히 중요하다.** 고객이 기존에 산출한 수치가 있으면
> 시스템 계산 결과를 **대조 검증**할 수 있어 신뢰 확보에 결정적이다.

# 7. 요약

- 본 문서는 **템플릿**이며, 고객 데이터 수신 후 사본을 만들어 작성한다.
- 핵심 산출물은 **① 컬럼 매핑 표, ② 품질 리포트, ③ 오류·매칭률 리포트** 세 가지다.
- **필수 5개 컬럼**(사업자등록번호·업체명·계약일·지급일·구매금액)이 대응되지 않으면
  Import를 진행하지 않고 고객에게 재요청한다.
- **PM 결정 필요 항목**: 사업자번호 체크섬 적용(V-013), 음수 금액 처리(V-033).
