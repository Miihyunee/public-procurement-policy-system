## 2. 상세 판단

### §A. 연도 귀속 — "세금계산서 신고연도" 를 무엇으로 볼 것인가

**고객 답변**

> "1월 1일 ~ 12월 31일 세금계산서 신고가 된 건은 그 해에 다 지출을 하게
> 되어있어서(회계팀 결산 때문에) 그 해는 그 해의 실적으로 해당"

**현재 데이터에 그 필드가 있는가 — 있다.**

| 필드 | 뜻 | 기간 축으로 쓸 수 있는가 |
|---|---|---|
| `resolution_date` | 결의일자 | ✅ 가능 |
| `payment_date` | 지급일 | ✅ 가능 |
| `contract_date` | 계약일 | ✅ 가능 |
| **`issue_date`** | **세금계산서 발행일자**(원본 `신고기준일`) | ❌ **축에 없다** |

`issue_date` 는 `Purchase` 에 존재하고 표준 양식의 필수 컬럼이지만,
`core/period.py` 의 `ALLOWED_DATE_FIELDS` 에는 들어 있지 않다. 즉 **데이터는
있는데 기간 축으로 고를 수 없다.**

**그래서 두 가지로 읽힌다**(`DECISIONS.md` §0.12.14).

```
(가) 연도 귀속 = 신고기준일(issue_date)
     → 기간 축에 issue_date 추가 (작은 변경)

(나) 신고연도 = 결의연도가 실무상 같으므로 기존 결의일자 기준 유지
     → 변경 없음
```

**왜 임의로 못 정하는가**

두 읽기는 **경계 건에서만 갈린다** — 12월 신고 / 이듬해 1월 결의. 고객 문장은
그런 건이 없다는 취지로 읽히지만, 있으면 **분모가 달라진다.**

**확인 방법 (실데이터가 있으면 즉시 판정 가능)**

```
신고기준일 연도 ≠ 결의일자 연도 인 건수를 센다
   0 건   → (가)와 (나)가 같은 결과 → 기존 결의일자 유지로 충분
   N 건   → 그 N 건을 고객에게 보여 주고 어느 해로 볼지 확인
```

⚠️ **한 줄 확인이면 끝나는 사안**이며, 실데이터로 건수를 먼저 세면 질문 자체가
사라질 수도 있다. ⛔ 그 전에 `payment_date` 나 `resolution_date` 를 세금계산서
신고일로 간주하지 않는다.

> ✅ **2026-09-02 · STEP 85 — 실데이터로 세었다. 결과는 `N 건` 이다.**
>
> **5건 · 233,393원** (전부 신고 2026 → 결의 2025 · 12월분 공과금).
> 반대 방향은 0건. → 질문이 사라지지 않았다. 그 5건을 고객에게 보여 드리고
> **어느 해로 볼지** 확인해야 한다. ⛔ 어느 쪽도 채택하지 않았다.
> 상세: `REAL_DATA_FINAL_VALIDATION.md` §4.

**최소 변경 범위 (가)를 택할 경우** — `core/period.py` 의 축 상수·허용집합에
`issue_date` 추가, 설정값으로 선택. 계산식은 그대로.

### §B. 음수 상계 — 저장 제약과 기존 확정 두 가지가 걸린다

**충돌 1 — 매칭 키** (`DECISIONS.md` §0.12.15)

| | 매칭 키 | 적요 |
|---|---|---|
| 🟢 2026-08-20 확정 | 기업 + 사업자번호 + **금액(절대값)** | 자동 선택에 **쓰지 않는다** |
| 2026-08-31 답변 | **적요** + 사업자번호 | 키로 쓰고, 다르면 확인 |

**두 답변을 모두 만족하는 읽기 후보**

```
후보 검색 : 사업자등록번호 + 금액(절대값)        ← 기존 확정 유지
자동 상계 : 후보 1건 이고 적요까지 같을 때        ← 이번 답변 반영
담당자 확인: 후보가 2건 이상이거나 적요가 다를 때  ← 양쪽 모두와 일치
```

이렇게 읽으면 기존 규칙을 버리지 않으면서 이번 답변의 *"적요가 다르면 확인해
줘야 함"* 도 지켜진다. ⛔ 다만 **이것은 제 해석이며 고객이 그렇게 말한 것은
아니다.** 한 줄 확인이 필요하다.

> ✅ **2026-09-02 · STEP 85 — 실데이터로 세었다.** 음수 **129건**.
>
> | 기존 규칙(금액) | 이번 답변(적요) |
> |---|---|
> | 단일 후보 41 · 복수 85 · 없음 3 | 단일 후보 83 · 복수 37 · 없음 9 |
>
> 두 규칙은 **실데이터에서 서로 다른 결과를 낸다.** 금액이 같은 126건 중
> **116건은 적요까지 같고 10건은 적요가 다르다** — 고객이 말한 *"간혹 적요가
> 다를 경우"* 가 실제로 있다. 위 읽기가 실데이터와 모순되지는 않는다는
> 것까지만 확인됐다. ⛔ 매칭 키를 바꾸지 않았다.
> 상세: `REAL_DATA_FINAL_VALIDATION.md` §5.

**충돌 2 — 저장 제약**

```
현재: amount <= 0  →  repository 가 저장 거부  →  음수 행이 DB 에 없다
```

상계하려면 **음수 행이 DB 에 있어야 한다.** 즉 이 항목은 검색 기능 추가와
성격이 다르다.

| 필요한 것 | 성격 |
|---|---|
| `purchase_repository._validate()` 의 `amount <= 0` 제약 완화 | **저장 규칙 변경** |
| 상계 결과를 원본·검토·계산 중 어디에 반영할지 | **계산 경로 변경** |
| 상계 전/후 금액을 모두 보존할 구조 | **설계 필요** |
| 담당자 확인 대상 표현 | 화면 |

⚠️ 상계 판정 로직 자체는 **이미 있다** — `core/offsetting.py`. 다만 그 모듈
머리말에 *"이 모듈은 아직 계산에 연결되어 있지 않습니다"* 라고 적혀 있고,
연결은 **별도 PM 승인 사항**으로 남아 있다(§0.6.3.3 D 단계 ·
`NEGATIVE_OFFSET_WIRING_DESIGN.md`).

**0원은 이번 답변에 없다**(§0.12.16). 답변은 `+`/`−` 상계에 관한 것이다.
⛔ 0원을 상계 대상으로도, 제외로도 확정하지 않는다.

### §C. 예산과목 공란 — "확인 필요" 를 어떻게 표현할 것인가

**고객 답변은 제외 규칙이 아니라 순서다.**

```
공란 발견 → G20 지출결의서 확인(사람) → 예산과목 작성 → 6종 규칙으로 판단
```

⛔ G20 자동 연계는 답변에 없고, 이 시스템은 G20 에 접근하지 않는다(기존 제약
유지). ⛔ 시스템이 예산과목을 추정해 채우지 않는다.

**시스템이 할 일은 하나** — *"이 건은 예산과목 확인이 필요하다"* 를 알리는 것.

**기존 구조에 이미 같은 모양의 전례가 있다.**

| 전례 | 하는 일 |
|---|---|
| 결의일자 미기재(W-15) | 대시보드 안내 + 행 목록 조회 + CSV — 원본을 고치지 않고 **확인 대상만 모아 보여 준다** |

같은 방식이면 새 개념을 만들지 않고 붙는다. ⛔ 다만 **제외 상태로 표시하지
않는다** — 공란은 제외 사유가 아니다.

### §D. 지출결의서 단위 묶음 — 식별정보가 있는가

**결론: 현재 데이터로는 묶을 수 없다.**

| 후보 | 상태 |
|---|---|
| 결의번호 | ❌ **없다** — 🟢 고객 확정 *"결의번호 없음, 식별용 별도 번호도 없음"*(§0.10.6) |
| 기표번호 · `LN_SQ` · `GRP_NB` | ❌ 실측에서 음수 125건 전부 비어 있었고, 판별 기준도 아니다 |
| 적요 + 사업자번호 + 날짜 | ⛔ **결의번호처럼 쓰지 않는다** — 같은 문구가 서로 다른 결의서에 쓰인다(§0.10.6) |

고객은 *"확인할 수 있으면 좋지"* 라고 **기능의 필요성**을 답했을 뿐, **묶는
기준을 답하지 않았다.** 기준 없이 묶으면 담당자가 잘못된 단위로 판단한다.

**따라서 자동 그룹핑은 구현하지 않는다.** 대신 고객이 실제로 쓰는 대조 수단은
이미 있다 — 적요·거래처명·사업자번호 검색, 금액 표시·정렬, 결의일자 정렬.
여기에 §0.12.5 의 **금액 검색**이 더해지면 *"같은 결의서로 보이는 건들을 모아
보는"* 실질적인 방법이 된다.

⚠️ 이것이 고객이 원한 것과 같은지는 **확인이 필요하다.** ⛔ 그러나 식별정보를
만들어 내는 방향으로는 가지 않는다.
