# 1. 왜 이 문서가 필요한가

운영 방식이 다음과 같이 확인되었다.

```text
매월 → 동일 형식 파일 업로드 → 연도 기준으로 누적 관리
```

이 요건을 현재 코드와 대조한 결과 **두 가지가 빠져 있다.**
둘 다 **데이터가 쌓이기 시작하면 즉시 잘못된 숫자를 만든다.**

| # | 문제 | 심각도 |
|---|---|---|
| 1 | **기간 필터가 없다** — 전 기간을 통째로 합산한다 | 🔴 P0 |
| 2 | **중복 적재를 막지 못한다** — 같은 파일을 두 번 올리면 두 배가 된다 | 🔴 P0 |

> 지금은 데이터가 없어 드러나지 않았을 뿐이다. **첫 달에는 문제가 없고, 두 번째 달부터 틀린다.**

# 2. 문제 1 — 기간 필터 부재

## 2.1 현재 코드 (실측)

`ProcurementAchievementCalculator` 는 구매데이터를 가져올 때
`PurchaseRepository.find_all()` 을 사용한다.

```sql
SELECT * FROM purchase ORDER BY purchase_id   -- 기간 조건 없음
```

## 2.2 결과

```text
2026년 데이터 적재 → 달성률 계산 → 2026년 기준으로 맞음 ✅
2027년 데이터 추가 → 달성률 계산 → 2026 + 2027 이 합산됨 ❌
```

| 영향 | 내용 |
|---|---|
| 분모 | 전체 구매액이 **여러 연도 합계**가 된다 |
| 분자 | 정책 인정 금액도 마찬가지 |
| 달성률 | **연간 달성률이 아니다.** 그런데 화면에는 달성률로 표시된다 |

> 🔴 **조용히 틀린다.** 오류도 경고도 나지 않고 그럴듯한 숫자가 나온다.
> 이것이 이 문제가 위험한 이유다.

## 2.3 인증 유효기간과는 별개다

현재도 인증 유효기간 판정은 하고 있다. 하지만 그것은
**"이 거래 시점에 인증이 유효했는가"** 를 보는 것이지,
**"이 거래가 어느 연도 실적인가"** 를 정하는 것이 아니다.

```text
인증 유효기간 판정 : 이미 있음 ✅
연도 귀속 판정     : 없음     ❌
```

# 5. 연도별 집계 설계

## 5.1 연도 귀속 기준 — **W-1 종속**

```text
어느 날짜로 연도를 정하는가?
  → 지급일이 확정되어야 한다 (W-1)
  → 지급일이 어느 컬럼인지 아직 모른다
```

| 정책 | 판정 기준일 | 연도 귀속 |
|---|---|---|
| 중소기업 · 여성기업 · 장애인기업 · 녹색제품 | 지급일 | 지급일의 연도 |
| 창업기업 | **계약일** | ⚠️ **계약일의 연도인가, 지급일의 연도인가** |

> 🔴 **정책마다 판정 기준일이 다른데, 연도 귀속도 그것을 따라야 하는가?**
>
> 한 거래의 계약일이 2026년, 지급일이 2027년이면
> **창업기업은 2026년 실적, 중소기업은 2027년 실적**이 될 수 있다.
> 이러면 **정책별로 분모가 달라진다.**
>
> → **D-24 (PM 결정 필요)**

### D-24 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **가** | **모든 정책이 같은 날짜(지급일)로 연도 귀속** | 분모가 하나로 유지됨. 단순 | 창업기업의 판정 기준일과 연도 기준이 달라짐 |
| 나 | 정책별 판정 기준일로 각각 연도 귀속 | 정책 정의와 일관 | **정책마다 분모가 달라짐**. 해석·설명이 어려움 |

> **어느 쪽도 임의로 정하지 않는다.** 실제 기관의 실적 보고 방식을 확인해야 한다.

## 5.2 회계연도 정의 — **D-23**

| 확인 필요 |
|---|
| 1/1 ~ 12/31 인가 |
| 별도 회계연도(예: 3/1 ~ 다음 해 2월말)인가 |

> 공공기관은 대부분 역년(1/1~12/31)을 쓰지만 **확인 없이 가정하지 않는다.**

## 5.3 구현 방향 (제안)

### Repository — 조회 메서드 추가

```python
def find_by_period(self, start: date, end: date, *, date_field: str) -> list[Purchase]:
    """지정 기간의 구매를 조회한다.

    date_field 는 어느 날짜 컬럼으로 필터링할지 지정한다.
    (W-1 확정 전까지 호출자가 명시하도록 둔다)
    """
```

| 설계 판단 | 이유 |
|---|---|
| **기간을 인자로 받는다** | 연도 하드코딩 금지. 분기·월 조회로도 확장 가능 |
| **날짜 컬럼을 인자로 받는다** | W-1 미확정 상태에서도 **구조를 먼저 만들 수 있다** |
| `find_all()` **유지** | 기존 테스트·호출부를 깨지 않는다 |

### Calculator — 기간을 받도록 확장

```text
현재:  calculate_all(target_rates)              → 전 기간
제안:  calculate_all(target_rates, period=None) → period 지정 시 해당 기간만
```

| 원칙 |
|---|
| **계산 로직 자체는 바꾸지 않는다** — 입력 데이터의 범위만 좁힌다 |
| `period=None` 이면 현재와 동일하게 동작 → **기존 테스트 전부 통과** |

### Dashboard API — 기간 파라미터

```http
GET /dashboard/summary?year=2026
```

| 항목 | 방침 |
|---|---|
| `year` 미지정 시 | 🔴 **D-27 결정 필요** — 5.4 참조 |
| 응답에 대상 기간 명시 | ✅ **필수** — 어느 기간의 숫자인지 화면에서 알 수 있어야 한다 |

## 5.4 기간 미지정 시 동작 — **D-27 (신규)**

| 안 | 동작 | 평가 |
|---|---|---|
| **가** | **최근 연도** 자동 선택 | 편리하나, "언제의 최근"인지 모호 |
| **나** | **400 오류** — 연도를 반드시 지정 | 안전. 실수로 전 기간 합산될 일 없음 |
| 다 | 전 기간 합산 (현재 동작) | 🔴 **위험** — 지금 문제의 원인 |

> **다안은 권장하지 않는다.** 가안·나안 중 선택이 필요하다.

# 6. 중복 적재 방지 설계

## 6.1 무엇을 "같은 거래"로 볼 것인가

원본 파일에 **행 고유 식별자가 있는가**가 핵심이다.

| 후보 | 샘플 관찰 | 사용 가능성 |
|---|---|---|
| `번호` | 파일 내 일련번호 | ❌ 파일마다 1부터 다시 시작 |
| `SEQNO` | 행마다 고유 | ⚠️ **파일 내에서만 고유한지 미확인** |
| `기표번호` · `결의번호` | 일부만 채워짐 (음수행은 전부 0) | ❌ 결측 |
| 조합 키 (사업자번호+날짜+금액+적요) | — | ⚠️ **동일 값 중복이 실제로 존재** |

> 🔴 **샘플에서 "사업자번호 + 날짜 + 금액 + 적요" 가 완전히 같은 행이 실제로 있었다.**
> 즉 **조합 키만으로는 "중복"과 "정상적인 분할 기록"을 구분할 수 없다.**

## 6.2 그래서 제안하는 방향 — **업로드 단위 관리**

행 단위 중복 판정이 불확실하므로, **업로드 단위**로 관리한다.

```text
업로드 이력 (import batch)
  ├─ 파일명 · 업로드 시각 · 대상 기간
  ├─ 행 수 · 금액 합계
  └─ 이 배치로 들어온 purchase 행들
```

| 이 방식의 장점 |
|---|
| 같은 기간을 다시 올렸는지 **확실히 알 수 있다** |
| 잘못 올린 배치를 **통째로 되돌릴 수 있다** |
| 행 단위 식별자가 없어도 동작한다 |
| **어느 달까지 올렸는지 조회할 수 있다** (운영에 필요) |

> 이것이 **D-19(Raw/Cleansed/Eligible 저장 방식)의 답**이기도 하다.
> 매월 누적 운영이면 **원본 추적이 선택이 아니라 필수**다.

## 6.3 동월 재업로드 시 동작 — **D-25 (PM 결정 필요)**

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **가** | **기존 배치를 대체** (이전 배치 무효화 후 새로 적재) | 수정본 반영이 자연스러움. 매월 운영에 가장 흔함 | 이전 데이터가 사라짐 (배치 이력은 남음) |
| 나 | **거부 + 경고** — 삭제는 명시적으로 | 실수로 덮어쓸 일 없음 | 수정본 반영 시 매번 삭제 절차 필요 |
| 다 | 중복 행만 걸러내고 새 행만 추가 | 자동 | 🔴 **6.1 때문에 정확한 판정 불가** |

> **다안은 권장하지 않는다.** 조합 키로 중복을 판정할 수 없기 때문이다.
> **가안이 매월 운영에서 가장 현실적**이나, 결정은 PM 몫이다.

## 6.4 어느 쪽이든 지켜야 할 것

| 원칙 |
|---|
| 재업로드 시 **이전 배치의 건수·금액을 먼저 보고**한다 |
| 대체하는 경우 **무엇이 사라지는지 확인 후 진행** |
| 배치 이력은 **삭제하지 않는다** |
| 조용히 덮어쓰지 않는다 |
