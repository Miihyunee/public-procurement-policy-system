# 1. 정책 3개 그룹 재분류

## 1.1 분류 기준

현재 계산 구조가 성립하려면 **세 조건**을 모두 만족해야 한다(코드 확인 사실).

| # | 조건 | 근거 코드 |
|---|---|---|
| 1 | 분모 = **전체 구매금액** | `_achievement_rate(policy_amount, total_amount, ...)` |
| 2 | 목표율 = **정책당 단일값** | `Policy.target_rate: Decimal \| None` |
| 3 | 판정 = **기업 인증 + 유효기간 + 기준일** | `DateBasisRule.matches()` |

## 1.2 그룹 A — 현재 구조로 계산 가능

> 조건 1·2·3 을 모두 만족. **코드 변경 없이** 정책 등록 + 인증데이터만 확보하면 계산된다.

| 정책 | ① 목표율 | ① 분모 | 근거 |
|---|---|---|---|
| **중소기업** | 50% | 총 구매금액 | 단일 목표율 · 기업 인증 · 표준 분모 |

| **장애인기업** | 1% | 총 구매금액 | 〃 |
| 사회적기업 | 3% | 총 구매금액 | 〃 — 현재 MVP 미포함 |
| 사회적협동조합 | 0.1% | 총 구매금액 | 〃 — 현재 MVP 미포함 |

# 2. 여성기업 — 데이터 요구사항 확정 (코드 수정 없음)

## 2.1 ① [정부확인] 기준

> **7. 여성기업(총 구매금액의 공사 3% 이상 및 용역·물품 5% 이상)**

| 구매유형 | 목표율 |
|---|---|
| 공사 | 3% |
| 용역·물품 | 5% |

### ⚠️ 분모 해석이 모호하다 → `미확인`

원문 "**총 구매금액의** 공사 3% 이상" 은 두 가지로 읽힌다.

| 해석 | 계산식 | 결과 차이 |
|---|---|---|
| **해석 ①** | 여성기업 공사 구매액 ÷ **전체 총 구매금액** ≥ 3% | 분모 공통 |
| **해석 ②** | 여성기업 공사 구매액 ÷ **공사 총 구매액** ≥ 3% | 분모가 유형별로 분리 |

**어느 쪽인지에 따라 필요한 데이터와 계산 구조가 달라진다.**
해석 ②라면 **유형별 총액**도 집계해야 하므로 구조 변경 폭이 커진다.
→ **공식 근거 확인 없이 결정하지 않는다.**

## 2.2 질문별 답변

### Q1. 현재 구매데이터에 공사/용역/물품 구분 필드가 있는가?

**❌ 없다.** `Purchase` 모델의 전체 필드는 다음뿐이다(코드 확인).

```
business_no, company_name, contract_date, payment_date, amount,
company_id, purchase_id, created_at, updated_at
```

구매유형·품목·계약방법 관련 필드가 **전혀 없다.**

### Q2. 없다면 어떤 최소 필드가 추가되어야 하는가?

**최소 1개 필드**로 충족 가능하다.

| 필드(안) | 타입 | 값 | 필수 여부 |
|---|---|---|---|
| `purchase_type` | TEXT (nullable) | `CONSTRUCTION`(공사) / `SERVICE`(용역) / `GOODS`(물품) | **nullable 권장** |

- **nullable 로 두는 이유**: 기존 데이터와 다른 정책에 영향을 주지 않기 위해서다.
  값이 없으면 유형 조건이 없는 정책은 지금과 동일하게 계산된다.
- 용역과 물품은 ① 기준에서 **같은 목표율(5%)** 이므로, 최소 구현에서는
  `SERVICE`/`GOODS` 를 구분하지 않고 하나로 묶어도 계산은 성립한다.
  다만 **원본 정보를 잃지 않도록 3종으로 저장**하고 계산 시 묶는 편이 안전하다.

### Q3. 구매유형별 목표율을 현재 `Policy.target_rate` 로 표현할 수 있는가?

**❌ 불가능하다.** `target_rate: Decimal | None` 은 **단일값**이다.
한 정책에 3%와 5% 두 값을 담을 수 없다.

### Q4. 최소한의 데이터 모델 변경안

두 가지 안을 제시한다. **어느 쪽도 이번에 구현하지 않는다.**

#### 안 ①: 정책 분리 (변경 최소)

| 변경 | 내용 |
|---|---|
| `Purchase` | `purchase_type` 필드 추가 (nullable) |
| `Policy` | `applicable_purchase_type` 필드 추가 (nullable) |
| 정책 등록 | `WOMAN_CONSTRUCTION`(공사, 3%) / `WOMAN_GOODS_SERVICE`(용역·물품, 5%) **2행으로 등록** |
| Calculator | 정책에 유형 조건이 있으면 해당 유형 구매만 집계 |

- **장점**: 새 테이블 없음. 필드 2개 추가로 끝. 기존 구조를 그대로 사용
- **단점**: 대시보드에 **여성기업이 2줄로 표시**됨. 정책 코드가 실제 제도명과 달라짐

#### 안 ②: 목표율 테이블 분리 (구조적으로 정확)

| 변경 | 내용 |
|---|---|
| `Purchase` | `purchase_type` 필드 추가 (nullable) |
| 신규 테이블 | `policy_target_rate(policy_id, purchase_type, target_rate)` |
| `Policy.target_rate` | 유형 구분이 없는 정책용으로 유지(하위호환) |
| Calculator | 정책별로 유형별 목표율을 조회해 각각 계산 |
| API | 정책 하나에 **유형별 달성률 목록**을 담도록 응답 확장 |

- **장점**: 제도와 구조가 일치. 향후 유형별 목표율이 더 생겨도 대응 가능
- **단점**: 테이블·API 응답 구조 변경. 작업량이 안 ①보다 큼

> **권장은 제시하지 않는다.** 선택은 2.1의 **분모 해석(`미확인`)** 이 확정된 뒤에
> 하는 것이 맞다. 해석 ②(유형별 분모)라면 안 ②가 사실상 강제된다.

### Q5. 기존 중소기업·창업기업·장애인기업 계산에 영향을 주는가?

**영향 없도록 설계할 수 있다.**

| 조건 | 결과 |
|---|---|
| 새 필드를 **nullable** 로 추가 | 기존 데이터는 값이 비어 있음 |
| 기존 정책에 **유형 조건 없음**(NULL) | 유형 필터가 적용되지 않아 **현재와 동일하게 전체 집계** |
| Calculator | 유형 조건이 있는 정책만 추가 필터를 적용 |

단, **DB 스키마 변경이 필요**하므로 기존 DB에는 컬럼이 추가되지 않는다
(`CREATE TABLE IF NOT EXISTS` 특성). Bootstrap Health Check 가 이를 감지하도록
되어 있으나, **기존 DB 처리 방침은 별도 필요**하다.

## 2.3 결론

| 항목 | 결론 |
|---|---|
| 현재 계산 가능 여부 | **불가능** |
| 최소 추가 필드 | `Purchase.purchase_type` **1개** |
| 목표율 표현 | 현재 구조로 **불가** → 모델 변경 필요 |
| 기존 정책 영향 | **없게 설계 가능**(nullable) |
| **선결 조건** | ⚠️ **고객 데이터에 구매유형 구분이 있는가** + **분모 해석 확정** |

> **고객 데이터에 구분이 없으면 어떤 구조를 만들어도 계산할 수 없다.**
> 개발보다 **데이터 확인이 먼저**다.

## 3.1 판정 기준일에 대한 중요 고지

| 사실 | 내용 |
|---|---|
| ① 정부 파일 | 지급일·계약일에 대한 언급이 **전혀 없다** |
| ② 프로젝트 | `POLICY_DEFINITION.md` 가 자체적으로 4종에 기준일을 부여했다 |
| ③ 미확인 | **그 설계의 근거 출처가 프로젝트 문서에 기재되어 있지 않다** |

> 즉 **"창업기업은 계약일 기준"은 현재 정부 기준으로 확인된 사항이 아니다.**
> 이미 코드·테스트에 반영되어 동작 중이므로, **근거 확인이 필요**하다.

# 4. 정책 간 의존성 분석

## 4.1 기술개발생산품 — 분모가 다른 정책의 결과

### ① [정부확인] 기준
> **3. 중소기업생산품 구매액의 15% 이상**

분모가 **"중소기업생산품 구매액"** 이다. 이는 정책 1(중소기업)의 **계산 결과**다.

### 계산 의존 관계

```
전체 구매금액
     ↓
중소기업 구매액          ← 정책 1의 분자
     ↓  (분모로 사용)
기술개발생산품 구매액     ← 정책 3의 분자
     ↓
기술개발생산품 달성률
```

**정책 3의 계산이 정책 1의 계산 결과에 의존한다.**

### 현재 Calculator 로 처리 가능한가 — ❌ **불가능**

| 이유 | 설명 |
|---|---|
| 1 | 분모가 `total_amount` 로 고정되어 있어 다른 값을 넣을 수 없다 |
| 2 | 정책은 서로 **독립적으로** 계산된다. 계산 순서·의존 개념이 없다 |
| 3 | "기술개발생산품"이 무엇인지 **판정할 데이터가 없다** (제품 인증 `미확인`) |

### 필요한 설계 방향 (제안만, 구현 없음)

| # | 필요 요소 |
|---|---|
| 1 | **분모 유형(denominator type)** 개념 도입 — 아래 4.4 참조 |
| 2 | 정책 간 **의존 관계 정의**(정책 3의 분모 = 정책 1의 분자) |
| 3 | 계산 **순서 보장**(의존 정책 우선 계산) |
| 4 | 기술개발생산품 **판정 기준 데이터** 확보 (`미확인`) |

> ⚠️ 순환 참조 방지 장치도 필요하다(A가 B에 의존하고 B가 A에 의존하는 경우).

## 4.2 온누리상품권 — 분모가 구매데이터 밖

### ① [정부확인] 기준
> **6. 온누리상품권 구매(기관 경상경비 금액의 1.5% 이상)**

| 항목 | 내용 |
|---|---|
| 분모 | **기관 경상경비 금액** — 구매데이터에 존재하지 않는 값 |
| 분자 | 온누리상품권 구매액 |
| 기업 인증 | **불필요**(상품권 구매 여부이지 기업 자격이 아님) |

### 현재 구조로 처리 가능한가 — ❌ **불가능**

- 분모 데이터 자체가 **시스템에 들어올 경로가 없다**.
- 기업 인증 기반 판정 구조(`Certification`)와 **성격이 다르다**.
- ① 파일도 업무자동화 DB 활용을 **`-`** 로 표시해 기업리스트 대상이 아님을 시사한다.

### 필요한 설계 방향
- **기관 단위 기준금액 입력 수단**(경상경비 총액) — 구매데이터가 아닌 별도 입력
- 인증 판정을 거치지 않는 **별도 계산 경로**

## 4.3 국가유공자자활용사촌 — 분모가 품목군

### ① [정부확인] 기준
> **11. 국가유공자자활용사촌(자활용사촌 생산가능품목 총 구매액의 7% 이상)**

|---|---|
| 분모 | **자활용사촌 생산가능품목의 총 구매액** |
| 분자 | 자활용사촌 구매액 |

**분자와 분모가 모두 품목 조건에 걸린다.**

### 현재 구조로 처리 가능한가 — ❌ **불가능**

| 이유 |
|---|
| `Purchase` 에 품목·물품목록번호 필드가 없다 |

### 필요한 설계 방향
- `Purchase` 에 **품목 식별 필드**
- **생산가능품목 기준 데이터**(마스터)
- 분모 유형 = 품목군 한정

# 6. 장애인표준사업장 목표율 — 확인 필요사항

## 6.1 원문 표기

> **9. 장애인표준사업장(총 구매금액의 1000분의 8% 이상)**

## 6.2 왜 임의 확정하면 안 되는가

"1000분의 8%" 는 **두 가지로 읽힐 수 있고, 값이 100배 차이 난다.**

| 해석 | 값 | 비고 |
|---|---|---|
| 해석 A | **0.8%** (= 1000분의 8) | "%" 가 잘못 붙은 표기로 보는 경우 |
| 해석 B | **0.008%** (= 1000분의 8퍼센트) | 문자 그대로 읽는 경우 |

> 다른 항목들이 모두 "N% 이상" 형식인데 **이 항목만 "1000분의" 표기**를 쓴 점,
> 그리고 **뒤에 "%" 가 함께 붙은 점**이 표기 혼선의 원인으로 보인다.
> **파일만으로는 판단할 수 없다** → `미확인`.

## 6.3 확인해야 할 사항

| # | 확인 항목 | 확인처(대상) |
|---|---|---|
| 1 | 장애인표준사업장 생산품 **의무구매 비율의 공식 수치** | 근거 법령·고시 원문 |
| 2 | 해당 비율의 **분모 정의** | 총 구매금액인지 별도 기준인지 |
| 3 | 본 파일의 표기가 **오기인지 의도된 표기인지** | 파일 작성 주체 |
| 4 | 적용 연도 | 2026년 기준이 맞는지 |

> **확정 전까지 이 정책은 등록하지 않는다.** 잘못된 목표율은 달성률을 100배 왜곡한다.
