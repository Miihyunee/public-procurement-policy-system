# 1. 목적과 범위

## 1.1 목적

고객 구매데이터를 시스템 안으로 넣고 **계산 엔진까지 끊김 없이 연결**하는 기반을 만든다.

```
고객 구매데이터 → Import → 정규화 → Company 연결 → Certification → 정책 판정 → 달성률
```

## 1.2 포함 / 제외

| 포함 | 제외 |
|---|---|
| 행 단위 Import (컬럼 매핑 후 데이터) | **파일 파싱(Excel/CSV)** — 실제 파일 규격 확인 후 |
| 사업자등록번호 정규화 | 외부 API Collector |
| 값 파싱·Validation | 음수 금액 허용(별도 Issue) |
| Company 연결(매칭) + 재매칭 | 선택 컬럼 저장 필드 확장 |
| 정상/경고/실패 구분 리포트 | |

> 파일 파싱을 제외한 이유: 실제 고객 파일의 인코딩·시트 구성·헤더 형태를 아직 모른다.
> **추측으로 구현하지 않는다**는 원칙에 따라, 파일 → 행(dict) 변환은 실데이터 확인 후 붙인다.
> 본 설계의 Import는 "이미 컬럼 매핑이 끝난 행"을 입력으로 받는다.

# 2. 입력

## 2.1 최소 필수 필드

| 키 | 의미 | 시스템 필드 |
|---|---|---|
| `business_no` | 사업자등록번호 | `purchase.business_no` |
| `amount` | 구매금액 | `purchase.amount` |
| `contract_date` | 계약일 | `purchase.contract_date` |
| `payment_date` | 지급일 | `purchase.payment_date` |
| `company_name` | 업체명 (필수, 보조) | `purchase.company_name` |

`company_name` 이 비어 있으면 저장이 불가능하므로(모델 필수), 값이 없을 때는
**`"(미상)"` 로 대체하고 경고**를 남긴다. 사업자번호가 있으면 계산은 가능하기 때문에
업체명 때문에 행을 버리지 않는다.

## 2.2 허용 입력 형태

| 항목 | 허용 형태 |
|---|---|
| 사업자번호 | `123-45-67890`, `1234567890`, `" 1234567890 "`, 숫자형(`1234567890`) |
| 날짜 | `date`/`datetime` 객체, `YYYY-MM-DD`, `YYYYMMDD`, `YYYY/MM/DD`, `YYYY.MM.DD` |
| 금액 | `Decimal`, `int`, `float`, `"3,000,000"`, `"3000000원"` |

# 3. 처리 흐름

```
원본 행
  ↓
[1] 컬럼 매핑        (호출자가 수행 — 매핑 템플릿 사용)
  ↓
[2] 값 정규화        사업자번호 / 날짜 / 금액
  ↓
[3] Validation      필수값·형식·금액 검증
  ↓
[4] Company 연결     정규화된 사업자번호로 조회
  ↓
[5] Purchase 저장    company_id 포함(미매칭이면 NULL)
  ↓
결과 집계 (정상 / 경고 / 실패)
```

## 3.1 결과 구분

| 상태 | 의미 | 저장 여부 |
|---|---|---|
| **IMPORTED** | 정상 적재 | ✅ 저장 |
| **WARNING** | 저장했으나 확인 필요 | ✅ 저장 |
| **FAILED** | 검증 실패로 적재 불가 | ❌ 저장 안 함 |

### WARNING 이 되는 경우

| 사유 | 근거 |
|---|---|
| 사업자번호 **체크섬 오류** | PM 결정 D-002 — 차단하지 않음 |
| 사업자번호 **자릿수 보정**(9자리 → 앞 0 채움) | Excel 앞자리 0 소실 복구 |
| **Company 미매칭** | 정책 실적에서 빠지므로 확인 필요 |
| 업체명 없음 → `(미상)` 대체 | 계산에는 영향 없음 |
| **계약일 > 지급일** | 선지급·정산으로 실제 발생 가능(거부 아님) |

### FAILED 가 되는 경우

| 사유 |
|---|
| 사업자번호 없음/빈 값 |
| 사업자번호 형식 오류(정규화 후 10자리 숫자 불가) |
| 계약일 또는 지급일 없음 / 파싱 불가 |
| 금액 없음 / 숫자 변환 불가 |
| **금액 0 이하** (현재 코드 제약 — 5장 참조) |

> **FAILED 행은 버리지 않고 리포트에 사유와 함께 남긴다.** 원본은 고객이 보관하며,
> 시스템은 "왜 못 넣었는지"를 설명할 수 있어야 한다.

# 4. 사업자등록번호 정규화 규칙

**이 프로젝트의 결합키이므로 가장 엄격하게 정의한다.**

## 4.1 정규화 절차

```
입력값
 ↓ ① 문자열 변환 (숫자형 대응: 1234567890.0 → "1234567890")
 ↓ ② 앞뒤 공백 제거
 ↓ ③ 하이픈·공백·마침표 등 구분자 제거
 ↓ ④ 남은 문자가 모두 숫자인지 확인
 ↓ ⑤ 자릿수 확인 (**정확히 10자리. 자동 보정하지 않음**)
 ↓ ⑥ 체크섬 검증 (실패해도 통과, 경고만)
정규화된 10자리 문자열
```

> ⚠️ **자릿수를 자동 보정하지 않는다 (PM 결정).**
> 사업자등록번호는 시스템의 **핵심 결합 키**이므로 근거 없이 값을 만들면
> **다른 기업과 잘못 연결될 위험**이 있다. 9자리 값(Excel 에서 앞자리 `0` 이
> 사라진 것으로 추정되는 경우)도 **보정하지 않고 형식 오류로 처리**하며,
> 원본 값은 보존해 추적할 수 있게 한다.

## 4.2 입력별 처리 정의

| 입력 | 결과 | 상태 |
|---|---|---|
| `"123-45-67890"` | `"1234567890"` | ✅ 정상 |
| `"1234567890"` | `"1234567890"` | ✅ 정상 |
| `" 1234567890 "` | `"1234567890"` | ✅ 정상 (공백 제거) |
| `1234567890` (숫자형) | `"1234567890"` | ✅ 정상 |
| `1234567890.0` (실수형) | `"1234567890"` | ✅ 정상 |
| `None` | — | ❌ **누락** |
| `""` | — | ❌ **누락** |
| `"   "` (공백만) | — | ❌ **누락** |
| `"123456789"` (9자리) | — | ❌ **형식 오류** (자동 보정 안 함) |
| `"12345678901"` (11자리) | — | ❌ **형식 오류** |
| `"12345abcde"` | — | ❌ **형식 오류** |
| 체크섬 불일치 | 그대로 사용 | ⚠️ **경고** (D-002) |

> **9자리를 보정하지 않는 이유 (PM 결정)**: Excel 에서 앞자리 `0` 이 사라져 9자리가 되는
> 사례가 흔하지만, **보정한 값이 실제 사업자번호라는 근거가 없다.** 사업자등록번호는
> 핵심 결합 키이므로 잘못 보정하면 **다른 기업의 실적으로 집계**될 수 있다.
> 따라서 형식 오류로 처리하되, 오류 메시지에 원인 가능성을 안내하고 원본을 보존해
> 담당자가 원본 파일에서 확인할 수 있게 한다.

## 4.3 체크섬 규칙

가중치 `[1,3,7,1,3,7,1,3,5]` 를 앞 9자리에 곱해 합산하고, 9번째 자리 × 5의 십의 자리를
더한 뒤 `(10 - 합 % 10) % 10` 이 마지막 자리와 같은지 확인한다.

**불일치해도 데이터를 버리지 않는다**(PM 결정 D-002). 리포트에만 기록한다.

## 4.4 정규화 적용 지점

| 지점 | 필요성 |
|---|---|
| **구매데이터 Import** | ✅ 구현됨 |
| **외부 인증데이터 수집** | ⚠️ Collector 구현 시 **반드시 동일 함수 사용** |

> **양쪽 모두 정규화해야 한다.** 한쪽만 하면 형식이 어긋나 매칭이 실패한다.
> 이를 위해 정규화 로직을 `matchers/business_no.py` 로 분리해 재사용 가능하게 두었다.

# 5. 금액 0 이하 처리 (미해결 — 별도 Issue)

| 구분 | 내용 |
|---|---|
| **PM 결정 (D-003)** | 음수 금액을 Import 단계에서 차단하지 않고 **원본 보존** |
| **현재 코드** | `purchase_repository.py` 가 `amount <= 0` 을 거부 |
| **결과** | **충돌** — 현재는 음수·0 행이 `FAILED` 로 분류된다 |

Import 계층은 금액을 임의로 바꾸지 않으며, 저장 거부 사유를 그대로 리포트한다.
Repository 검증 완화는 **별도 구현 Issue**로 관리한다(본 단계 범위 밖 — PM 지시 10항).

# 6. Company 연결 (매칭) 설계

## 6.1 연결 방식

Import 시 정규화된 사업자번호로 `Company` 를 조회해 `Purchase.company_id` 를 채운다.
조회에 실패하면 `company_id` 를 비운 채 저장한다.

```
Purchase.business_no (정규화됨)
        ↓ CompanyRepository.find_by_business_no (완전 일치)
Company.company_id  → 있으면 연결 / 없으면 NULL
```

## 6.2 Q1 — 사업자번호가 Company 에 없을 때 (PM 결정 요청)

| 방안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. Import 실패** | 행을 저장하지 않음 | 데이터 정합성 단순 | **전체 구매액이 왜곡된다.** 미인증 업체 구매도 분모에는 포함되어야 하는데 사라짐. 초기에는 Company 가 비어 있어 **전 행 실패** |
| **B. Company 자동 생성** | 구매데이터로 Company 생성 | 매칭률 100% | **대표자명을 알 수 없음**(현재 필수). 외부 API 수집 시 **중복·충돌** 발생. 인증 없는 껍데기 기업이 대량 생성 |
| **C. 미매칭 보관 후 검수** | `company_id=NULL` 로 저장, 나중에 재매칭 | 전체 구매액 정확. **재매칭 가능**. 기존 모델과 이미 정합 | 매칭률 관리가 필요 |

### 권장: **C (미매칭 보관 후 검수)**

근거는 다음과 같다.

1. **현재 데이터 모델이 이미 C를 전제로 한다.** `Purchase.company_id` 는 nullable 이고
   `find_unmatched()` 조회가 이미 존재한다. 새로운 개념을 만들지 않는다.
2. **계산 정확성**: 매칭 실패 건도 전체 구매액(분모)에 포함되어야 달성률이 왜곡되지 않는다.
   A안은 분모를 줄여 **달성률을 실제보다 높게** 만든다.
3. **외부 API 수집 구조와 맞는다.** 기업정보는 이후 외부에서 들어온다.
   B안으로 미리 만들면 나중에 수집한 정보와 **중복·충돌 정리 비용**이 든다.
4. **되돌리기 쉽다.** C로 쌓아두면 이후 A·B 어느 쪽으로도 전환할 수 있다.
   반대로 B로 만들어 버린 기업 데이터는 되돌리기 어렵다.

> A·B가 필요하다고 판단하시면 변경 지점은 Import의 매칭 단계 한 곳이며, 작업량은 작다.

## 6.3 재매칭 (경우 B 대응)

PM 지시 7항의 두 유입 순서 중, 실제로는 **경우 B(구매데이터 먼저)** 가 자주 발생한다.

```
경우 B:  구매데이터 먼저 → Company 없음 → 미매칭 보관
                              ↓
                    외부 기업정보 수집 → Company 생성
                              ↓
                    재매칭 → company_id 채워짐 → 달성률 반영
```

### 해결 방안

`CompanyMatcher.match_all()` 을 **재매칭 수단**으로 사용한다.

- 미매칭(`company_id IS NULL`) 건만 대상으로 하므로 **반복 실행해도 안전**하다.
- 이미 매칭된 건은 건드리지 않는다(멱등).
- 인증데이터 수집 후 한 번 실행하면 기존 구매데이터가 자동으로 연결된다.

즉 **유입 순서와 무관하게 최종 결과가 같아진다.** 이것이 C안을 택하는 실질적 이유다.

## 6.4 G-4 (Matcher 미배선) 해소

| 이전 | 이후 |
|---|---|
| `CompanyMatcher` 가 어디에서도 호출되지 않음 | Import가 매칭을 수행하고, `rematch()` 로 재매칭 제공 |

# 7. Certification 연결 설계

## 7.1 연결 흐름

Import는 Certification 을 직접 다루지 않는다. **연결은 계산 시점에 이루어진다.**

```
Purchase.company_id  (Import 가 채움)
        ↓
Certification (company_id + policy_id)  ← 외부 수집으로 적재
        ↓
Policy.evaluation_basis 로 판정 기준일 선택
        ↓
valid_from ≤ 기준일 ≤ valid_to  (경계 포함)
        ↓
정책별 구매금액 집계 → 달성률
```

이 흐름은 **이미 구현·검증되어 있다**(`tests/test_end_to_end_chain.py`).
Import 가 `company_id` 를 채우면 나머지는 기존 계산 경로가 그대로 처리한다.

## 7.2 현재 제약

| 항목 | 상태 |
|---|---|
| Certification 적재 경로 | ❌ **없음** — 외부 API 필요 (G-1) |
| 계산 로직 | ✅ 구현·검증 완료 |

> 따라서 **Import 를 완성해도 인증데이터가 없으면 정책 실적은 0** 이다.
> Import 는 "구매데이터 쪽 연결"을 담당하고, 나머지 절반은 API 확보에 달려 있다.

# 8. 리포트

Import 결과는 아래를 포함한다.

```
전체 행       : ____
정상 적재     : ____
경고          : ____   (저장됨)
실패          : ____   (저장 안 됨)
기업 매칭     : ____   (매칭률 __%)
미매칭        : ____
```

행별로 **행 번호 · 상태 · 사유** 를 남겨 고객에게 설명할 수 있게 한다.

> **매칭률은 달성률 신뢰도 지표**이므로 반드시 함께 보고한다.
> 매칭률이 낮으면 달성률이 실제보다 낮게 나온다.

# 9. 요약

- Import 는 **행 단위**로 동작하며, 파일 파싱은 실데이터 확인 후 붙인다.
- 사업자번호 정규화를 **공용 함수**로 분리해 Import·수집 양쪽에서 쓰도록 했다.
- 미매칭은 **버리지 않고 보관**하며(C안), 이후 `rematch()` 로 자동 연결된다.
- Certification 연결은 기존 계산 경로가 담당하며, **외부 API 확보가 남은 절반**이다.
