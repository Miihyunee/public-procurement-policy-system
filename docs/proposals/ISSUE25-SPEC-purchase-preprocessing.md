# 2. 데이터 처리 경계 (3단계 분리)

> **원본을 훼손하지 않고, 계산 대상만 좁혀 나가는 구조**로 설계한다.

```text
① 원본 데이터 (Raw)
      고객이 제공한 파일 그대로. 변형·삭제하지 않는다.
      ↓  [전처리 1] 집계행 식별
② 정제/전처리 데이터 (Cleansed)
      거래가 아닌 행(집계행)을 계산 대상에서 배제.
      매출/매입 구분값을 부여.
      ↓  [전처리 2] 정책 계산 대상 판정
③ 정책 계산 대상 데이터 (Eligible)
      우선구매 실적 계산에 사용할 행.
```

## 2.1 각 단계의 정의와 책임

| 단계 | 정의 | 이 단계에서 **하는 것** | 이 단계에서 **하지 않는 것** |
|---|---|---|---|
| **① 원본** | 고객 제공 파일 그대로 | 보관, 형식 확인 | 값 변경·행 삭제 |
| **② 정제** | 거래가 아닌 행을 배제하고 구분값 부여 | 집계행 식별, 매출/매입 구분 | 금액 재계산, 날짜 해석, 유형 분류 |
| **③ 계산 대상** | 정책 실적 계산에 투입할 행 | 대상 여부 판정 | 정책별 판정(그건 Calculator 책임) |

## 2.2 핵심 원칙 — **행을 삭제하지 않는다**

| 원칙 | 이유 |
|---|---|
| **원본 행을 물리 삭제하지 않는다** | 제외 사유를 추적할 수 없게 되면 "왜 이 금액이 빠졌는가"에 답할 수 없다 |
| **제외는 "삭제"가 아니라 "표시"** | 집계행·매출행도 저장하되 계산 대상에서만 뺀다 |
| **제외 건수·금액을 반드시 보고** | 조용한 누락은 잘못된 달성률보다 위험하다 |

> ⚠️ 지시서 3장의 "원본 데이터 자체를 삭제하지 않는다"를 이렇게 구현한다.

## 2.3 저장 방식 후보 (구현 시 선택 — 아직 결정하지 않음)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **가** | 제외 행을 **저장하지 않고**, Import 리포트에만 남김 | 스키마 변경 없음 | 사후 추적 불가 |
| **나** (권장 방향) | 전 행을 저장하되 **구분 필드**로 계산 대상 여부 표시 | 추적 가능, 재판정 가능 | 스키마 변경 필요 |
| 다 | 별도 테이블에 원본 보관 | 완전 분리 | 복잡도 증가 |

> **결정하지 않았다.** 세 안의 상세 비교는 `docs/PREPROCESSING_DECISION_ANALYSIS.md` 5장 참조.
> **샘플만으로 스키마를 확정하지 않는다** → **D-19**

# 3. P0-A. 집계행 식별 / 제외 설계

## 3.1 문제

샘플에서 `[소계]` · `[누계]` · `[분기계]` · `합계` 6건이 데이터 영역에 섞여 있었다.
제외하지 않으면 **총액이 약 2배로 계산**된다. 실제 운영데이터에도 집계행이 포함될 수
있으므로 전처리에서 반드시 판별해야 한다.

## 3.2 식별 규칙 — **[샘플-관찰]**

| # | 규칙 | 근거 | 해당 건수 |
|---|---|---|---|
| R-1 | `세무구분` 값이 `[소    계]` / `[누    계]` / `[분 기 계]` 중 하나 | 샘플 값 확인 | 5건 |
| R-2 | `번호` 값이 `합계` | 샘플 값 확인 | 1건 |

> **[운영-확인필요]**: 실제 운영데이터에 **다른 집계 표기**가 있을 수 있다.
> 알려진 목록은 고정값이 아니라 **현재까지 확인된 목록**이다.

> ⚠️ **공백에 주의**: 샘플의 값은 `[소    계]` 처럼 **내부에 공백이 들어 있다**.
> 단순 문자열 비교 시 공백 정규화가 필요하다.

## 3.3 설계 방침

| 항목 | 방침 |
|---|---|
| 판정 위치 | **전처리 계층**(Parser 이후, Import 이전). Calculator·Repository 를 건드리지 않는다 |
| 판정 방식 | **명시적 값 목록 대조**. "금액이 크다", "마지막 행이다" 같은 휴리스틱을 쓰지 않는다 |
| 예상 밖 값 발견 시 | ⛔ **자동 제외하지 않고 경고로 보고**. 새로운 집계 표기가 나오면 사람이 판단한다 |
| 결과 보고 | 제외 건수·금액을 Import 리포트에 반드시 포함 |

## 3.4 위험

| 위험 | 대응 |
|---|---|
| 집계 표기가 파일마다 다를 수 있음 | 알려진 목록 외 값은 **경고 후 계산 대상 유지**(누락보다 과대 계상이 눈에 띄기 쉬움) → **PM 결정 필요 D-18** |
| `번호` = `합계` 판정이 다른 파일에서 다를 수 있음 | 두 규칙을 **OR** 로 적용하고 각각 몇 건이 걸렸는지 리포트 |

# 4. P0-B. 매출/매입 구분 및 정책 계산 대상 판정 설계

## 4.1 문제

샘플에서는 데이터행의 **79.4%가 매출**이었다. 구분 없이 집계하면 분모가 왜곡되고
매출 거래처가 구매 거래처로 잘못 등록된다.
**[운영-확인필요]**: 실제 비율은 다를 수 있으나, **매출이 섞여 들어올 수 있는 형식**이라는
사실 자체가 설계 요구사항이다.

## 4.2 샘플에서 관찰된 값 — **[샘플-관찰]**

| `세무구분` | 건수 | 성격 |
|---|---|---|
| `[13]면세매출` | 2,306 | 매출 |
| `[24]매입불공제` | 479 | 매입 |
| `[21]과세매입` | 77 | 매입 |
| `[23]면세매입` | 41 | 매입 |

## 4.3 3단 구분 설계 — **중요**

지시서 3장의 요구대로 **"매입"과 "정책 계산 대상"을 같은 것으로 보지 않는다.**

```text
거래 구분(transaction kind)     : 매출 / 매입 / 미분류
        ↓ (매입만 후보)
정책 계산 대상 여부(eligible)   : 대상 / 대상 아님 / 판정 보류
```

| 구분 | 판정 근거 | 현재 상태 |
|---|---|---|
| **거래 구분** | `세무구분` 문자열에 `매출` / `매입` 포함 여부 | ✅ **확정 가능** |
| **정책 계산 대상 여부** | 업무 기준 | 🔴 **미확정 — 고객 확인 필요(W-7)** |

> **"매입 = 우선구매 실적 전체" 라고 확정하지 않는다.**
> 부가세 신고 대상이 아닌 지출이 이 원장에서 빠져 있을 수 있다.

## 4.4 판정 규칙 (설계안)

| # | 조건 | 거래 구분 | 계산 대상 |
|---|---|---|---|
| K-1 | 집계행 | — | **제외** |
| K-2 | `세무구분` 에 `매출` 포함 | 매출 | **제외** |
| K-3 | `세무구분` 에 `매입` 포함 | 매입 | **대상 후보** |
| K-4 | 그 외 / 빈값 | **미분류** | ⛔ **판정 보류 + 경고** |

> **K-4 를 임의로 매입이나 매출로 밀어넣지 않는다.** 샘플에서는 0건이었지만,
> 실제 운영데이터에서 나타날 수 있다.

## 4.5 보고 항목 (필수)

| 항목 |
|---|
| 원본 행 수 |
| 집계행 제외 건수·금액 |
| 매출 제외 건수·금액 |
| 미분류(보류) 건수·금액 |
| **계산 대상 행 수·금액** |

> 세 단계의 건수·금액이 **원본과 합이 맞는지** 검증할 수 있어야 한다.

## 8.1 이미 확정된 것
