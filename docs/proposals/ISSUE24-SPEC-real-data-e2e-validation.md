# 1. 검증 목적

현재 시스템은 **최소 Fixture 로는 전 구간이 동작함이 확인**되어 있다(테스트 516건 통과).
그러나 아직 **실제 데이터로 한 번도 검증된 적이 없다.**

이번 검증의 목적은 다음 한 문장으로 요약된다.

> **실제 데이터를 넣었을 때, 어디에서 무엇이 깨지는지를 데이터 투입 전에 정의하고,
> 투입 후 실제로 확인한다.**

세부 목적:

| # | 목적 |
|---|---|
| 1 | 구매데이터 → Dashboard 전 구간이 **실제 데이터로도** 이어지는지 확인 |
| 2 | 사업자등록번호 결합이 실제 데이터 형식에서 성립하는지 확인 (**매칭률 측정**) |
| 3 | 판정 기준일(지급일/계약일) 차이가 실제 데이터에서 결과 차이를 만드는지 확인 |
| 4 | 인증 유효기간 경계에서 포함·제외가 의도대로 동작하는지 확인 |
| 5 | API 응답과 내부 계산 결과가 **일치**하는지 확인 |
| 6 | 실제 데이터에서만 드러나는 **미확정 항목·Blocker** 를 식별 |

## 1.1 이번 검증이 목적하지 **않는** 것

- 정책 계산 규칙의 **정당성** 검증 (공식 근거 확인은 별도 트랙)
- 성능·부하 측정
- 실제 목표율 값의 확정

# 2. 현재 구현된 기능과 검증 대상 범위

## 2.1 검증 대상 전체 흐름

```text
구매데이터
  → Import (PurchaseImporter)
  → 사업자등록번호 정규화 (normalize_business_no)
  → Company 매칭 (CompanyMatcher)
  → Certification 연결 (company_id + policy_id + 유효기간)
  → 정책별 Rule 판정 (PaymentDateRule / ContractDateRule)
  → 구매금액 집계 (Calculator)
  → 목표율 적용 (Policy.target_rate)
  → 달성률 산출
  → Dashboard 요약 (DashboardDataService → DashboardApiService)
  → GET /dashboard/summary
```

## 2.2 구간별 구현 상태 (`main = 4aa6be9` 실측)

| # | 구간 | 구현 | 검증 대상 |
|---|---|---|---|
| 1 | 구매데이터 **파일 읽기** | ❌ **Parser 없음** | ⛔ 이번 범위 밖 — 데이터는 행(dict) 형태로 준비해 투입 |
| 2 | Import (행 단위) | ✅ `PurchaseImporter.import_rows()` | ✅ |
| 3 | 사업자번호 정규화 | ✅ `normalize_business_no()` | ✅ |
| 4 | Company 매칭 | ✅ `CompanyMatcher.match_all()` / `rematch()` | ✅ |
| 5 | Certification 연결 | ✅ `CertificationRepository` | ✅ |
| 6 | 정책 Rule 판정 | ✅ Rule Engine | ✅ |
| 7 | 금액 집계 | ✅ `Calculator` | ✅ |
| 8 | 목표율 적용 | ✅ `Policy.target_rate` | ✅ |
| 9 | **목표율 등록 수단** | ✅ `PUT /policies/{code}/target-rate` (PR #57) | ✅ |
| 10 | 달성률·상태 | ✅ `NORMAL` / `WARNING` / `SHORTAGE` / `TARGET_RATE_NOT_SET` | ✅ |
| 11 | Dashboard API | ✅ `GET /dashboard/summary` | ✅ |
| 12 | 인증 데이터 **수집** | ❌ **Collector 없음** | ⛔ 범위 밖 — 인증정보는 수동 투입 |

> **검증 대상은 2~11 구간이다.** 1·12(Parser·Collector)는 실제 파일·API 응답을 확인하기
> 전에는 만들지 않으므로, 이번 검증에서는 **데이터를 사람이 준비해 투입**한다.

# 3. 필요한 실제 데이터 목록

| # | 데이터 | 용도 | 최소 건수(권장) |
|---|---|---|---|
| 1 | **구매데이터** | Import → 매칭 → 집계의 입력 | 실제 1개 기관 1개 연도 전체 |
| 2 | **기업정보** | 사업자번호 ↔ 기업 결합 | 구매데이터에 등장하는 거래처 전체 |
| 3 | **인증정보** | 정책 대상 판정 | 정책별 인증 보유 기업 |
| 4 | **정책정보** | 정책 정의 | ✅ 이미 seed 됨(5종) |
| 5 | **목표율** | 달성률 계산 | PM 이 공식 근거 확인 후 입력 |

## 3.1 데이터 준비 형태

Parser 가 없으므로 구매데이터는 **행(row) 단위 매핑 리스트**로 준비한다.

```python
rows = [
    {"business_no": "...", "company_name": "...",
     "contract_date": "...", "payment_date": "...", "amount": "..."},
]
report = PurchaseImporter(purchase_repo, company_repo).import_rows(rows)
```

원본 파일 → 이 형태로의 변환은 **이번 검증에서 1회성 수동 작업**으로 처리한다.
반복 자동화(Parser)는 파일 구조가 확정된 뒤 별도 Issue 로 만든다.

# 5. 사업자등록번호 결합 규칙

`main` 구현 실측 기준이다. **검증 시 이 규칙대로 동작하는지 확인한다.**

| # | 입력 | 처리 | 결과 |
|---|---|---|---|
| 1 | `1234567890` | 그대로 | ✅ 정상 |
| 2 | `123-45-67890` | 구분자 제거 → `1234567890` | ✅ 정상 |
| 3 | 공백 포함 / 숫자형 | 정규화 | ✅ 정상 |
| 4 | **9자리** (`123456789`) | ⛔ **자동 0 보충하지 않음** | ❌ `INVALID_FORMAT` |
| 5 | 10자리 초과 | 거부 | ❌ `INVALID_FORMAT` |
| 6 | 특수문자·문자 포함 | 거부 | ❌ `INVALID_FORMAT` |
| 7 | `None` / 빈 문자열 | 거부 | ❌ `MISSING` |
| 8 | **체크섬 불일치** | **Warning**, 저장은 허용 | ⚠️ `WARNING` |
| 9 | 매칭 실패 | 저장하고 `company_id = NULL` | ⚠️ 나중에 `rematch()` 로 재매칭 |

## 5.1 검증 항목

| # | 확인 |
|---|---|
| B-1 | 실제 데이터의 사업자번호 표기 형식 분포(하이픈/공백/숫자형) |
| B-2 | **9자리 건수** — Excel 앞자리 0 손실 의심. 자동 보정하지 않으므로 별도 확보 필요 |
| B-3 | 체크섬 불일치 건수 및 그 건들의 매칭 성공 여부 |
| B-4 | **전체 매칭률** = 매칭 성공 건수 ÷ 전체 건수 |
| B-5 | 미매칭 건의 총 금액 — **분모에는 들어가고 분자에는 빠지므로 달성률을 낮춘다** |
| B-6 | 기업정보 나중 투입 후 `rematch()` 로 매칭률이 개선되는지 |

> ⚠️ **매칭률은 달성률과 함께 반드시 보고한다.** 매칭률이 낮으면 달성률은
> 실제보다 낮게 나오며, 이 사실을 모르면 잘못된 판단을 하게 된다.

# 7. 인증 유효기간 판정

판정 기준일이 `valid_from <= 기준일 <= valid_to` 범위 안이면 해당 정책 실적으로 인정한다.

| 상황 | 결과 |
|---|---|
| 기준일이 기간 내 | ✅ 인정 |
| 기준일이 `valid_from` 이전 | ❌ 제외 |
| 기준일이 `valid_to` 이후 | ❌ 제외 |
| 기준일 == `valid_from` | ✅ 인정 (경계 포함) |
| 기준일 == `valid_to` | ✅ 인정 (경계 포함) |
| 인증 없음 | ❌ 제외 (전체 구매액에는 포함) |
| `valid_from` / `valid_to` 결측 | ⛔ **저장 불가** — 현재 NOT NULL |

## 7.1 검증 항목

| # | 확인 |
|---|---|
| C-1 | 경계값 4종(`valid_from` 당일 / 하루 전 / `valid_to` 당일 / 하루 뒤) |
| C-2 | 한 기업이 **여러 정책 인증**을 동시에 보유할 때 각각 집계되는가 |
| C-3 | 한 기업의 같은 정책 인증이 **기간을 나눠 여러 건** 존재할 때 |
| C-4 | 실제 데이터에 **취소·정지 인증**이 있는가 → 있으면 🔴 **즉시 Blocker**(4.3) |

# 8. 정책별 테스트 시나리오

## 8.1 시나리오 목록

| ID | 정책 | 기준일 | 검증 초점 | 상태 |
|---|---|---|---|---|
| **S-A** | 중소기업 (`SMALL_BUSINESS`) | 지급일 | 기본 흐름 전 구간 | ✅ 검증 가능 |
| **S-B** | 장애인기업 (`DISABLED`) | 지급일 | 다른 정책과 동시 집계 | ✅ 검증 가능 |
| **S-C** | 창업기업 (`STARTUP`) | **계약일** | ⭐ **기준일 차이가 결과를 바꾸는가** | ✅ 검증 가능 |
| **S-D** | 여성기업 (`WOMAN`) | 지급일 | 단일 목표율 기준 집계만 | 🟡 **부분 검증** |
| **S-E** | 녹색제품 (`GREEN`) | — | — | ⛔ **검증 제외 (Blocker)** |

## 8.2 S-A 중소기업 — 기본 흐름

| 단계 | 확인 |
|---|---|
| 1 | 구매데이터 Import → `IMPORTED` / `WARNING` / `FAILED` 건수 |
| 2 | 사업자번호 정규화 후 Company 매칭 |
| 3 | 인증 기간 내 거래만 정책 실적으로 집계 |
| 4 | 목표율 등록 전 → `TARGET_RATE_NOT_SET` |
| 5 | 목표율 등록 후 → 달성률·상태 산출 |
| 6 | API 응답 = 내부 계산 결과 |

## 8.3 S-B 장애인기업 — 정책 간 독립성

| 확인 |
|---|
| 한 기업이 중소기업·장애인기업 인증을 모두 가질 때 **두 정책 모두에 집계**되는가 |
| 정책별 구매금액 합이 전체 구매액을 초과할 수 있다(중복 인정은 정상) |

## 8.4 S-C 창업기업 — ⭐ 기준일 차이

가장 중요한 시나리오다.

| 확인 |
|---|
| **계약일은 인증기간 내, 지급일은 인증기간 밖**인 거래가 실제 데이터에 있는가 |
| 그 거래가 창업기업에는 **인정**되고, 지급일 기준 정책에는 **제외**되는가 |
| 반대 케이스(계약일 밖 / 지급일 안)도 확인 |

이 시나리오가 통과해야 Rule Engine 이 실제로 정책별로 다르게 동작함이 증명된다.

## 8.5 S-D 여성기업 — 🟡 부분 검증만

**검증 가능한 것**

- 사업자번호 매칭 · 인증 연결 · 지급일 기준 집계 · Dashboard 표시

**검증할 수 없는 것 (Blocker)**

|---|---|

> 그 결과를 **여성기업 정책의 실제 달성률로 보고하지 않는다.**

# 12. API 응답과 내부 계산 결과 일치 여부

같은 DB 에 대해 **두 경로의 결과를 비교**한다.

```text
경로 1  Calculator 직접 호출 결과 (Decimal)
경로 2  GET /dashboard/summary 응답 (문자열)
```

| # | 확인 |
|---|---|
| W-1 | 정책별 `purchase_amount` 일치 |
| W-2 | `total_purchase_amount` 일치 |
| W-3 | `achievement_rate` · `shortage_rate` 일치 |
| W-4 | **문자열 → `Decimal` 재변환 시 정밀도 손실이 없는가** |
| W-5 | 금액이 지수 표기(`1E+7`)로 직렬화되지 않는가 |
| W-6 | 큰 금액(수백억 단위)에서 자릿수 손실이 없는가 |

> 비교는 문자열 그대로가 아니라 **`Decimal` 로 변환해 수행**한다.
> `"0"` 과 `"0.00"` 은 문자열로는 다르지만 값으로는 같다.

# 22. 실제 고객 데이터가 없을 경우 — 비식별화 / 최소 샘플 검증

실제 데이터 확보가 지연될 경우의 대안이다. **완전한 대체는 아니다.**

## 22.1 단계별 대안

| 단계 | 방법 | 검증 가능 범위 |
|---|---|---|
| **1단계** | 18장 최소 데이터셋 | 구조 연결·기준일 차이·경계값 |
| **2단계** | 실제 데이터 **비식별화** 샘플 | + 실제 형식 분포·데이터 품질 |
| **3단계** | 실제 데이터 전체 | 전부 |

## 22.2 비식별화 규칙 (2단계)

| 항목 | 처리 |
|---|---|
| 사업자등록번호 | ⚠️ **형식은 유지**하되 값을 치환. 하이픈·9자리·체크섬 오류 **패턴은 보존** |
| 기업명 | 익명 치환(`거래처001`) |
| 대표자명 | 익명 치환 또는 제거 |
| 금액 | ⚠️ **그대로 유지 권장** — 배율 변환 시 정밀도·자릿수 검증(W-5·W-6)이 무의미해진다 |
| 날짜 | ⚠️ **그대로 유지** — 이동하면 인증기간 판정 검증이 깨진다 |
| 계약번호·품목 | 제거 가능 |

> 🔒 비식별화 샘플이라도 **저장소에 커밋하지 않는다.** 로컬 또는 별도 보관 경로만 사용한다.

## 22.3 비식별 샘플로 검증할 수 없는 것

| 항목 | 사유 |
|---|---|
| 실제 매칭률 | 사업자번호를 치환하면 실제 기업정보와 결합되지 않는다 |
| 실제 달성률 | 위와 동일 |
| 인증 데이터 품질 | 인증정보 자체가 별도 확보 대상 |

> 따라서 **비식별 샘플 결과를 실제 달성률로 보고하지 않는다.**
> 검증 결과에는 사용한 데이터 단계(1/2/3)를 반드시 명시한다.

# 23. 데이터 공급 현황

| 데이터 | 현재 확보 여부 | 필요한 형태 | Blocker |
|---|---|---|---|
| **구매데이터** | ❓ **확인 필요** | 실제 또는 비식별 샘플 (행 단위 매핑) | 🔴 **여부 확인 필요 — 미확보 시 핵심 Blocker** |
| **기업정보** | ❓ **확인 필요** | 사업자번호 기준 (+ 기업명·대표자명) | 🔴 여부 확인 필요. `representative_name` 필수 제약 |
| **인증정보** | ❓ **확인 필요** | 사업자번호 + 인증기간(`valid_from`/`valid_to`) | 🔴 여부 확인 필요. **인증 API 키 미확보** |
| **정책정보** | ✅ **구현됨** | DB seed (5종) | 없음 |
| **목표율** | ✅ **기능 구현됨** (PR #57) | PM 입력 필요 | 🔴 **실제 값 미확정** |

## 23.1 핵심 Blocker (재확인)

> **실제 인증 API 키와 실제 고객 구매데이터가 현재 프로젝트의 핵심 Blocker다.**
>
> - 인증 API 키가 없으면 → 인증정보를 수집할 수 없고, 실제 응답 필드도 확인할 수 없다.
>   이 때문에 `Company.representative_name` nullable 전환과 Certification 상태 필드
>   확장도 착수할 수 없다.
> - 실제 구매데이터가 없으면 → 매칭률·달성률을 실제 값으로 산출할 수 없고,
>   여성기업 구매유형 존재 여부와 음수/0 금액 실태도 확인할 수 없다.
>
> 이 둘은 **코드로 해결할 수 없는 Blocker**이며, 데이터 확보가 다음 단계의 전제다.
