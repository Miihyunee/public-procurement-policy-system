# 2. 음수 금액의 업무적 의미 (분석)

> ⚠️ **아래는 일반적인 지출 데이터에서 관찰되는 유형에 대한 정리이며,
> 이 프로젝트의 고객 데이터에서 확인된 사실이 아니다.**
> 실제 어떤 유형이 존재하는지는 **샘플 확보 후 확인**해야 한다. (7장)

| 유형 | 설명 | 달성률 반영 관점 |
|---|---|---|
| **취소** | 계약·지출이 취소되어 원거래를 무효화 | 원거래와 상계해야 실적이 정확 |
| **반품** | 물품을 반환하고 대금을 돌려받음 | 상계 대상 |
| **환입** | 과오납·정산으로 금액 일부를 회수 | 부분 상계 |
| **조정** | 회계 정정(계정 대체 등) | 실적과 무관할 수 있음 |
| **선급 정산** | 선지급 후 정산 차액 | 원거래와 함께 봐야 의미가 있음 |

### 핵심 논점

음수 금액은 **단독으로 의미를 갖지 않고 원거래와 짝을 이룰 때 의미를 갖는다.**
그런데 현재 `Purchase` 모델에는 **원거래를 가리키는 필드가 없다.**

| 확인 필요 | 이유 |
|---|---|
| 음수 행이 원거래와 **같은 사업자번호·같은 기간**에 있는가 | 상계 가능 여부 판단 |
| 원거래 식별자(계약번호 등)가 제공되는가 | 정확한 상계에 필요 |
| 취소분이 **별도 플래그**로 표기되는가 | 음수 대신 상태값일 수 있음 |
| 고객이 이미 **상계된 금액**을 제공하는가 | 그렇다면 음수가 아예 없을 수 있음 |

# 3. 달성률 계산에 미치는 영향 (분석)

## 3.1 현재 계산 구조

```
전체 구매액   = 모든 Purchase.amount 합계
정책 구매액   = 인증 유효 구매의 amount 합계
정책 구매비율 = 정책 구매액 / 전체 구매액 × 100
달성률        = 정책 구매비율 / 목표율 × 100
```

- 합산은 단순 `+` 이므로 **음수가 들어오면 자동으로 상계된다.**
- 즉 계산기를 수정하지 않아도 음수는 "차감"으로 동작한다.

## 3.2 예상되는 문제

| # | 문제 | 설명 |
|---|---|---|
| 1 | **전체 구매액이 0 이 될 수 있음** | 계산기는 `total == 0` 이면 달성률 `0` 을 반환한다(0 나눗셈 회피). 데이터가 있는데 0 으로 표시될 수 있다 |
| 2 | **정책 구매액이 음수가 될 수 있음** | 취소분만 인증 기간에 포함되고 원거래는 벗어난 경우. 달성률이 **음수**가 된다 |
| 3 | **음수 달성률의 상태 판정** | 현재 `SHORTAGE`(< 80)로 분류된다. 의미상 맞는지 확인 필요 |
| 4 | **부족률 계산** | `max(0, 100 - 달성률)` 이므로 음수 달성률이면 부족률이 **100 초과** |
| 5 | **판정 기준일 불일치** | 원거래와 취소분의 지급일이 다르면 **서로 다른 기간**에 집계된다 |

> **5번이 가장 주의할 항목이다.** 원거래가 3월, 취소가 5월에 지급 처리되면
> 인증 유효기간에 따라 한쪽만 인정될 수 있어 상계가 성립하지 않는다.

# 4. 검증 규칙 설계 (제안)

**Import 단계와 Repository 단계의 역할을 분리한다.**

## 4.1 Repository 단계 (저장 계층)

| 규칙 | 현재 | 변경안 |
|---|---|---|
| `amount` NOT NULL | 유지 | 유지 |
| `amount` 숫자 변환 가능 | 유지 | 유지 |
| **`amount > 0`** | **거부** | **제거** — 음수·0 저장 허용 |

**근거**: Repository 는 **원천 데이터를 있는 그대로 보존**하는 계층이다.
업무 판단(취소를 어떻게 볼 것인가)은 저장 계층의 책임이 아니다.

## 4.2 Import 단계 (적재 계층)

| 금액 | 처리 | 상태 |
|---|---|---|
| 양수 | 정상 저장 | `IMPORTED` |
| **음수** | 저장 + 사유 기록 | **`WARNING`** |
| **0** | 저장 + 사유 기록 | **`WARNING`** |
| 숫자 변환 불가 | 저장 안 함 | `FAILED` |
| 비어 있음 | 저장 안 함 | `FAILED` |

**근거**: 음수·0 은 **오류가 아니라 확인이 필요한 값**이다.
Import 리포트에 건수와 합계를 남겨 담당자가 검수할 수 있게 한다.

## 4.3 리포트 추가 항목 (제안)

```
0 금액 건수    : ____
```

# 5. `amount = 0` 허용 여부 (결정 필요)

> 이 항목은 **음수와 별개**로 결정해야 한다.
> `amount > 0` 제약을 제거하면 **0 도 자동으로 허용**되기 때문이다.

| 방안 | 장점 | 단점 |
|---|---|---|
| **A. 0 허용 (경고)** | 원천 보존 원칙과 일관. 무상공급·정산 잔액 0 등을 표현 가능 | 의미 없는 행이 늘 수 있음 |
| B. 0 거부 | 무의미한 행 차단 | 원천 보존 원칙과 충돌. 0 이 유효한 사례를 잃음 |

**권장: A (허용 + 경고)** — 음수를 보존하기로 한 결정과 일관되며,
0 을 걸러야 한다면 **집계 단계**에서 판단하는 편이 되돌리기 쉽다.

# 6. 달성률 반영 규칙 (미결 — 샘플 분석 후 결정)

> PM 결정에 따라 **이번 단계에서 확정하지 않는다.** 선택지만 정리한다.

| 방안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **① 단순 합산(현행)** | 음수를 그대로 더해 상계 | 코드 변경 없음. 회계 관점에 부합 | 기간이 어긋나면 상계 실패. 음수 달성률 가능 |
| ② 음수 제외 | 집계에서 음수 행 제외 | 달성률이 음수가 되지 않음 | **실적이 과대 계상**됨(취소분 미반영) |
| ③ 원거래 상계 | 원거래를 찾아 짝지어 차감 | 가장 정확 | **원거래 식별자 필요**(현재 없음). 구현 복잡 |
| ④ 고객 상계본 요청 | 상계가 끝난 데이터를 받음 | 시스템 단순 | 고객 업무 부담. 검증 어려움 |

### 결정에 필요한 정보 (샘플에서 확인)

1. 음수 행이 **실제로 존재하는가**, 존재한다면 **비율은?**
2. 원거래를 식별할 수 있는 컬럼(계약번호 등)이 있는가
3. 음수와 원거래의 **지급일이 같은 기간**에 있는가
4. 고객이 기존에 산출한 달성률은 음수를 **어떻게 처리**했는가

> **4번이 가장 유용하다.** 고객의 기존 산출 방식과 맞춰야 수치 검증이 가능하다.

# 11. 요약

- D-003(음수 보존)과 현재 코드(`amount > 0` 거부)가 **충돌**한다.
- **Repository 는 원천 보존**, **Import 는 경고로 표시**하는 역할 분리를 제안한다.
- 음수는 **단독으로 의미가 없고 원거래와 짝을 이뤄야** 하는데, 현재 모델에는
  **원거래 식별자가 없다.**
- **달성률 반영 규칙은 확정하지 않는다** — 실제 샘플에서 음수의 존재·형태를 확인한 뒤
  결정한다. 특히 **고객의 기존 산출 방식**을 확인하는 것이 가장 유용하다.
