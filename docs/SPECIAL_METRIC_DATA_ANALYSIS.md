|---|---|
| 구매유형 직접 컬럼 | ❌ 없음 |

⚠️ 실제 파일이 없으므로 이는 **시스템이 읽도록 정의된 컬럼**이다. 원본 파일에
다른 컬럼이 더 있을 가능성은 이 조사로 배제하지 못한다 — 파일을 받으면
§3-1 을 다시 수행해야 한다.

### 1-2. 구매유형은 어디에 있는가 — A·B·C·D 구분

| 구분 | 내용 | 현황 |
|---|---|---|
| **A. 원본에서 자동으로 아는 값** | — | ❌ **없다** |
| **B. 담당자가 증빙을 보고 확정** | `purchase_review.final_purchase_type` | ✅ 구조 있음 |
| **C. 저장 가능한가** | 같은 컬럼. `CONSTRUCTION`/`SERVICE`/`GOODS`, `NULL`=판단 보류 | ✅ 저장됨 |
| **D. 계산기에 연결되어 있는가** | 계산 경로가 이 값을 읽지 않는다 | ❌ **미연결** |

확정 시점: 검토 화면에서 담당자가 확정할 때
(`review_status`: `PENDING` → `CONFIRMED`, 이력은 `purchase_review_history` 에
append-only 로 남는다). 미확정 건은 `final_purchase_type = NULL` 이며 이는
**"담당자가 아직 모른다"** 는 정상 상태다 — ⛔ 아무 값이나 채우지 않는다.

### 1-3. ⭐ 연결 통로는 이미 있다

`purchase_repository._performance_exclusion_conditions()` 는 계산 대상 조회에서
**이미 `purchase_review` 를 참조한다.**

```sql
NOT EXISTS (SELECT 1 FROM purchase_review r
            WHERE r.purchase_id = purchase.purchase_id
            AND r.performance_status = 'EXCLUDED')
```

즉 «담당자가 검토 화면에서 확정한 값을 계산이 읽는다» 는 **이미 동작하는 방식**
이다. `final_purchase_type` 도 같은 자리에서 같은 방식으로 읽을 수 있다.

또한 구 스키마 DB 를 위해 `_has_performance_status_column()` 으로 컬럼 존재를
먼저 확인하는 패턴이 있으므로, 확장 시 그 패턴을 그대로 따르면 된다.

### 1-4. 판정 — **B. 일부 계산 가능 (구조는 준비됨 / 데이터가 관건)**

* `final_purchase_type` 을 여성기업 특수지표의 **공식 입력값으로 쓸 수 있다.**
  담당자 확정값이며(고객이 정한 업무방식), 이력이 남고, 계산 경로가 이미
  같은 테이블을 읽는다.
* 부족한 것은 **시스템 구조가 아니라 확정된 데이터의 양**이다.
  구매유형이 확정되지 않은 거래는 공사 분모에도 용역·물품 분모에도 넣을 수 없다.

따라서 계산 가능 여부는 **실제 확정 비율에 달려 있고, 실제 파일이 없어 그 비율을
측정하지 못했다.** 세 가지가 함께 필요하다.

1. 여성기업 실적(공사) / 전체 공사 구매금액
2. 여성기업 실적(용역·물품) / 전체 용역·물품 구매금액
3. 미확정 건을 어떻게 볼 것인가 — **고객 확인 필요**(분모에서 빼는가,
   분모에는 넣고 분자에서만 빼는가). ⛔ 임의로 정하지 않았다.

⛔ 적요 키워드 분류·BM25/RAG/FUSE·임계값을 만들지 않았다.

## 2. 국가유공자 자활용사촌

### 2-1. 시스템 전체에 품목 식별자가 있는가

10개 테이블 전 컬럼을 조사했다.

**어느 테이블에도 물품목록번호·물품분류번호·세부품명·품목코드가 없다.**

기업정보 표준 양식에도 없다 — 사업자등록번호 · 기업명 · 대표자명 · 인증종류 ·
유효시작일 · 유효종료일 6개뿐이다.

### 2-2. 유일한 품목 필드 — 저장되지 않는다

`collectors/models.py` 에 `product_item_no`(세부품명번호 `detailPrdnmNo`,
조달청 물품목록번호 10자리)가 있다. 그러나

* SMPP **직접생산확인** API 응답의 메모리 DTO 일 뿐 **저장 경로가 없다**
  (어느 테이블에도 컬럼이 없다)
* 그 API 키는 🔴 **미발급**이다
* 직접생산확인은 ⛔ **실적 집계에 쓰지 않기로 확정**되어 있다(§0.12.6)

### 2-3. ⭐ 결정적 구분 — 업체와 거래는 다르다

목표의 분모는 **「자활용사촌 생산가능품목 총 구매액」** 이다.

> 업체가 생산가능품목을 **보유**한다는 사실과,
> 특정 지출건이 **그 품목을 산 것**이라는 사실은 별개다.

가령 자활용사촌 업체에서 사무용품과 청소용역을 함께 샀다면, 둘 중 어느 것이
생산가능품목인지 알아야 분모가 나온다. 그 정보는 **거래 쪽에 있어야 하는데
지출 원본에 품목이 없다.**

`26년 자활용사촌.xlsx` 의 생산품목 시트가 채워 주는 것은 **업체 쪽 목록**이다.
업체 쪽 목록만으로는 분모를 만들 수 없다.

⛔ 사업자등록번호가 같다는 이유로 그 업체의 **모든** 구매액을 생산가능품목
구매액으로 보지 않는다 — 그렇게 하면 분모가 부풀고 달성률이 실제보다 낮아진다.

### 2-4. 판정 — **LEVEL 3 (현재 데이터로 7% 계산 불가)**

거래 쪽 품목 식별정보가 **원본에도, 시스템 10개 테이블 어디에도 없다.**

부족한 것은 두 가지이며 성격이 다르다.

| 부족한 것 | 성격 | 확보 경로 |
|---|---|---|
| 업체별 생산가능품목 목록 | **데이터 부족** | 자활용사촌 파일에 있을 수 있음(파일 부재로 미확인) |
| **거래별 품목** | **데이터 + 구조 부족** | 원본에 없음. 저장할 컬럼도 없음 |

⛔ 새 품목 자동분류 기능을 만들지 않았다. 적요·거래처명으로 품목을 추정하지
않았다.

## 4. 고객·PM 에게 물어야 할 것

이 조사로 새로 드러난 질문은 두 개다.

**(가) 여성기업 — 구매유형 미확정 건을 어떻게 볼 것인가**
담당자가 아직 유형을 정하지 않은 거래는 공사 분모에도 용역·물품 분모에도
넣을 수 없다. 분모에서 빼는가, 아니면 분모에는 넣고 분자에서만 빼는가.
⛔ 달성률 숫자를 바꾸는 문제라 임의로 정하지 않았다.

**(나) 자활용사촌 — 거래별 품목을 어디서 얻는가**
업체 목록이 아니라 **거래 쪽** 품목이 필요하다. 지출결의서나 계약 자료에
품목이 적혀 있어 담당자가 확인할 수 있는지, 아니면 별도 자료가 있는지.

기존 확인 요청서 ⑤ ⑥ 과 이어지는 질문이며, 답을 받기 전까지 두 정책은
«계산 보류» 로 둔다.
