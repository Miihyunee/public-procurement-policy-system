## C-1. 필수 컬럼에 **계약일**이 포함되어 있다

| 항목 | 내용 |
|---|---|
| 기존 기준 | §2.2 — 필수 컬럼 5개에 **계약일** 포함. §4 — "필수 컬럼 없으면 **전체 거부**" |

## C-2. 금액 규칙 — "0보다 커야 함"

| 항목 | 내용 |
|---|---|
| 기존 기준 | §3.3 — "**0보다 커야 함** (0 이하는 오류 처리)". §4 — "금액 > 0, 오류 행 보고" |
| 샘플 관찰 | 매입행 중 **음수 거래가 관찰됨** (0원은 0건) |
| 현재 코드 | `PurchaseRepository._validate()` 가 `amount <= 0` 을 거부 |
| 충돌 내용 | 기존 규칙대로면 **음수 행이 전부 오류 처리**된다 |
| 관련 | **Issue #49 보류 중** — 이미 인지된 문제 |

> ⚠️ 다만 `PURCHASE_DATA_SPEC.md` §3.3 은 "확인 필요" 항목으로
> **"취소·반품 건의 음수 표기 여부"** 를 이미 적어 두었다. 즉 **문서가 이 가능성을
> 예견하고 있었고, 샘플이 그것을 확인해 준 것**이다.
>
> **해소는 W-4 확정 후 Issue #49 에서 처리한다.** 지금 규칙을 바꾸지 않는다.

## C-3. 파일 규격 — `.xlsx` 우선 vs 샘플 `.xls`

| 항목 | 내용 |
|---|---|
| 기존 기준 | §5 — "Excel(**`.xlsx`**) 우선, CSV 병행" |
| 샘플 관찰 | 정본 후보가 **`.xls` (BIFF)** — `.xlsx` 아님 |
| 충돌 내용 | 지원 형식 목록에 `.xls` 가 없다 |
| 영향 | 🟡 기술적으로 해소 가능(라이브러리 차이). 다만 **지원 형식을 명시해야 한다** |

**추가 관찰**: 기존 문서는 CSV 인코딩으로 "UTF-8 권장, CP949 흔함"을 적었으나,
샘플의 `.txt` 는 **UTF-16LE** 였다. **인코딩 후보에 UTF-16 계열도 포함**되어야 한다.

> **[운영-확인필요] W-9** — 실제 운영데이터가 어떤 형식으로 오는지 확인 후 확정.

# 3. 🟡 보완 필요 (충돌 아님)

## S-1. `PURCHASE_IMPORT_DESIGN.md` — 매출/매입 구분 단계가 없다

| 항목 | 내용 |
|---|---|
| 기존 흐름 | `원본 행 → 컬럼 매핑 → 값 정규화 → Validation → Company 연결 → Purchase 저장` |
| 누락 | **집계행 식별**, **매출/매입 구분** 단계가 없다 |
| 사유 | 이 문서 작성 시점에는 실제 파일 형식을 몰랐다 (행 단위 입력 전제) |
| 판정 | **충돌이 아니라 확장 필요.** 기존 흐름은 그대로 유효하고, **앞단에 전처리가 추가**되는 구조 |

Parser Spec 과의 관계:

```text
[Parser Spec 범위]                          [기존 Import Design 범위]
파일 → 행 유형 판별 → 집계행 → 거래 구분  →  정규화 → Validation → 매칭 → 저장
```

> 기존 문서를 수정하지 않았다. **전처리 단계 추가는 D-20 결정 후**.

## S-2. `PURCHASE_IMPORT_DESIGN.md` — 컬럼 매핑이 "호출자 수행"

| 항목 | 내용 |
|---|---|
| 기존 | `[1] 컬럼 매핑 (호출자가 수행 — 매핑 템플릿 사용)` |
| Parser Spec | Parser 가 **원본 컬럼명 그대로 파싱**하고, 업무 매핑은 별도 단계 |
| 판정 | ✅ **일치한다.** 두 문서 모두 "파싱과 매핑을 분리"한다는 같은 방향 |

## S-3. `DATA_DICTIONARY.md` — Purchase 항목에 신규 컬럼 없음

| 항목 | 내용 |
|---|---|
| 현재 | `business_no` · `company_name` · `contract_date` · `payment_date` · `amount` · `company_id` |
| 샘플에 있으나 사전에 없는 것 | `세무구분`(거래 구분) · `적요` · `예산과목` |
| 판정 | **충돌 아님.** 저장 필드가 확정되면 그때 사전에 등재 |

> 지금 등재하면 **저장하지도 않는 필드가 사전에 생긴다.** D-19 결정 후 반영한다.

## S-4. `DATA_MAPPING.md` — 표준 컬럼 목록이 인증 데이터 중심

| 항목 | 내용 |
|---|---|
| 현재 표준 키 | `business_no` · `company_name` · `representative_name` · `valid_from` · `valid_to` |
| 관찰 | **구매데이터 표준 키가 정의되어 있지 않다** |
| 판정 | **충돌 아님 — 범위 밖.** 구매데이터 매핑 규칙 추가가 필요하나, **업무 매핑 확정 후** |

원칙("사업자등록번호를 모든 데이터 연결의 기준 키로 사용")은 Parser Spec 과 **완전히 일치**한다.
