# STEP A — 원본 파일 확인

업로드 **전에** 원본 파일 자체를 확인한다.

```
□ 파일명이 확인되는가
□ 대상 연도가 확인되는가
□ 대상 기간이 확인되는가
□ 원본 행 수를 기록했는가
```

표준 양식의 컬럼이 있는지 확인한다(`uploads/format.py` 기준 · 9개).

```
□ 결의일자          (필수)
□ 계약일자          (필수)
□ 지급일            (필수)
□ 기업명            (필수)
□ 사업자등록번호     (필수)
□ 계                (필수 · 부가세 포함 총액)
□ 신고기준일         (필수)
□ 적요              (선택 · 공란 허용)
□ 예산과목          (선택 · 공란 허용)
```

⛔ **새 필수 컬럼을 임의로 추가하지 않는다.** 원본에 `공급가액` · `세액` ·
`결의번호` · `원본 행 번호` 가 있어도 시스템은 그 값을 저장하지 않는다.

⚠️ `계` 는 **부가세 포함 총액**이다. 공급가액을 넣으면 분모가 달라진다.

# STEP C — 원본 / 적재 / 미적재 정합성

`GET /imports/trace` 로 확인한다.

```
원본 행 수 = 적재 행 수 + 미적재 행 수
```

```
□ source_rows = stored + rejected 인가
□ unexplained = 0 인가              (업로드 응답의 unexplained_rows)
```

미적재 행이 있으면 각 행마다 확인한다.

```
□ 원본 행 번호가 존재하는가      (row_number)
□ 미적재 사유가 존재하는가        (reason)
□ 미적재 사유 설명이 존재하는가   (reason_label · message)
□ CSV 에서 동일한 행을 확인할 수 있는가  (/imports/trace.csv)
□ 원본 파일의 해당 행과 실제로 일치하는가
```

## C.1 ⛔ 미적재 행을 부르는 말

Q5-8 이 아직 확정되지 않았으므로 미적재 행에는 **현재 시스템의 표현만** 쓴다.

| 쓴다 | 쓰지 않는다 |
|---|---|
| 미적재 | 무효 데이터 |
| 원본에는 있으나 현재 검토 대상에 포함되지 않은 행 | 삭제된 데이터 |
| 처리 방식 확인이 필요함 | 부적합 · 오류 데이터 · 검토 불필요 |

⚠️ 금액이 0 이하인 행이 미적재로 나오는 것은 **현재 시스템의 동작**이며,
업무상 어떻게 처리할지는 **Q5-8 미확정**이다. 검수자가 정하지 않는다.

# STEP D — ACTIVE 배치 확인

동일 기간의 과거 업로드가 있으면 `GET /imports/batches` 로 확인한다.

```
□ 현재 업로드 배치가 ACTIVE 인가            (status · is_current)
□ 이전 동일 기간 배치가 SUPERSEDED 되었는가  (superseded_by)
□ 이전 purchase 행 자체가 삭제되지 않았는가
□ 계산에는 현재 ACTIVE 배치만 사용되는가
□ 이전 배치 + 현재 배치가 중복 합산되지 않는가   ← 가장 중요
```

## D.1 두 숫자를 맞대어 본다

```
현재 ACTIVE 배치 합계
      vs
Dashboard 계산 대상 금액(정책 카드의 "계산 대상 전체 구매액")
```

두 값이 **다를 수 있는 정당한 이유는 셋뿐**이다. 그 외의 차이는 결함이다.

| 차이의 이유 | 확인 방법 |
|---|---|
| 기간 조건 — 조회 연도 밖의 행 | STEP E |

| 결의일자 미기재 — 연도를 나눌 수 없는 행 | `GET /dashboard/missing-resolution-date` |

```
□ 차이가 있다면 위 셋 중 어느 것인지 기록했는가
□ 셋 중 어느 것으로도 설명되지 않는 차이가 있는가  → 결함으로 보고
```

(`DECISIONS.md` §0.11).

⛔ 정리하면 같은 번호가 되는 기업이 있으면 **자동으로 합치지 않는다.** 어느

**기업명이 달라도 사업자등록번호가 같으면 같은 기업**이다 — 현재 기준을

```

전체라 **대체된 배치의 행도 포함**한다(응답의 `includes_superseded` ·

# STEP G — 구매유형 검수

구매유형은 **자동 확정하지 않는다.** 담당자 검토 영역이다.

```
□ 구매유형 PENDING 건수를 확인          (/reviews/progress)
□ 담당자가 확인해야 할 건을 확인
□ 필요한 경우 지출결의서 확인
□ 필요한 경우 세금계산서 확인
□ 구매유형을 담당자가 확정
```

고객 확정에 따라 다음을 유지한다(Q5-3).

```
결의번호 없음
자동 그룹핑 없음
```

⛔ 시스템에서 **지출결의서 단위로 임의 묶음을 만들지 않는다.** 같은 문구가
서로 다른 결의서에 쓰일 수 있어, 묶으면 담당자가 잘못된 단위로 판단한다.

건을 찾을 때는 고객이 말한 대조 수단을 그대로 쓴다.

```
□ 적요로 검색                (/reviews?page=1&search=…)
□ 거래처명으로 검색           (같은 검색 칸)
□ 사업자등록번호로 검색        (같은 검색 칸)
□ 금액을 목록에서 눈으로 대조   (금액순 정렬 가능)
□ 결의일자 오름·내림차순 정렬로 지출 순서 확인
```

□ 적요 내용과 관계없이 제외 대상인지 확인
□ 실제 계산 대상에서 빠졌는지 확인
```

⛔ **부분 문자열이 아니라 정확히 같은 값**만 본다(앞뒤 공백만 제거).
`교육훈련비지원` · `특별교육훈련비` 는 빠지지 않는다.
⛔ 여기에 다른 과목을 임의로 더하지 않는다.

## H.2 교육비 / 강사료 (담당자 확정)

```
□ 의심 거래 확인
□ 지출결의서 확인
□ 세금계산서 내역 확인
□ 실제 교육비/강사료인지 담당자 판단
□ 담당자 확정 후 실적 제외
```

⛔ 다음 낱말이 있다는 이유만으로 자동으로 빼지 않는다.

```
교육
교육비
강사
강사료
교육훈련
```

고객이 **지출결의서와 세금계산서 내역을 직접 확인**한다고 답했고, 그 자료는
시스템에 없다.

## H.3 단기 차량 임차 (고객 확정)

```
출장지에서 단발성 출장 목적으로 임차한 차량
→ 기간과 관계없이 단기 차량 임차
→ 실적 제외
```

```
□ 사업부서 품의서 확인
□ 단발성 출장 목적인지 확인
□ 담당자 확정 후 실적 제외
```

⛔ 기간 임계값을 쓰지 않는다.

```
1일   2일   3일   7일   30일
```

고객이 *"하루 · 1박2일 · 2박3일 등 기간과 상관없이"* 라고 명시했다.

⛔ 적요 낱말만으로 자동 제외하지 않는다.

```
렌트   렌터카   쏘카   임차
```

⚠️ 화면의 *"단기 차량 임차 여부는 사업부서 품의서를 확인하여 판단합니다"* 는
**사람에게 보여 주는 안내**이며 자동 판정 기준이 아니다.

## H.4 고객이 지목한 2건

```
민원 담당자 교육
민원 담당자 교육 2차
```

```
□ 동일 거래인지 확인
□ 업체 확인
□ 사업자등록번호 확인
□ 금액 확인
□ 지출결의서 확인
□ 세금계산서 내역 확인
□ 담당자 확정
□ 실적 제외 상태 확인      (/reviews/{id} 의 performance 블록)
```

⛔ **같은 적요라는 이유만으로 다른 거래까지 일괄 제외하지 않는다.**

# STEP H.5 — 실적 제외 후 분모 / 분자 검수

실적 제외에서 **가장 중요한 확인**이다.

```
제외 전
  분모 = 계산 대상 전체 구매액
  분자 = 정책 대상 구매액

제외 후
  분모 = 제외 금액만큼 감소
  분자 = 그 거래가 정책 구매에 들어 있었다면 함께 감소
```

⛔ **분모에서만 빼는 방식이 되어서는 안 된다.** 분모만 줄면 달성률이 실제보다
높아진다.

검수 시 다음을 기록한다.

```
제외 전 분모:
제외 전 분자:
제외 금액:
제외 후 분모:
제외 후 분자:
제외 후 구매비율:
제외 후 달성률:
```

```
□ 제외한 거래가 정책 인증기업 거래였는가
□ 그렇다면 분자도 함께 줄었는가
□ 그렇지 않다면 분모만 줄고 분자는 그대로인가
```

# STEP I — 정책별 달성률 검수

`GET /dashboard/summary?year=` 로 정책마다 확인한다.

```
□ 목표 구매비율            (target_rate)
□ 정책 구매액              (purchase_amount · 분자)
□ 계산 대상 전체 구매액     (total_purchase_amount · 분모)
□ 구매비율                 (아래 ⚠️ 참고)
□ 달성률                   (achievement_rate)
□ 부족률                   (shortage_rate)
```

두 관계를 손으로 맞대어 본다.

```
구매비율 = 정책 구매액 ÷ 계산 대상 전체 구매액 × 100
달성률   = 구매비율 ÷ 목표 구매비율 × 100
```

⚠️ **구매비율은 API 와 화면에 별도 값으로 없다.** 계산 안에서만 쓰이고
`achievement_rate` 로 합쳐져 나온다. 검수자가 분자 ÷ 분모로 직접 구해
달성률과 앞뒤가 맞는지 본다.

```
□ 목표율이 설정되지 않은 정책은 달성률이 "미설정" 으로 나오는가 (0% 가 아님)
□ 분모가 0 이면 달성률이 0 으로 나오는가
```

# STEP J — 대시보드 화면 검수

## J.1 KPI

```
□ 적재된 구매금액 합계
□ 구매 건수
□ 기업 매칭률
□ 목표율 설정 정책
```

⚠️ **`적재된 구매금액 합계` 를 계산 분모와 같은 숫자로 보지 않는다.** 이 타일은
적재된 **전부**라 대체된 배치와 다른 해까지 들어 있다. 분모는 정책 카드의
`계산 대상 전체 구매액` 이다.

## J.2 정책 카드

```
□ 목표 구매비율
□ 정책 구매액              (분자)
□ 계산 대상 전체 구매액     (분모)
□ 달성률
□ 부족률
□ 분자와 분모가 모두 화면에 보이는가
```

## J.3 기간 안내

```
□ 조회 연도가 화면에 보이는가
□ 결의일자 기준으로 연도를 나눈다는 안내가 있는가
□ 인증 유효기간 판정 기준과 혼동시키는 문구가 없는가
```

⛔ **연도 귀속 기준일(결의일자)과 인증 유효기간 판정 기준일은 다른 것이다.**
후자는 **W-1-2 미확정**이며, 일반 정책 3종은 현재 지급일을 쓴다. 화면 문구가
둘을 하나처럼 읽히게 하면 결함이다.

```
□ resolution_date 같은 내부 컬럼명이 사용자 화면에 노출되지 않는가
```

## J.4 결의일자 미기재 안내

```
□ 결의일자가 입력되지 않은 건수·금액이 안내되는가
□ 그 건수·금액이 달성률에 반영되어 있지 않다는 설명이 있는가
□ 목록·CSV 로 어떤 행인지 확인할 수 있는가
```

⛔ 이 행들을 "오류" · "무효" · "실적 불인정" 으로 부르지 않는다. 처리 방식은
아직 정해지지 않았다.

`GET /reviews/{purchase_id}` 의 `performance` 블록으로 확인한다.

```
□ 실적 포함 건수
□ 실적 제외 건수
□ 제외 사유            (reason_label)

```

⚠️ 현재 대시보드에는 실적 제외 현황 KPI 가 **없다.** 이번 검수에서는 확인
항목으로만 두고, 실제로 한 번 돌려 본 뒤 화면에 무엇을 추가할지 판단한다.

# STEP L — 재업로드 검수

같은 기간 데이터를 다시 올리는 경우.

```
□ 기존 배치 SUPERSEDED
□ 새 배치 ACTIVE
□ 기존 purchase 행 보존
□ 계산에는 새 ACTIVE 배치만 사용
□ 이전 배치와 새 배치가 중복 합산되지 않음
```

```
적재된 구매금액 합계        (KPI · 적재된 전부)
      ≠ 일 수 있다
계산 대상 전체 구매액        (분모 · ACTIVE + 기간 + 실적 제외)
```

두 값이 다른 것은 **정상**이며, 다른 이유는 배치 상태 · 기간 · 실적 제외
셋이다(STEP D.1).
