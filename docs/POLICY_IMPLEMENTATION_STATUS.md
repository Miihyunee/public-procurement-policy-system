# 8. 목표율 등록 수단 — 검토 및 제안 (지시서 11장)

> **제안 단계다. 이 장의 어떤 것도 구현하지 않았다.** PM 승인 후 별도 Spec PR →
> 구현 PR 순서로 진행한다(지시서 19장 임의 구현 금지 원칙).

## 8.1 현재 확인된 사실 (코드 실측)

| 확인 항목 | 현재 상태 |
|---|---|
| 목표율 저장 위치 | `policies.target_rate` (nullable, `TEXT` 로 저장 후 `Decimal` 복원) |
| 목표율 **조회** 수단 | `PolicyRepository.find_active()` / `find_active_with_target_rate()` / `find_by_policy_code()` ✅ |
| 목표율 **변경** 수단 | ❌ **`PolicyRepository` 에 `update` 계열 메서드가 없다** |
| 등록 경로 | `bootstrap.seed_policies()` 의 최초 seed(전부 `target_rate=None`)뿐 |
| 변경 이력 | ❌ 이력 테이블 없음. `policies.updated_at` 컬럼만 존재 |
| 쓰기 API | ❌ 없음. `app.py` 에는 `GET /dashboard/summary` 하나뿐 |

> 즉 운영자가 목표율을 넣으려면 **SQLite 에 직접 `UPDATE` 를 실행하는 방법밖에 없다.**

## 8.2 최소 요구사항 대조 (지시서 11장)

| 최소 요구사항 | 현재 | 필요한 것 |
|---|---|---|
| 정책 코드 선택 | ✅ `policy_code` 로 조회 가능 | 목록 조회 엔드포인트 |
| 목표율 입력 | ❌ | 쓰기 경로 |
| 저장 | ❌ | `PolicyRepository.update_target_rate()` |
| 기존 목표율 조회 | ✅ 내부적으로 가능 | 외부 노출 엔드포인트 |
| 잘못된 값 검증 | 🟡 부분 — `insert` 경로에만 `target_rate > 0` 검증 존재 | 갱신 경로에도 동일 규칙 적용 |
| 변경 이력 확인 가능성 | ❌ | 이력 테이블(선택) |

## 8.3 제안 구조 — 기존 계층을 깨지 않는 형태

현재 읽기 경로는 다음 계층을 따른다.

    FastAPI → DashboardApiService → DashboardDataService → Calculator → Repository

목표율 등록은 **계산 경로가 아니라 관리(설정) 경로**이므로, Calculator 를 지나지 않는
별도 서비스로 분리하는 것이 기존 계층을 가장 적게 건드린다.

    FastAPI → PolicyAdminService → PolicyRepository → SQLite

| 원칙 | 준수 방법 |
|---|---|
| HTTP 계층은 Repository 에 직접 접근하지 않는다 | 엔드포인트는 `PolicyAdminService` 만 호출 |
| 조립은 composition root 한 곳에서만 | `app.py` 에 `build_policy_admin()` 추가 |
| 기존 Dashboard 경로 무변경 | `DashboardApiService`·`DashboardDataService`·Calculator 수정 없음 |
| 계산 로직 중복 금지 | Admin 서비스는 **저장만** 담당, 달성률 계산 안 함 |

## 8.4 제안 엔드포인트 (최소)

| Method | Path | 용도 |
|---|---|---|
| `GET` | `/policies` | 정책 목록 + 현재 목표율 조회(미설정은 `null`) |
| `PUT` | `/policies/{policy_code}/target-rate` | 목표율 설정·변경 |

- 요청/응답 금액·비율은 기존 규약대로 **문자열 직렬화**(`Decimal` 정밀도 보존).
- 미설정 해제(다시 `null` 로) 허용 여부는 **PM 결정 필요**(8.6 D-11).

## 8.5 검증 규칙 (제안 — 확정 아님)

| 규칙 | 근거 |
|---|---|
| `target_rate > 0` | **기존 `insert` 경로에 이미 있는 규칙**(`_validate_required`). 갱신 경로에도 같은 규칙을 적용해 경로 간 불일치를 막는다 |
| 상한(예: `<= 100`) | ⚠️ **현재 코드에 상한 규칙이 없다.** 도입 여부는 D-13 |
| 소수 둘째 자리까지 허용 | 기존 `Decimal` 저장 형식과 일치 |
| 존재하지 않는 `policy_code` → 404 | — |
| 검증 실패 → 422 | 기존 `CalculatorValidationError → 422` 규약과 일치 |

> ⚠️ **상한 100 이 정책적으로 옳은지는 정부 파일에서 확인되지 않았다(미확인).**
> Group C(온누리상품권 등)처럼 분모가 다른 정책에서 100 초과 목표율이 필요한지
> 확인되기 전까지는 상한값을 확정하지 않는다.
