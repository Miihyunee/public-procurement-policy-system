# 7. 작업 원칙 — 왜 이렇게 하고 있는가

이전 PM 이 반복해서 지시한 원칙입니다. **이유가 있어 만들어진 것**이므로 배경을
함께 적어 둡니다. 바꾸실 수 있지만, 바꾼다는 사실을 알고 바꾸시는 편이 좋습니다.

| 원칙 | 배경 |
|---|---|
| **확정되지 않은 업무규칙을 추정해 구현하지 않는다** | 이 시스템은 **법정 실적 수치**를 산출합니다. 틀린 숫자가 나오면 기관이 잘못 보고하게 됩니다 |
| **업무 로직을 JavaScript 로 재작성하지 않는다** | 계산이 두 곳에 생기면 반드시 어긋납니다. Electron 은 UI·생명주기만 담당 |
| **기존 Importer / BatchImportService 를 재사용한다** | 적재 로직이 둘이 되면 데이터가 갈라집니다 |
| **테스트 기대값을 통과시키려고 바꾸지 않는다** | 업무규칙이 실제로 바뀐 경우에만 바꾸고, **사유를 docstring 에 남깁니다** |
| **`DECISIONS.md` 가 결정의 단일 출처** | 결정이 여러 문서에 흩어지면 어느 것이 최신인지 알 수 없게 됩니다 |
| **새 문서를 만들기 전에 기존 문서를 갱신할 수 있는지 본다** | 한때 문서가 39개까지 늘어 서로 모순됐고, 18개를 삭제해 정리한 이력이 있습니다 |
| **원격 push 는 승인 후** | 이전 PM 지시. 새 PM 이 해제하실 수 있습니다 |

| 기표번호·결의번호·`LN_SQ`·`GRP_NB` 를 음수 판별키로 사용 | 샘플 음수 125건에서 **전부 비어 있음**이 실측됨 |

# 8. 실행 방법

```bash
# 최초 1회
python -m venv .venv && .venv/bin/pip install -e ".[dev]"

# DB 초기화 (멱등 — 기존 데이터를 지우지 않음)
.venv/bin/python -m procurement init

# 서버 실행 → http://127.0.0.1:8000/
.venv/bin/python -m procurement run

# 상태 점검
.venv/bin/python -m procurement health

# Electron (Electron 바이너리 필요)
npm install && npm start

# Electron 없이 백엔드 생명주기만 검증
node scripts/verify-backend.js
```

**대시보드에 숫자가 안 나올 때**는 대부분 두 가지입니다.

1. 정책 `target_rate` 가 `NULL` (의도된 기본값 — D-004). 목표율을 등록하면 계산됩니다
2. `PURCHASE_PERIOD_DATE_FIELD` 미설정 → 연도 조회가 503. 어느 날짜로 연도를
   나눌지 확정 전이라 **일부러** 기본값을 두지 않았습니다
