# 1. 목적

> **실제 운영데이터를 받았을 때 Import 하기 전에, 파일 구조와 데이터 품질을
> 자동으로 검사해 보고서 형태로 제공한다.**

## 1.1 이 도구가 답하는 질문

| 질문 | 답할 수 있는가 |
|---|---|
| 이 파일을 읽을 수 있는가 | ✅ |
| 샘플과 컬럼 구조가 같은가 | ✅ |
| 사업자번호·날짜·금액이 **형식상** 정상인가 | ✅ |
| 집계행·매출행이 얼마나 섞여 있는가 | ✅ |
| 어느 날짜가 **지급일**인가 | ❌ **업무 규칙 필요 (W-1)** |
| 어느 금액이 **정책 실적금액**인가 | ❌ **업무 규칙 필요 (W-3)** |
| 음수 거래를 어떻게 **처리**할 것인가 | ❌ **업무 규칙 필요 (W-4)** |

## 1.2 위치

```text
운영데이터 수신
    ↓
【구조 검증】  ← 이 도구
    ↓
검증 결과 확인
    ↓
업무 규칙 / 매핑 확인
    ↓
Parser
    ↓
Import
```

> ⛔ **운영데이터를 받았다고 바로 Import 하지 않는다.**

# 2. 핵심 원칙

## 원칙 1 — 구조 검증과 업무 의미 판정을 분리한다

| 구조 검증 (이 도구) | 업무 규칙 (별도) |
|---|---|
| `"2026/08/10"` 이 날짜 형식인가 | 이 날짜가 **지급일**인가 |
| `"1,000,000"` 을 숫자로 읽을 수 있는가 | `공급가액`·`계` 중 무엇이 **실적금액**인가 |
| 음수 값이 몇 건인가 | 음수를 **어떻게 처리**할 것인가 |
| `세무구분` 값 분포가 어떤가 | 매입이 **우선구매 실적**인가 |
| 사업자번호가 10자리인가 | — |

## 원칙 2 — 읽기 전용

| 항목 | 방침 |
|---|---|
| 원본 파일 | **수정하지 않는다** |
| DB | **쓰지 않는다** — 저장·Import 하지 않는다 |
| 값 보정 | **하지 않는다** — 정규화는 판정용 사본에만 |

> 이 도구는 **진단만 한다.** 그래서 업무 규칙이 확정되기 전에도 안전하게 만들 수 있다.

## 원칙 3 — 기준값을 하드코딩하지 않는다

⛔ 샘플에서 관찰된 숫자(2,903행 · 매출 79.4% · 음수 5.70% 등)를
**기대값·임계값으로 코드에 넣지 않는다.**

| 허용 | 금지 |
|---|---|
| 샘플의 **컬럼명 목록**을 비교 기준으로 사용 | 샘플의 **행 수·금액·비율**을 기준값으로 사용 |
| 알려진 집계행 **표기 목록** 사용 | "매출이 79% 이상이어야 정상" 같은 판정 |

> 비교 기준(컬럼명·집계행 표기)은 **외부에서 주입 가능**해야 한다. 기관마다 다를 수 있다.

## 원칙 4 — 기존 규칙을 재사용한다

| 항목 | 재사용 대상 |
|---|---|
| 사업자번호 정규화 | `procurement.matchers.business_no.normalize_business_no()` |
| 체크섬 | 기존 정책 — **Warning, 저장 차단 없음** |
| 날짜 형식 | 기존 `_parse_date` 와 동일 형식 지원 |
| 금액 파싱 | 기존 `_parse_amount` 와 동일 (쉼표·통화기호 제거, `Decimal`) |

> **새 규칙을 만들지 않는다.**

# 4. PASS / WARNING / ERROR 기준

## 4.1 3단계 정의 (`PURCHASE_PARSER_SPEC.md` 11장 기반)

| 수준 | 의미 | 이후 행동 |
|---|---|---|
| **ERROR** | 이 파일로는 **진행할 수 없다** | 검증 중단. 파일 재요청 또는 원인 해소 |
| **WARNING** | 진행할 수 있으나 **사람이 확인해야 한다** | 내용 확인 후 판단 |
| **PASS** | 구조상 문제 없음 | 다음 단계 진행 |

> ⚠️ **PASS 는 "이 데이터로 계산해도 된다"는 뜻이 아니다.**
> **"구조적으로 읽을 수 있다"**는 뜻일 뿐이며, 업무 규칙 확인은 별개다.

## 4.2 ERROR 인 항목과 근거

| 항목 | ERROR 인 이유 |
|---|---|
| **필수 컬럼 누락 (A-9)** | 모든 행이 **동일하게 실패**한다. 행마다 실패를 반복 보고하는 것은 의미가 없고, 부분 처리는 더 위험하다 |
| **합계 정합성 실패 (B-9·B-10)** | 행이 **조용히 사라졌다**는 뜻이다. 이 상태의 통계는 신뢰할 수 없다 |
| **파일 형식 미지원 / 읽기 불가 (A-1·A-2)** | 이후 모든 검증이 불가능하다 |
| **헤더 없음 (A-6)** | 컬럼명 기반 접근이 성립하지 않는다 |

## 4.3 WARNING 인 항목과 근거

| 항목 | WARNING 인 이유 |
|---|---|
| **체크섬 오류 (C-9)** | **기존 확정 정책**이 Warning 이다. 실제로 유효한 번호가 체크섬을 어기는 경우가 있어 차단하지 않는다 |
| **미지 집계행 (F-2)** | 자동 제외하면 **거래행을 잃을 수 있다**. 유지하고 사람이 판단한다 |
| **미분류 거래 (G-4·G-5)** | 임의 분류는 **분모·분자를 조용히 왜곡**한다 |
| 9자리 사업자번호 (C-5) | 자동 보정 금지 정책. 원본 재확보가 필요하나 검증 자체는 계속 가능 |
| 음수 금액 (E-5) | 의미가 미확정(W-4). 처리하지 않고 보고만 한다 |
| 금액 정합성 불일치 (E-8) | 컬럼 구성에 따라 다를 수 있어 단정할 수 없다 |
| 컬럼 구조 변화 (A-10~A-12) | 정상적인 확장일 수 있다 |
| 날짜·금액 파싱 실패 (D-3·E-2) | 일부 행 문제이며 전체를 막지 않는다 |

## 4.4 최종 판정 규칙

```text
ERROR 가 1건이라도 있으면        → ERROR
ERROR 없고 WARNING 이 1건 이상   → WARNING
둘 다 없으면                     → PASS
```

## 4.5 기존 문서와의 충돌 여부

| 확인 | 결과 |
|---|---|
| 체크섬 Warning | ✅ `PURCHASE_IMPORT_DESIGN` · `PURCHASE_PARSER_SPEC` 와 일치 |
| 필수 컬럼 누락 = 파일 단위 | ✅ `PURCHASE_PARSER_SPEC` 3.3 과 일치 |
| 합계 정합성 = ERROR | ✅ `PURCHASE_PARSER_SPEC` V-11 과 일치 |
| 음수 = Warning(보고만) | ⚠️ **`PURCHASE_DATA_SPEC` §4 는 "금액 > 0, 오류 행 보고"** — **C-2 충돌(기존 보고)** |

> **C-2 는 이번에도 해소하지 않았다.** 다만 이 도구는 **Import 하지 않으므로**
> 저장 검증과 무관하며, "오류 행 보고"가 아니라 **"관찰 보고"** 로 동작한다.
> 저장 시 규칙은 **W-4 확정 후 Issue #49 에서 결정**한다. → **PM 확인 요청**

# 5. 리포트 출력

## 5.1 출력 형태 — 기존 프로젝트 구조에 맞춘 제안

프로젝트에는 이미 두 가지 리포트 선례가 있다.

| 선례 | 형태 |
|---|---|
| `ImportReport.format_report()` | 결과 객체 + **텍스트 요약 메서드** |
| `HealthReport.format_report()` | 〃 (`[OK ]` / `[FAIL]` 마커 + `결과: 정상`) |

> **동일 패턴을 따르는 것을 제안한다.**
>
> - **결과 객체**(구조화된 데이터) + **`format_report()`**(콘솔용 텍스트)
> - CLI 는 기존 `python -m procurement <subcommand>` 구조에 맞춰 **서브커맨드 1개 추가**
> - **JSON 출력은 선택 옵션**으로 두되, 필요성이 확인되기 전에는 만들지 않는다
>
> ⛔ **임의로 정하지 않는다.** 출력 형식·CLI 이름은 **구현 Spec 승인 시 확정**한다.

## 5.2 리포트 구성 (초안)

# 6. 기존 코드와의 관계

## 6.1 변경하지 않는 것

| 대상 | 이유 |
|---|---|
| `Calculator` · Rule Engine | 이 도구는 **계산하지 않는다** |
| `DashboardDataService` · `DashboardApiService` | 표시 계층과 무관 |
| `PurchaseRepository` · `Purchase` 모델 | 이 도구는 **DB 에 쓰지 않는다** |
| `PolicyRepository` · Bootstrap | 무관 |
| `PurchaseImporter` | 이 도구는 **Import 하지 않는다** |
| `business_no` matcher | **재사용만** 한다 |

> 기존 계층 원칙은 그대로 유지된다.
> `FastAPI → DashboardApiService → DashboardDataService → Calculator → Repository`

## 6.2 신규로 필요한 것 (제안 — 미구현)

| 항목 | 성격 |
|---|---|
| 구조 검증 모듈 (신규 패키지) | 읽기 전용, 독립 |
| 결과 객체 + `format_report()` | 기존 패턴 재사용 |
| CLI 서브커맨드 1개 | `__main__` 은 얇게 유지 |

> **DB 스키마 변경 없음. 기존 모듈 수정 없음.**

## 6.3 외부 의존성 확인 필요

`.xls`(BIFF) 를 읽으려면 표준 라이브러리로는 부족하다.

| 항목 | 상태 |
|---|---|
| `.xls` 읽기 라이브러리 추가 | ⚠️ **의존성 추가 필요 — 구현 Spec 승인 시 확정** |
| `.xlsx` 읽기 | 별도 라이브러리 필요 |

> 현재 프로젝트는 **표준 라이브러리 + FastAPI/Pydantic 중심**이다.
> 의존성 추가는 **PM 승인 사항**으로 분리한다.
