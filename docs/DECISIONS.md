### 0.5.2 정책 중복 인정 — 상호 배타 분류 금지

```text
사업자 A ─┬─ 여성기업 인증
          └─ 창업기업 인증
     ↓
A 와의 구매거래는 여성기업 실적 ✅ 창업기업 실적 ✅ 둘 다 인정
```

| 규칙 | 내용 |
|---|---|
| **분자** | 각 정책을 **독립적으로 판정**한다. 동일 거래가 여러 정책의 분자에 각각 포함될 수 있다 |
| **분모** | 전체 구매금액은 **실제 구매금액 기준으로 1회만** 계산한다. 중복 가산하지 않는다 |
| ⛔ **금지** | `IF 여성기업 … ELSE IF 창업기업 …` 같은 **우선순위 기반 배타 분류** |

검증 예 (실측):

```text
전체 구매 100만 · 사업자 A 20만(여성+창업)
→ 여성기업 분자 20만 · 창업기업 분자 20만 · 분모 100만  (120만이 아님)
```

### 0.5.3.1 🔴 고객 발언 간 충돌 — 임의 해석하지 않는다

전달받은 고객 발언:

> "일단 창업기업을 제외하고는 **계약일자 컬럼으로 실적을 확인**하면 돼"

이 문장은 앞서 확정된 **"구매실적 기준일 = 결의일자"**(§0.1 ①) 및
**"창업기업은 계약일자도 고려"**(§0.1 ④)와 **정반대**로 읽힙니다.

| 해석 | 일반 정책 | 창업기업 |
|---|---|---|
| 앞선 확정(§0.1) | 결의일자 | 결의일자 + 계약일자 |
| 위 발언 그대로 | **계약일자** | 계약일자 아님(?) |

> ✅ **2026-08-14 (3차) 회신으로 해소되었다.** → §0.6.2
>
> 일반 정책은 결의일자 기준이 맞고, **창업기업만** 결의일자·계약일자를 **OR** 로
> 판정한다. "창업기업을 제외하고는 계약일자" 라는 문장은 일반 정책의 기준을
> 바꾸라는 뜻이 아니었다.

### 0.5.5 🔴 "11개 − 3개 = 8개" 가 현재 문서와 맞지 않는다

`POLICY_GAP_ANALYSIS_2026.md` §1 기준으로 **정부권장정책 구매 부문은 11개**이고,
**녹색제품은 그 11개에 포함되어 있지 않다**(파일에서 확인되지 않은 MVP 전용 정책).

```text
구매 11개 − 기술개발생산품 − 중증장애인생산품 = 9개
(녹색제품은 애초에 11개 밖 → 빼도 11개는 줄지 않음)
```

| 후보 | 정책 | 현재 구현 |
|---|---|---|
| 1 | 중소기업 | ✅ `SMALL_BUSINESS` |
| 2 | 창업기업 | ✅ `STARTUP` |
| 3 | 여성기업 | ✅ `WOMAN` |
| 4 | 장애인기업 | ✅ `DISABLED` |
| 5 | 사회적기업 | ❌ 미구현 |
| 6 | 사회적협동조합 | ❌ 미구현 |
| 7 | 온누리상품권 구매 | ❌ 미구현 (분모가 **기관 경상경비**로 다름) |
| 8 | 장애인표준사업장 | ❌ 미구현 |
| 9 | 국가유공자자활용사촌 | ❌ 미구현 (분모가 **생산가능품목 총 구매액**으로 다름) |

> **9개 중 어느 1개가 더 빠져 8개가 되는지 확정되지 않았다.** 임의로 정하지 않고
> PM 확인 대기한다.

**불일치의 원인 후보** — 어느 쪽인지 확인이 필요하다.

| # | 가능성 |
|---|---|

| 3 | 위 9개 중 1개가 이미 다른 경로로 제외되었는데 **기록되지 않았다** |

## 0.6 🟢 2026-08-14 (3차) 고객 회신 — 미확정 4건 해소

> **§0.5.3.1 의 진술 충돌이 해소되었다.** 창업기업만 다르게 처리하는 것이지,
> 일반 정책의 기준일이 계약일자로 바뀐 것이 아니었다.

### 0.6.1 확정 ① — 일반 정책 기준일 = 결의일자 (유지)

연도별 구매실적 귀속 기준일은 **결의일자**다. §0.1 ① 을 그대로 유지한다.

> ✅ **2026-08-15 해소** — 결의일자는 **`Purchase.resolution_date` 라는 별도 필드**다.
> `payment_date` · `contract_date` 어느 쪽에도 매핑하지 않는다. → §0.7 (W-1-1 종결)

### 0.6.2 확정 ② — 창업기업은 **두 날짜 OR** 로 판정 · ✅ 구현 완료

> 창업기업은 결의일자와 계약일자가 기업 인증 유효기간에 해당할 경우
> **모두** 실적으로 인정한다.

| `resolution_date` | `contract_date` | 판정 |
|---|---|---|
| 유효기간 안 | 유효기간 안 | ✅ 인정 |
| 유효기간 안 | 유효기간 밖 | ✅ 인정 |
| 유효기간 밖 | 유효기간 안 | ✅ 인정 |
| 유효기간 밖 | 유효기간 밖 | ❌ 불인정 |

⛔ **`STARTUP = CONTRACT_DATE` 단독으로 구현하면 안 된다.** 계약일이 기간 밖이고
다른 날짜만 안에 있는 구매를 놓친다.

**구현**

| 항목 | 내용 |
|---|---|
| 규칙 | `calculators.rules.ResolutionOrContractDateRule` |
| 기준값 | `evaluation_basis = "RESOLUTION_OR_CONTRACT_DATE"` |
| seed | `STARTUP` → 새 기준값 |
| 기존 DB | `migrate_policy_evaluation_basis()` 가 `CONTRACT_DATE` · `PAYMENT_OR_CONTRACT_DATE` 인 STARTUP 행만 갱신 (멱등 · 구매/인증 데이터 무변경) |

> **2026-08-15 변경.** 결의일자가 `resolution_date` 로 확정되기 전에는 어느 컬럼이
> 결의일자인지 몰라 `payment_date` 와 `contract_date` 를 함께 보았고, 기준값 이름도
> `PAYMENT_OR_CONTRACT_DATE` 였다. 지금은 **`resolution_date` 와 `contract_date`** 를
> 본다. **업무규칙(결의일자 OR 계약일자)은 그대로이고, 물리 필드만 확정된 것이다.**
>
> ⚠️ `resolution_date` 가 비어 있는 **기존 행은 계약일자만으로** 판정한다. 없는 값을
> `payment_date` 로 대체하지 않는다(§0.7 금지 사항).

### 0.6.3.2 🟢 2026-08-20 (2차) 고객 회신 — 다건 매칭 기준 확보

| 2 | 동일 사업자등록번호 |

**동일 조건의 거래가 여러 건인 경우 — 담당자의 실제 처리**

| # | 확인 |

⛔ **적요는 절대적 필수 조건이 아니다.** 고객 답변상 약 99.5% 동일하지만 100%
동일하지는 않다(담당자별 작성 방식 차이). **적요 완전일치를 필수로 걸면 안 된다.**

⚠️ **"이전" 이 아니라 "가장 가까운" 이다.** 선후 방향은 보지 않고 **발행일자 차이의

```text

```

**실측 검증** (2026년 매입 2,292행 · 음수 129건 · 양수 2,161건 · 0원 2건 제외).
발행일자는 원본 `신고기준일` 컬럼으로 보았다(결측 0건).

| 항목 | 결과 |
|---|---|
| 상계 쌍 | **126쌍** (담당자 표시 126쌍과 동수) |
| **상계된 음수** | **126 / 126 담당자 표시와 완전 일치** ✅ |
| 짝 없는 음수 | 3건 (사업비 잔액 반환금 등) |

| 🔴 **최근접 동률(거리 최소가 2건 이상)** | **54건** (대부분 거리 0일 = 같은 날 발행) |
| 발행일자 거리 분포 | 0일 111 · 1~7일 6 · 8~30일 9 · 31일+ 0 (최대 27일) |

> ✅ **"어떤 음수가 상계되는가" 는 이 규칙으로 완전히 결정된다.**
> 🔴 **"그 음수와 어떤 양수를 짝짓는가" 는 아직 결정되지 않는다** — 동률 54건.

**적요를 하드 조건으로 쓸 수 없음(실측 확인)**

| 규칙 | 상계 쌍 | 담당자 표시행 중 놓침 |
|---|---|---|
| 3조건 + 최근접 | 126쌍 | 0건(음수 기준) |
| 3조건 + **적요 완전일치 필수** + 최근접 | 115쌍 | **22행** |

1:1 로 자명한 그룹에서도 적요가 다른 쌍이 **7 / 101** 있었다. 고객 진술("99.5%
동일하지만 100%는 아니다")과 일치한다. → **적요는 후보를 좁히는 참고 정보**로만 쓴다.

**예산과목 공란은 판별력이 없음(실측 확인)**

| 음수 | 128 / 129 |
| 양수 | 130 / 2,161 |

음수는 거의 전부 공란이라 **음수 쪽을 가려내지 못하고**, 양수 쪽에도 130건이 있어
후보를 좁히지도 못한다. 고객 확인대로 **"공란 = 상계" 규칙은 만들지 않는다.**

```text
상계 72쌍 · 남은 거래 2,148건 · 짝 없는 음수 3건 · 담당자 확인 54건 · 발행일자 없음 0건

음수 129건 = 자동 상계 72 + 담당자 확인 54 + 짝 없음 3
담당자 표시 음수 126건 → 자동 72 + 확인 54 = 126 / 126  전건 포착 ✅
```

🔴 **자동 상계 72쌍 중 5쌍은 담당자와 다른 양수를 골랐다.** 다섯 건 모두 **더
가까운 날짜의 다른 적요** 후보를 골랐고, 담당자는 **날짜가 먼 대신 적요가 같은**
후보를 골랐다. 5건 중 4건은 담당자가 고른 후보의 적요가 음수와 **완전히 동일**
했고, 규칙이 고른 후보의 적요가 음수와 같은 경우는 **0건**이었다.

```text
− 2026-04-16  이오엘소사이어티(주)  −360,000  "에스프레소 원두(디카페인)"
    규칙 선택  행1653  2026-04-16 (0일)  "[소모성물품구입비] 카페테리아 4월분 원두(디카페인)"
    담당자 선택 행2056  2026-05-06 (20일) "에스프레소 원두(디카페인) -4월 분"   ★
```

> ⛔ **적요를 발행일자보다 앞세우는 규칙을 만들지 않았다.** 5건은 PM 에 보고했고,
> 그 결과 **발행일자 최근접 자동 선택 자체가 폐기**되었다 → §0.6.3.5

### 0.6.3.4 🟢 2026-08-20 (3차) 고객 회신 — ⚠️ 일부 §0.6.3.5 로 개정됨

> ⚠️ **이 절의 ⑦(발행일자 최근접 자동 매칭)은 2026-08-20 4차 회신으로 폐기되었다.**
> 최종 절차는 **§0.6.3.5** 를 보라. 이 절의 나머지 내용(적요·예산과목·발행 순서에
> 관한 확인 사항, 실측 수치)은 그대로 유효하다.

**절차 (⑦ 폐기 전 판)**

```text
① 동일 기업 + ② 동일 사업자등록번호 + ③ 동일 금액(절대값)  →  후보 확인
      ↓  후보가 여러 건이면
④ 적요 확인  ⑤ 예산과목 공란 여부 확인  ⑥ 세금계산서 발행일자 확인
      ↓
⑦ 발행일자가 가장 가까운 (+)/(−) 를 1:1 매칭
      ↓  발행일자 차이가 동률이면
⑧ 담당자가 G20 에서 지출결의서 조회 가능 여부를 확인
   → 지출결의서 확인 탭으로 넘어가지 않는 건(= 실제 지출 미완료)을 상계 처리
```

| 원칙 | 내용 |
|---|---|
| 적요 | **필수 조건이 아니다.** 적요가 다르다는 이유만으로 상계를 제외하지 않는다 |
| 예산과목 공란 | **자동 삭제 조건이 아니다.** 판단 시 **참고하는 정보**일 뿐이다 |
| 발행일자 | `신고기준일`. 선후 방향이 아니라 **차이의 절대값이 최소**인 건을 고른다 |

**⑧ 동률 — 업무규칙은 확정, 시스템 자동화는 범위 밖**

> 고객: "지금까지 이런 경우는 없었던 것 같은데, 그럴 경우에 지출결의서가 조회가 되는지
> 확인해서 상계처리할 거야. 실제로 지출이 완료되지 않은 건은 G20에서 지출결의서
> 확인하는 탭으로 넘어가지지 않아."

| 항목 | 판정 |
|---|---|
| 업무규칙 | ✅ **확정** — 담당자가 G20 지출결의서 조회 가능 여부로 판단 |
| 시스템 자동 판정 | ⛔ **불가 · 범위 밖.** G20 은 계정이 필요한 외부 프로그램이며 우리 시스템은 로그인·조회·자동화를 하지 않는다 |
| 따라서 코드는 | 🟡 **동률 건을 임의로 고르지 않고 "담당자 확인 대상" 으로 남긴다** |

⛔ **G20 조회 가능 여부를 시스템이 판정할 수 있는 것으로 가정하지 않는다.** 예산과목
공란 등을 "지출결의서가 조회되지 않는다" 의 대체 신호로 쓰는 것도 **추측이므로 금지**다.

📌 **고객 의견 기록**: 동률 상황은 **지금까지 실제로 겪은 적이 없다**고 답변했다.
저희 실측에서는 2026년 데이터에 **54건** 존재한다(발행일자 완전 동일 50 · 같은 방향
동일거리 4 · 이전/이후 대칭 0). 담당자가 인지하지 못한 이유는, 동률이어도 **어느 쪽을
고르든 상계 건수와 금액이 같아** 수작업에서는 문제로 드러나지 않기 때문으로 보인다.

**세금계산서 발행 순서 — 업무 흐름 기록 (⛔ 코드 조건 아님)**

> 고객: "(−) 세금계산서는 (+) 세금계산서보다 발행일자가 먼저 올 수 없어. (+) 를 잘못
> 발행했거나 그런 사유로 (−) 를 발행한 거일 테니까."

일반적인 흐름은 **(+) 발행 → (−) 발행** 이다. 다만 이것을 **`양수 발행일 < 음수 발행일`
이라는 필터 조건으로 코드에 넣지 않는다.** 실측 반례가 있기 때문이다.

| 담당자가 상계 표시한 126쌍 (신고기준일 기준) | 건수 |
|---|---|
| (+) 가 먼저 | 17 |
| **같은 날** | **107** |
| 🔴 **(+) 가 나중** | **2** |

(+) 가 나중인 2건은 **후보가 하나뿐인 1:1 그룹**이라 짝짓기 선택의 문제가 아니다.

```text
+ 2026-01-26  (주)포커스디앤에스        242,000  "토너"
− 2026-01-22  (주)포커스디앤에스       −242,000  "토너"

+ 2026-05-06  이오엘소사이어티(주)      360,000  "에스프레소 원두(디카페인) -4월 분"
− 2026-04-16  이오엘소사이어티(주)     −360,000  "에스프레소 원두(디카페인)"
```

> 전체 후보쌍 324개 중 **98개**가 (+) 가 (−) 보다 나중 발행이다. 이를 필터로 넣으면
> 위 2쌍을 포함해 담당자가 실제로 상계한 건을 놓친다. → **업무 흐름으로만 기록하고,
> 판정 조건으로는 쓰지 않는다.** (2026-08-19 에 제거한 "양수가 이전" 조건을 되살리는
> 것이 아니다.)

> 🔴 **계산에 연결하지 않았다.** `PurchaseRepository._validate()` 가 `amount <= 0`
> 저장을 거부하므로 **음수 거래가 DB 에 존재할 수 없다**(D-003 · C-2 · Issue #49).
> 저장 제약 해제는 PM 결정 사항이며, 그전에는 연결해도 대상 데이터가 없다.

⛔ `기표번호` · `결의번호` · `LN_SQ` · `GRP_NB` 를 식별자로 쓰지 않는다.

### 0.6.3.5 🟢 2026-08-20 (4차) 고객 회신 — **최종 확정 업무규칙**

> 고객: "그럴 경우 **C의 방식으로 지출결의서 내 내용(세금계산서, 비고란 작성 내용)
> 등을 확인하여 진행**해야 해."

즉 고객은 적요·발행일자 중 무엇을 우선하라고 답한 것이 **아니다.** 후보가 여러
건이고 데이터만으로 판단하기 어려우면 **G20 지출결의서를 직접 확인**한다는 뜻이다.

**최종 절차**

```text
① 동일 기업 + ② 동일 사업자등록번호 + ③ 동일 금액(절대값)
          ↓  후보 검색
┌──────────────────┐
│ 후보 0건          │ → 짝 없음 (상계하지 않고 보고)
├──────────────────┤
│ 후보 1건 (1:1)    │ → ✅ 자동 상계
├──────────────────┤
│ 후보 2건 이상      │ → 🟡 담당자 확인 대상
└──────────────────┘
```

후보가 여러 건이면 담당자가 **적요 · 예산과목 · 세금계산서 발행일자 · G20
지출결의서의 세금계산서 내용 · 비고란**을 종합해 판단한다.

**🔴 폐기된 로직 — 발행일자 최근접 자동 선택**

| 폐기 근거 | 내용 |
|---|---|
| 고객 답변과 불일치 | "발행일자가 가까우니 그 거래다" 라고 자동 결정하지 않는다 |
| 실측 오류 | 자동 상계 72쌍 중 **5쌍(6.9%)** 이 담당자 처리와 달랐다 (§0.6.3.4) |
| 경계 취약 | 그중 한 건은 **4일 대 5일** — 하루 차이로 결과가 뒤집혔다 |

⛔ **어떤 자동 우선순위도 만들지 않는다** — 발행일자 근접 · 적요 동일 · 적요
유사도 · 예산과목 공란 · 파일 행 순서 · 최근 거래 · 최초 거래. 세 값(발행일자 ·
적요 · 예산과목)은 **담당자에게 보여줄 참고정보**일 뿐이다.

**구현**

| 항목 | 내용 |
|---|---|
| 자동 상계 조건 | 같은 판별 키에 **양수 1건 · 음수 1건** 뿐일 때만 |
| 담당자 확인 | `NeedsManualReviewGroup` — 판별 키 · 음수 · **모든 후보** · 사유 · 같은 키의 다른 음수 |
| 사유 | `MULTIPLE_CANDIDATES`(양수 2건 이상) · `CONTESTED_CANDIDATE`(음수가 여러 건이라 1:1 불성립) |
| 후보 표시 | `candidate_lines()` — 발행일자 · 적요 · 예산과목을 나란히 (⛔ 우선순위 아님) |
| `OffsetPair` | `distance_days` **제거** (선택 근거로 오해될 수 있음) |
| 발행일자 결측 | 🟡 **내부 판단(미확정 예외)** — 아래 별도 표기 |

**실데이터 회귀 (2026년 매입 2,292행 · 음수 129건)**

```text
자동 상계 42쌍 · 남은 거래 2,208건 · 짝 없는 음수 3건 · 담당자 확인 84건

음수 129건 = 자동 42 + 담당자 확인 84 + 짝 없음 3
담당자 표시 음수 126건 포착 = 42 + 84 = 126 / 126  ✅
자동 상계 42쌍의 84행 → 담당자 표시와 84 / 84 일치 (**불일치 0**)
```

> ✅ **자동 상계에서 선택 오류가 구조적으로 사라졌다.** 후보가 하나뿐인 경우만
> 자동 처리하므로 "잘못 골랐다" 가 성립할 수 없다. 이전 판의 5건은 모두 후보가
> 2건 이상이므로 자동으로 담당자 확인 대상이 되었다.

담당자 확인 84건의 후보 수 분포: 2건 55 · 3건 9 · 4건 2 · 5건 5 · 6건 3 · 8건 7 ·
12건 2 · 14건 1.

### 0.7.4 ✅ STEP 59 — 결의일자 공란 건을 **화면에 알린다**(표시 전용)

§0.7.2 대로 "없으면 없는 대로" 두기 때문에, 결의일자가 비어 있는 행은
결의일자 기준 집계에 **들어가지 못한다**. 지금까지 그 사실이 화면 어디에도
나타나지 않아, 총액이 왜 작은지 사용자가 알 수 없었다.

STEP 59 는 그 사실만 알린다.

| 항목 | 내용 |
|---|---|
| 무엇을 센다 | `purchase.resolution_date IS NULL` 인 행의 **건수 · 금액 합계** |

| 화면 | 「정책별 달성률」 카드 하단 안내 문구. **0 건이면 표시하지 않는다** |
| 계산 영향 | **없다.** 분모·분자·달성률은 이전과 완전히 동일 |

⛔ **판정하지 않는다.** "제외"·"무효"·"오류 데이터"·"실적 불인정" 으로 부르지
않으며, 다른 날짜로 대체하지도 않는다. 이 건들을 어떻게 할지는 여전히
**미확정**이며, 사람이 정한다.

#### 기간 조건을 적용하지 않는 이유

집계에 **기간 범위를 걸지 않는다.** 결의일자가 비어 있는 행에 결의일자
범위 조건을 걸면 정의상 항상 0 건이 되어 알림 자체가 성립하지 않기
때문이다. 대신 계산 경로(`find_for_calculation`)와 **같은 배치 조건**
(ACTIVE 배치 또는 배치 없음)만 적용한다.

⛔ 기간의 의미가 애매하다고 해서 **다른 날짜 기준으로 바꾸지 않았다.**
조회 기준일이 결의일자가 **아닌** 경우(지급일·계약일 기준)에는 결의일자
공란이 누락 사유가 아니므로 `applies=false` 로 내려보내고 화면에 아무것도
표시하지 않는다.

### 0.7.7 🔴 STEP 62 — 결의일자 미기재 건 사전 점검 (조사 전용 · **확정 없음**)

처리 규칙을 정하기 전에, **현재 코드가 이미 무엇을 정해 놓았는지**를 먼저
읽었다. 코드는 한 줄도 바꾸지 않았다.

#### 확인 ① — 결의일자 공란은 **표준 업로드로는 들어올 수 없다**

`결의일자` 는 표준 업로드 양식의 **필수 컬럼**(`uploads/format.py`,
`required=True`)이다. 공란이면 `uploads/validation.py` 가 severity `error`
인 문제를 만들고, `UploadService` 는 "전부 검증 → 전부 저장" 원칙에 따라
`storable=False` 로 **파일 전체를 저장하지 않는다**(적재 계층을 호출조차
하지 않는다).

즉 `purchase.resolution_date IS NULL` 인 행이 생기는 경로는 다음뿐이다.

| 경로 | 설명 |
|---|---|
| **이 필드 도입 이전 적재** | §0.7 에서 컬럼을 신설하며 기존 행은 `NULL` 로 남겼다 |
| `PurchaseImporter` 직접 호출 | 적재 계층은 결의일자를 **선택 항목**으로 받는다(하위호환) |

표준 업로드 경로는 `to_import_row` 가 검증을 통과한 값만 넘기므로, **배치에
속한 행**(`batch_id` 가 있는 행)에는 결의일자 공란이 생길 수 없다.

⚠️ **따라서 이것은 "앞으로 들어올 데이터를 어떻게 볼 것인가" 가 아니라
"이미 들어와 있는 옛 데이터를 어떻게 할 것인가" 의 문제다.** 질문의 성격이
다르므로 고객께도 그렇게 여쭙는다.

#### 확인 ② — 자동 분류에 쓸 수 있는 정보가 **없다**

`purchase` 에 있는 값 중 "이 행의 결의일자가 왜 비어 있는가" 를 말해 주는
것은 없다. 사유 컬럼·출처 컬럼·상태 컬럼이 모두 없으며, 만들지 않았다.

| 후보 | 왜 쓸 수 없는가 |
|---|---|
| `batch_id IS NULL` | "배치 도입 이전" 만 뜻한다. 결의일자 공란의 **사유**가 아니다 |
| `created_at` | 적재 시각일 뿐, 원본이 비어 있었는지 알려 주지 않는다 |
| `description` · `budget_account` | ⛔ 구매유형 자동분류 금지와 같은 이유로 판정 근거로 쓰지 않는다 |

⛔ **자동 분류하지 않는다.** 근거가 없는 분류는 추측이며, 추측한 분류는
나중에 실적 숫자로 굳는다.

#### 확인 ③ — 다른 날짜로 대체할 **근거가 문서에 없다**

오히려 **금지가 세 곳에 기록되어 있다.**

| 위치 | 내용 |
|---|---|
| §0.7.2 | "값이 없는 결의일자를 다른 날짜로 대체" — PM 이 명시적으로 금지 |
| `models/purchase.py` | `issue_date` 가 없어도 "⛔ 값이 없다고 해서 `resolution_date` 등 다른 날짜로 대체하지 않습니다" |
| `calculators/rules/date_rules.py` | 결의일자가 없는 행을 `payment_date` 로 대체하면 PM 이 금지한 "`payment_date` 를 결의일자로 재정의" 가 된다 |

⚠️ `CUSTOMER_DATA_QUESTIONS.md` Q1 의 *"`결의일자` − `신고기준일` 평균
0.84일(84%가 같은 날)"* 은 **대체 근거가 아니다.** ① 결의일자가 **있는**
행에서 관찰한 상관일 뿐이고, ② 16%는 날짜가 다르며, ③ 고객 원본
매입매출장에 대한 관찰이지 업무규칙이 아니다.

#### 확인 ④ — 같은 공란이 두 곳에서 **다르게** 동작한다

| 상황 | 결의일자 공란 행의 취급 |
|---|---|
| 연도 귀속(결의일자 기준 기간 조회) | **빠진다** — 어느 해인지 알 수 없으므로 |
| 창업기업 인증 유효기간 판정 | **계약일자만으로 판정된다**(§0.6.2 OR 규칙) |

두 번째는 이미 확정된 규칙이므로 바꾸지 않는다. 다만 **같은 행이 한쪽에서는
빠지고 한쪽에서는 판정된다**는 사실을 고객께 알린 뒤 처리 규칙을 받아야
한다. (결의일자 기준 기간 조회에서는 앞단에서 이미 빠지므로 두 동작이 한
화면에서 동시에 보이지는 않는다.)

| 연도 귀속 | `resolution_date` 선택 가능 (운영자 지정) |
| 인증 유효기간 판정 | 일반 정책 4종 = `payment_date` (**변경하지 않음**) |

포함한다면 일반 정책 4종의 판정 기준일이 바뀌고 **달성률 숫자가 달라진다.**
→ **고객 확인 사항 W-1-2 로 남긴다.**

#### W-1-2 선택지 (2026-08-28 정리 · **미회신**)

| | 중소기업 | 여성기업 | 장애인기업 | 창업기업 |
|---|---|---|---|---|
| **① 현행 유지** | 대금 지급일 | 대금 지급일 | 대금 지급일 | 결의일자 **또는** 계약일자 |
| **② 결의일자 기준** | 결의일자 | 결의일자 | 결의일자 | 〃 (변경 없음) |

⛔ **고객의 명시적 답변 전까지 어느 쪽도 확정으로 기록하지 않는다.** 문맥상
자연스럽다는 이유로 고르지 않는다. ②를 택하면 `evaluation_basis` 3종이 바뀌고
**이미 산출한 달성률 숫자가 달라진다.**

### 0.8.4 결정 4 의 backlog 항목

`resolution_date` 가 `NULL` 인 행은 결의일자 기준 연도 조회에서 제외된다.
분모·분자 양쪽에서 빠지므로 달성률은 왜곡되지 않으나, **전체 구매액이 조용히
줄어드는데 화면 표시가 없다.**

→ backlog: 대시보드에 "결의일자 미기재 N건 제외" 표시. **계산 로직은 바꾸지 않는다.**

> 사업자등록번호에 거래처명 표기가 여러 형태로 존재하더라도 **하나의 업체
> 이력**으로 취급한다. **거래처명 자체는 동일 업체 여부 또는 구매유형
> 자동판정의 기준으로 사용하지 않는다.**

| 항목 | 내용 |
|---|---|
| 묶는 키 | `purchase.business_no` **완전 일치** |
| 거래처명 | **표시용**으로만 응답에 싣는다(`company_name`). 묶음 기준이 아니다 |
| 기준 표시 | 응답에 `business_no` 를 함께 실어 **무엇으로 셌는지** 밝힌다 |
| 화면 문구 | "사업자등록번호가 같은 건을 모아 셉니다. 거래처명 표기가 달라도 함께 잡힙니다." |
| 정규화 | ⛔ **하지 않는다.** 저장 시점(`normalize_business_no`)에 이미 하이픈 제거 10자리다. 여기서 또 손대면 규칙이 두 곳에 생긴다 |
| 값 없음 | ⛔ **그 건은 세지 않는다.** 거래처명으로 되돌아가지 않는다 |
| 상호변경 | ⛔ **자동 판정하지 않는다.** 번호가 같으면 이력은 이어지고, 왜 이름이 달라졌는지는 사람이 확인한다 |

## 0.4 ⛔ `결의일자` 와 API `stdrDate` 를 같은 것으로 취급하지 않는다

| 개념 | 상태 |
|---|---|
| 구매실적 연도 귀속 기준 | ✅ **결의일자** (고객 회신) |
| SMPP `stdrDate` (인증 유효성 확인 기준일자) | 🟡 **결의일자** — PM 결정(2026-08-27) |

`stdrDate` 는 "유효확인서를 확인할 기준일자" 로, 인증 유효성 판정에 쓰이는 값이다.
구매실적의 연도 귀속 기준과 **업무적 의미가 다르다** — 두 값이 같아진 것은 결정의
결과이지, 하나가 다른 하나를 자동으로 따라간 것이 아니다.

> 🟡 **PM 결정으로 기록한다(2026-08-27, STEP 45·47 지시서).** 이 결정이 고객
> 회신을 근거로 한 것인지, PM 판단인지는 **문서로 확인되지 않았다.** 달성률 숫자를
> 바꾸는 값이므로, 고객 회신 근거가 있다면 그 출처를 여기에 덧붙일 것.

#### `stdrDate` 선택지 (2026-08-28 정리 · **미확정** · W-11)

| 안 | 내용 |
|---|---|
| ① | 구매 건별 판정 기준일과 **동일한 날짜**를 전달 |
| ② | **조회 시점(오늘)** 날짜를 전달 |
| ③ | **회계연도 말일** 등 고정 기준일을 전달 |
| ④ | 고객이 별도 기준을 지정 |

⛔ **어느 안도 코드에 넣지 않았다.** 확정 전까지 `stdrDate` 자동 계산·오늘 날짜
자동 입력·정책별 자동 분기를 만들지 않는다.

⛔ **코드는 여전히 `stdrDate` 를 필수 인자로만 받으며 기본값을 두지 않는다**
(`collectors/client.py`). 위 결정이 곧바로 코드의 기본값이 되지는 않는다 — 어느
행의 결의일자를 넣을지는 호출하는 쪽이 매번 명시해야 하고, 그래야 "무엇을 기준으로
판정했는지" 가 호출 지점에 남는다.

### D-24 확정 후 — 현재 구조로 무엇이 되고 무엇이 남는가

기존 구조는 **날짜를 인자로 받도록** 만들어 두었으므로, 확정된 값을 넣기만 하면 된다.

|---|---|---|
| `PeriodFilter` | `date_field` 를 **필수 인자**로 받는다. 기본값 없음 | 구조 변경 불필요 |

| Dashboard | 기간 조회 불가 사유를 화면에 표시 | 유지 |

> ⚠️ **남은 문제 — 물리 컬럼 매핑.** 코드의 `payment_date` 는 "대금 지급일(지출완료)"
> 로 정의되어 있다. 고객이 확인해 준 것은 "**산정 기준일**이 `결의일자`" 이지,
> "`결의일자` = 대금 지급 완료일" 이라고 답한 것이 아니다. 두 진술은 다르다.

# 5. 🔴 매월 누적 운영 요건 — 새로 드러난 구조적 문제

> **운영 방식**: 매월 동일 형식 파일을 업로드하고, **연도 기준으로 누적 관리**한다.

## 5.1 문제 1 — 기간 필터가 없다 (P0)

`Calculator` 가 `PurchaseRepository.find_all()` 을 사용한다. **전 기간을 통째로 합산**한다.

```text
현재: 2026년 데이터 + 2027년 데이터 → 하나의 달성률로 합산
필요: 연도별로 분리된 달성률
```

> **2년차부터 달성률이 틀린다.** 지금은 데이터가 없어 드러나지 않았을 뿐이다.

## 5.2 문제 2 — 중복 적재를 막지 못한다 (P0)

`purchase` 테이블에 **UNIQUE 제약이 없고**, Import 에 중복 검사가 없다.

```text
7월 파일 업로드        → N건 저장
7월 파일 재업로드(실수) → N건 추가 저장 = 2N건
```

> 매월 운영에서 **재업로드는 반드시 발생한다** (파일 오류·수정본 수령 등).
