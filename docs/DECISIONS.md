## 0.3 🔴 음수 상계 — 샘플 데이터에서 확인된 구조적 장애

> 업무규칙 ③ 은 확정되었으나, **제공된 샘플로는 그대로 구현할 수 없다.**
> 근거: `REAL_PURCHASE_DATA_ANALYSIS.md` §7.3 · §7.4 (음수 125건 실측).

| 후보 컬럼 | 음수 125건 채움률 | 판정 |
|---|---|---|
| `기표번호` | **0 / 125** | ❌ 사용 불가 |
| `결의번호` | **0 / 125** | ❌ 사용 불가 |
| `LN_SQ` | **0 / 125** | ❌ 사용 불가 |
| `GRP_NB` | **0 / 125** | ❌ 사용 불가 |
| `SEQNO` | 125 / 125 | ⚠️ 행 일련번호일 뿐 원거래를 가리키지 않음 |
| `코드` | 125 / 125 | ⚠️ 거래처 코드이지 거래 식별자가 아님 |
| `사업자번호` | 125 / 125 | ⚠️ 거래처 단위. 거래 단위가 아님 |
| `적요` | 채워짐 | ⚠️ 자유 텍스트. 동일 문구가 여러 거래에 반복됨 |

**금액만으로 짝을 맞출 수 없는 이유**: 동일 금액이 중복 존재한다
(`−132,000` 2건 · `−200,000` 2건 등). 어느 원거래에 대응하는지 결정할 수 없다.
또한 음수 24건(19.2%)은 같은 사업자에 절대값이 같은 양수조차 없다.

> ⛔ **상계 로직을 구현하지 않는다.** 판별 키가 확정될 때까지 임의의 중복/상계 키를
> 만들지 않는다. → 고객 확인 질문은 `CUSTOMER_DATA_QUESTIONS.md` Q4-1.

### 0.5.1 정책 범위 — 3종 제외 확정

| 정책 | 처리 |
|---|---|
| 중증장애인생산품 | ⛔ **프로젝트 범위 제외** |
| 기술개발생산품 | ⛔ **프로젝트 범위 제외** |
| **녹색제품 (`GREEN`)** | ⛔ **프로젝트 범위 제외** |

> 🔴 **`GREEN` 은 "개발 보류"가 아니라 "범위 제외" 다.** D-3(정책은 유지하되 계산
> 보류)은 **이 결정으로 대체된다.** 화면에서 "계산 보류" 로 표시하던 처리도 더는
> 맞지 않는다.

### 0.5.2 정책 중복 인정 — 상호 배타 분류 금지

```text
사업자 A ─┬─ 여성기업 인증
          └─ 창업기업 인증
     ↓
A 와의 구매거래는 여성기업 실적 ✅ 창업기업 실적 ✅ 둘 다 인정
```

| 규칙 | 내용 |
|---|---|
| **분자** | 각 정책을 **독립적으로 판정**한다. 동일 거래가 여러 정책의 분자에 각각 포함될 수 있다 |
| **분모** | 전체 구매금액은 **실제 구매금액 기준으로 1회만** 계산한다. 중복 가산하지 않는다 |
| ⛔ **금지** | `IF 여성기업 … ELSE IF 창업기업 …` 같은 **우선순위 기반 배타 분류** |

검증 예 (실측):

```text
전체 구매 100만 · 사업자 A 20만(여성+창업)
→ 여성기업 분자 20만 · 창업기업 분자 20만 · 분모 100만  (120만이 아님)
```

### 0.5.3 구매유형 분류 — **확정된 3건만**

| 지출 항목 | 구매 유형 |
|---|---|
| `도서인쇄비` | **물품** |
| `소모성물품구입비` | **물품** |
| `임차료` | **용역** |

> ⛔ **문자열 매칭 범위를 임의로 확대하지 않는다.** "도서가 들어가면 전부 물품",
> "임대가 들어가면 전부 용역" 같은 규칙을 만들지 않는다. **정확히 위 세 값만** 확정
> 이며, 다른 지출항목은 고객 확인 전까지 분류하지 않는다.

### 0.5.5 🔴 "11개 − 3개 = 8개" 가 현재 문서와 맞지 않는다

`POLICY_GAP_ANALYSIS_2026.md` §1 기준으로 **정부권장정책 구매 부문은 11개**이고,
**녹색제품은 그 11개에 포함되어 있지 않다**(파일에서 확인되지 않은 MVP 전용 정책).

```text
구매 11개 − 기술개발생산품 − 중증장애인생산품 = 9개
(녹색제품은 애초에 11개 밖 → 빼도 11개는 줄지 않음)
```

| 후보 | 정책 | 현재 구현 |
|---|---|---|
| 1 | 중소기업 | ✅ `SMALL_BUSINESS` |
| 2 | 창업기업 | ✅ `STARTUP` |
| 3 | 여성기업 | ✅ `WOMAN` |
| 4 | 장애인기업 | ✅ `DISABLED` |
| 5 | 사회적기업 | ❌ 미구현 |
| 6 | 사회적협동조합 | ❌ 미구현 |
| 7 | 온누리상품권 구매 | ❌ 미구현 (분모가 **기관 경상경비**로 다름) |
| 8 | 장애인표준사업장 | ❌ 미구현 |
| 9 | 국가유공자자활용사촌 | ❌ 미구현 (분모가 **생산가능품목 총 구매액**으로 다름) |

> **9개 중 어느 1개가 더 빠져 8개가 되는지 확정되지 않았다.** 임의로 정하지 않고
> PM 확인 대기한다.

## 0.4 ⛔ `결의일자` 와 API `stdrDate` 를 같은 것으로 취급하지 않는다

| 개념 | 상태 |
|---|---|
| 구매실적 연도 귀속 기준 | ✅ **결의일자** (고객 회신) |
| SMPP `stdrDate` (인증 유효성 확인 기준일자) | 🔴 **별도 결정 필요** |

`stdrDate` 는 "유효확인서를 확인할 기준일자" 로, 인증 유효성 판정에 쓰이는 값이다.
구매실적의 연도 귀속 기준과 **업무적 의미가 다르다.** 코드는 현재 `stdrDate` 를
필수 인자로만 받으며 기본값을 두지 않는다(`collectors/client.py`).

### D-24 확정 후 — 현재 구조로 무엇이 되고 무엇이 남는가

기존 구조는 **날짜를 인자로 받도록** 만들어 두었으므로, 확정된 값을 넣기만 하면 된다.

| 계층 | 처리 | D-24 확정 반영 |
|---|---|---|
| `PeriodFilter` | `date_field` 를 **필수 인자**로 받는다. 기본값 없음 | 구조 변경 불필요 |
| 설정 | `PURCHASE_PERIOD_DATE_FIELD` — 기본값 `None` | **설정값 주입만으로 활성화** |
| API | 연도를 지정했는데 설정이 없으면 **503** | **유지** — 설정 누락 방어선으로 계속 필요 |
| Dashboard | 기간 조회 불가 사유를 화면에 표시 | 유지 |

> ⚠️ **남은 문제 — 물리 컬럼 매핑.** 코드의 `payment_date` 는 "대금 지급일(지출완료)"
> 로 정의되어 있다. 고객이 확인해 준 것은 "**산정 기준일**이 `결의일자`" 이지,
> "`결의일자` = 대금 지급 완료일" 이라고 답한 것이 아니다. 두 진술은 다르다.
> 어떤 물리 컬럼에 `결의일자` 를 넣을지는 **PM 결정 사항**이다.

> ⚠️ **정책별 기준일은 별개 축이다.** 현재 코드에서 `evaluation_basis`
> (`PAYMENT_DATE`/`CONTRACT_DATE`)는 **인증 유효기간 판정**에만 쓰이고,
> **연도 귀속 기간 필터는 전 정책 공통으로 하나의 `date_field`** 를 쓴다.
> 창업기업에 계약일자를 추가로 고려하려면 이 구조에 손을 대야 한다 → §0.2 다.

# 5. 🔴 매월 누적 운영 요건 — 새로 드러난 구조적 문제

> **운영 방식**: 매월 동일 형식 파일을 업로드하고, **연도 기준으로 누적 관리**한다.

## 5.1 문제 1 — 기간 필터가 없다 (P0)

`Calculator` 가 `PurchaseRepository.find_all()` 을 사용한다. **전 기간을 통째로 합산**한다.

```text
현재: 2026년 데이터 + 2027년 데이터 → 하나의 달성률로 합산
필요: 연도별로 분리된 달성률
```

> **2년차부터 달성률이 틀린다.** 지금은 데이터가 없어 드러나지 않았을 뿐이다.

## 5.2 문제 2 — 중복 적재를 막지 못한다 (P0)

`purchase` 테이블에 **UNIQUE 제약이 없고**, Import 에 중복 검사가 없다.

```text
7월 파일 업로드        → N건 저장
7월 파일 재업로드(실수) → N건 추가 저장 = 2N건
```

> 매월 운영에서 **재업로드는 반드시 발생한다** (파일 오류·수정본 수령 등).
