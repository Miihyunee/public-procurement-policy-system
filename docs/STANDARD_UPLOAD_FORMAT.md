# 1. 왜 표준 양식인가

현재는 기관이 준 매입매출장(88개 컬럼)을 직접 해석해야 한다. 그 방식은 다음 문제가 있다.

| 문제 | 실측 근거 |
|---|---|
| 필요한 컬럼이 **없다** | 계약일자 · 대표자명 · 구매유형 — 88개 중 0건 |
| 컬럼 의미가 **불명확하다** | 날짜만 4종(`신고기준일`·`기표일자`·`결의일자`·`발행일`) |
| 대부분이 **구매가 아니다** | 2,903행 중 매출이 79.4% |
| 기관마다 **양식이 다르다** | 컬럼명이 바뀌면 시스템 전체가 영향받음 |

→ **사용자가 우리 양식에 맞춰 입력**하면 위 4가지가 한 번에 사라진다.

## 1.1 목표 구조

```text
표준 Excel  →  Validation  →  Mapping  →  Purchase Model  →  Repository  →  Calculator
   (사용자 입력)                              (내부 계산용)
```

**핵심 원칙**: 업로드 컬럼이 바뀌어도 Calculator 가 영향받지 않는다.
Mapping 계층이 그 사이를 흡수한다.

# 3. ✅ 해소 — 결의일자는 `resolution_date` 로 담는다 (2026-08-15 PM 결정)

> `resolution_date` 필드를 신설한다. 기존 `payment_date` 를 결의일자로 재정의하지 않는다.

`Purchase` 모델의 날짜는 셋이 되었다.

| 필드 | 정의 | 필수 |
|---|---|---|
| `resolution_date` | **결의일자.** 구매실적 연도 귀속·산정 기준일 | 선택(기존 행 보호) |
| `contract_date` | 계약일자. 창업기업 OR 판정에 함께 사용 | 필수 |
| `payment_date` | 대금 지급일(지출완료). **산정 기준일이 아니다** | 필수 |

| 매핑 | |
|---|---|
| Excel `결의일자` | → `Purchase.resolution_date` |
| Excel `계약일자` | → `Purchase.contract_date` |

반영 범위와 하지 않은 것은 `DECISIONS.md` §0.7 참조.

**창업기업 OR 규칙도 함께 바뀌었다.** 이전에는 어느 컬럼이 결의일자인지 몰라
`payment_date` 와 `contract_date` 를 함께 보았으나, 이제 `ResolutionOrContractDateRule`
이 **`resolution_date` 와 `contract_date`** 를 본다. 업무규칙 자체는 그대로다.

## 3.1 ✅ 해소 — 지급일 컬럼 추가 (2026-08-17 PM 결정)

표준 양식이 **6컬럼**이 되었다.

```text
결의일자 | 계약일자 | 지급일 | 기업명 | 사업자등록번호 | 계
```

`payment_date` 를 nullable 로 바꾸는 안은 **정책 4종(중소·여성·장애인·녹색)의
판정 기준일을 새로 정해야** 해서 채택하지 않았다 → `DECISIONS.md` §0.8.1.

세 날짜는 **서로 다른 업무 의미**를 가지며 섞이지 않는다.

| 필드 | 의미 | 쓰이는 곳 |
|---|---|---|
| `resolution_date` | 결의일자 | 연도 귀속 · 창업기업 판정 |
| `contract_date` | 계약일자 | 창업기업 판정 |
| `payment_date` | 지급일(지출완료) | 일반 정책 4종 인증 판정 |

# 4. 업로드 검증 규칙 — ✅ 구현 완료

`uploads/validation.py`. 테스트 45건으로 고정했다.

## 4.1 파일 단위

| 검증 | 실패 시 |
|---|---|
| 파일 형식 (`.xlsx`) | 파일 거부 |
| 필수 컬럼 존재 | 파일 거부 — 누락 컬럼명 표시 |
| 알 수 없는 컬럼 | 경고 (자동 매핑하지 않음) |
| 빈 파일 | 파일 거부 |

## 4.2 행 단위

| 검증 | 처리 |
|---|---|
| 사업자등록번호 형식 | 하이픈 제거 후 10자리. **9자리 자동 보정 금지**. 체크섬 오류는 **경고** |
| 날짜 형식 | 파싱 실패 시 행 오류 |
| 금액 형식 | 숫자 아니면 행 오류 |
| **음수·0원 금액** | ⚠️ **경고**. 오류로 단정하지 않는다 — §5 |
| 필수값 누락 | 행 오류 |
| 중복 행 | 🔴 **미구현** — 판정 기준 미정 |
| 구매유형 값 | 🔴 **미구현** — 컬럼 자체가 양식에 없음 |

> 정규화 규칙은 **새로 만들지 않고** 기존 `matchers.business_no` 를 재사용한다.

## 4.3 결과 표시 — ✅ 구현 완료

실제 출력(`ValidationReport.summary_lines()` · `issue_lines()`):

```
총 2건
정상 1건
오류 1건

  3행 | 결의일자       | 날짜 형식이 잘못되었습니다: '2026.13.45' (예: 2026-03-15)
  3행 | 계             | 숫자가 아닙니다: 'abc'
  3행 | 기업명         | 값이 없습니다.
  3행 | 사업자등록번호 | 사업자등록번호를 사용할 수 없습니다: '123' (하이픈 제외 10자리)
```

**행 · 컬럼 · 사유**로 보여준다. stack trace 를 노출하지 않는다.
한 행에 문제가 여러 개여도 오류 **건수는 1행**으로 센다.

# 5. 🔴 음수 금액 — 저장 자체가 막혀 있다

고객 확정 규칙(§0.6.3)에 따라 상계 로직은 구현했다(`core/offsetting.py`).
그러나 현재 `PurchaseRepository._validate()` 가 **`amount <= 0` 저장을 거부**한다.

```
음수 거래 → 저장 거부 → DB 에 없음 → 상계할 대상이 없음
```

| 선택지 | 영향 |
|---|---|
| ① 현행 유지 | 음수 행을 업로드 오류로 처리. **상계 규칙이 영원히 동작하지 않음** |
| ② 저장 허용 | D-003(원본 보존)과 일치. **C-2 충돌 해소 · Issue #49** |
| ③ 업로드 시점에 상계 | 원본이 남지 않아 추적 불가 |

**②가 확정 업무규칙과 일치**하지만, Repository 검증 변경은 승인 대상이라
진행하지 않았다. 영향 범위는 `Purchase` 모델 · Repository 검증 · Importer ·
Calculator · 기존 테스트 · 0원 거래 처리다.

# 7. 확정 / 미확정 요약

## ✅ 확정

- 구매실적 기준일 = **결의일자** (일반 정책)
- 창업기업 = **결의일자 OR 계약일자**가 인증 유효기간에 해당하면 인정
- 구매금액 = **VAT 포함 총액** (원본의 `계`)
- 음수 상계 판별 = **기업명 + 사업자번호 + 절대금액 + 이전 거래**
- 구매유형 3건 — 도서인쇄비/소모성물품구입비 → `GOODS`, 임차료 → `SERVICE`
- 표준 양식을 **우리가 지정**하는 방향
- 결의일자를 담을 내부 필드 = **`Purchase.resolution_date`** (2026-08-15) — 구현 완료
