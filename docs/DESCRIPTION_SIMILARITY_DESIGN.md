# 1. 분류 체계 — 기존 정의를 따릅니다

지시서에 "실제 최종 분류 항목은 기존 정의를 확인하고 따른다" 고 되어 있어
`core/purchase_type.py` 를 확인했습니다.

```python
CONSTRUCTION: Final = "CONSTRUCTION"   # 공사
SERVICE:      Final = "SERVICE"        # 용역
GOODS:        Final = "GOODS"          # 물품
PURCHASE_TYPES: Final = frozenset({CONSTRUCTION, SERVICE, GOODS})
PURCHASE_TYPE_LABELS = {CONSTRUCTION: "공사", SERVICE: "용역", GOODS: "물품"}
```

| 항목 | 결정 |
|---|---|
| 분류값 | **기존 3값을 그대로** 사용 |
| "기타 / 미분류" | ⛔ **새 값을 만들지 않습니다.** 기존 코드에서 미분류는 `None` 입니다 |
| 새 분류 체계 | ⛔ 만들지 않습니다 |

**왜 유형이 필요한가**: 여성기업 목표율이 유형별로 다르기 때문입니다
(공사 3% / 용역·물품 5% — `DECISIONS.md` §0.5.3).

## 1.1 현재 확정된 분류 규칙 — 예산과목 3건뿐

```python
CONFIRMED_BUDGET_ACCOUNT_TYPES = {
    "도서인쇄비": GOODS,
    "소모성물품구입비": GOODS,
    "임차료": SERVICE,
}
```

`classify_budget_account()` 는 **완전 일치**로만 판정하며, 그 밖의 예산과목은
`None`(미분류)입니다. 샘플 기준 금액의 **약 34%** 만 덮으며, 가장 큰
`외주용역비`(약 42.4억)는 미분류로 남습니다.

> 🔴 **이 3건 외의 분류 규칙은 고객 미확정입니다**(결정 대기 ②). 적요 분석은
> 이 공백을 **자동으로 메우는 것이 아니라**, 담당자가 판단할 **후보를 제시**
> 하는 것입니다.

## 1.2 참고 — 원본 데이터의 담당자 분류 실적

작업본 시트에는 담당자가 직접 채운 `구분` 컬럼이 있습니다(1,744행).

| 구분 | 건수 |
|---|---|
| 용역 | 1,172 |
| 물품 | 502 |
| 공사 | 70 |

> ⚠️ 이 값은 **담당자의 과거 판단**이며 업무규칙이 아닙니다. 분석기의 **정답
> 후보(seed)** 로 쓸 수 있으나, ⛔ 여기서 규칙을 역추론해 자동 확정하지
> 않습니다.

# 2. 공통 인터페이스 (개념 설계)

방법을 고르기 **전에** 인터페이스를 고정합니다. 그래야 나중에 어떤 방법을
선택해도 상위 계층(DB-2 · 검토 API · 화면)을 다시 만들지 않습니다.

```python
# core/description_classifier.py  (신규 · 미구현)

@dataclass(frozen=True, kw_only=True)
class TypeCandidate:
    """구매유형 후보 하나."""
    purchase_type: str          # CONSTRUCTION | SERVICE | GOODS
    score: Decimal              # 0.0 ~ 1.0
    evidence: str = ""          # 왜 이 후보인지 (담당자에게 보여줄 근거)


@dataclass(frozen=True, kw_only=True)
class ClassificationResult:
    """적요 하나에 대한 분석 결과.

    ⛔ 최종 유형을 담지 않는다. 후보와 점수만 담는다.
    """
    candidates: list[TypeCandidate]     # 점수 내림차순. 비어 있을 수 있음
    analyzer_name: str
    analyzer_version: str

    @property
    def top(self) -> TypeCandidate | None: ...

    @property
    def is_ambiguous(self) -> bool:
        """이중 매칭 여부. ⛔ 판정 기준(임계값)은 미확정 → 4장"""
        ...


class DescriptionClassifier(Protocol):
    """적요 → 구매유형 후보. 구현체는 아직 없다."""

    name: str
    version: str

    def classify(self, description: str) -> ClassificationResult: ...
```

## 2.1 인터페이스 설계 근거

| 결정 | 이유 |
|---|---|
| `ClassificationResult` 에 **최종값이 없다** | 타입 수준에서 "자동 확정" 을 불가능하게 만듭니다. 확정은 DB-2 의 `final_purchase_type` 에만 존재 |
| `candidates` 가 **빈 리스트 가능** | 판단할 수 없으면 후보를 만들지 않는 것이 정직합니다. 억지 후보를 만들지 않습니다 |
| `evidence` | 담당자가 "왜 이 후보인가" 를 봐야 판단할 수 있습니다. BM25 면 매칭 키워드, RAG 면 유사 사례 |
| `analyzer_name` · `version` | 방법 비교와 재현에 필요. DB-2 에 함께 저장 |
| `Protocol` | 구현체를 갈아 끼워도 상위 계층이 안 바뀝니다 |
| 입력이 `description` 문자열 하나 | 예산과목·거래처를 넣으면 그 순간 **분류 규칙**이 됩니다(고객 미확정). ⛔ 넣지 않습니다 |

⛔ **이 파일을 이번에 만들지 않았습니다.** 위는 개념 설계입니다.

# 3. BM25 / RAG / FUSE — 적용 위치와 장단점

**어느 것도 선택하지 않습니다.** 셋 다 위 `DescriptionClassifier` 를 구현하는
형태이므로, 나중에 실측으로 고르면 됩니다.

```text
       적요 문자열
            │
            ▼
  ┌────────────────────────┐
  │ DescriptionClassifier  │  ← 공통 인터페이스 (고정)
  └────────────────────────┘
     ▲         ▲         ▲
  BM25       RAG       FUSE      ← 교체 가능한 구현체 (미선택)
```

## 3.1 BM25

| 항목 | 내용 |
|---|---|
| **적용 위치** | `classify()` 안. 유형별 키워드 문서를 만들고 적요를 질의로 검색 |
| **필요 데이터** | 유형별 대표 어휘 집합 |
| **장점** | 외부 의존성 없음 · 결정적(같은 입력 = 같은 출력) · 근거 제시가 쉬움(매칭된 단어) · 빠름 · 설명 가능 |
| **단점** | 🔴 **유형별 키워드 집합을 누군가 만들어야 함** — 그 자체가 미확정 업무규칙 · 표현이 다르면 못 찾음("LED 교체" vs "조명 개선") |
| **위험** | 키워드 목록이 곧 분류 규칙이 되어, ⛔ **금지된 "키워드 기반 자동 분류"** 로 미끄러지기 쉬움 |

## 3.2 RAG (유사 사례 검색)

| 항목 | 내용 |
|---|---|
| **적용 위치** | `classify()` 안. **담당자가 이미 확정한 DB-2 사례**를 검색해 유사 사례의 유형을 후보로 |
| **필요 데이터** | 확정 사례 축적 (초기에는 작업본 `구분` 1,744건을 seed 로 검토) |
| **장점** | 🟢 **규칙을 만들지 않아도 됨** — 담당자 판단이 곧 근거 · 근거 제시가 가장 자연스러움("과거 이 건을 공사로 확정하셨습니다") · 쓸수록 정확해짐 |
| **단점** | 🔴 **초기에 데이터가 없으면 동작하지 않음**(cold start) · 임베딩 모델을 쓰면 **외부 의존성·비결정성** 발생 · 담당자의 과거 실수를 학습 |
| **위험** | 외부 LLM/임베딩 API 를 쓰면 **구매 데이터가 외부로 나감** → 공공기관 데이터 반출 검토 필요 |

## 3.3 FUSE (결과 결합)

| 항목 | 내용 |
|---|---|
| **적용 위치** | 여러 `DescriptionClassifier` 를 감싸는 **또 하나의 구현체**. 각 결과를 합산·재순위 |
| **필요 데이터** | 위 두 방법이 먼저 있어야 함 |
| **장점** | 한 방법의 약점을 다른 방법이 보완 · **후보가 갈리면 이중 매칭으로 잡아내기 좋음**(4장) |
| **단점** | 🔴 결합 가중치가 **또 하나의 미확정 규칙** · 근거 설명이 어려워짐 · 가장 복잡 |
| **전제** | 개별 방법의 성능을 먼저 실측해야 의미가 있음 |

## 3.4 비교 요약

| 기준 | BM25 | RAG | FUSE |
|---|---|---|---|
| 외부 의존성 | 없음 | 임베딩 방식이면 있음 | 하위 방법에 따름 |
| 결정적 | ✅ | 방식에 따라 ❌ | 하위에 따름 |
| cold start | ✅ 동작 | 🔴 동작 안 함 | 하위에 따름 |
| 근거 제시 | 쉬움 | 가장 자연스러움 | 어려움 |
| 미확정 규칙을 만드는가 | 🔴 키워드 목록 | 🟢 만들지 않음 | 🔴 결합 가중치 |
| 데이터 반출 위험 | 없음 | 🔴 방식에 따라 있음 | 하위에 따름 |
| 구현 난이도 | 낮음 | 중간~높음 | 높음 |

## 3.5 🟡 선택 절차 제안 (선택 자체는 하지 않음)

```text
1. 인터페이스 확정                      ← 지금 할 수 있음
2. 검토 화면으로 확정 사례를 쌓는다      ← 데이터 확보
3. 쌓인 사례를 정답으로 세 방법을 실측
4. 실측 결과를 근거로 PM/고객이 선택
```

> ⛔ **실측 없이 고르지 않습니다.** 이전에 "적요+거래처명 = 100% 결정력" 이
> 실은 85% 가 단일 출현 키였고 시간 분할 시 95% 가 예측 불가였던 전례가
> 있습니다(`PURCHASE_TYPE_CLASSIFICATION_ANALYSIS.md`).

# 4. 🔴 이중 매칭 (지시 7번)

## 4.1 요구사항

```text
"시설물 유지관리"      용역 0.72 · 공사 0.68   → ⚠️ 담당자 확인 필요
"LED 교체공사"         공사 0.97 · 용역 0.21   → 공사 후보로 표시
```

## 4.2 설계

`ClassificationResult.is_ambiguous` 가 이 판정을 담습니다. 다만 **임계값은
정하지 않습니다.**

```python
@property
def is_ambiguous(self) -> bool:
    """1순위와 2순위가 충분히 벌어지지 않았는가.

    🔴 판정 기준(임계값)은 **미확정**이다.
       - 절대 차이? (0.72 − 0.68 = 0.04)
       - 상대 비율? (0.68 / 0.72 = 0.94)
       - 1순위 절대 점수 하한도 볼 것인가?
    실측 없이 정하지 않는다. → 결정 대기
    """
```

## 4.3 ⛔ 하지 않는 것 — 가장 중요

| 금지 | 이유 |
|---|---|
| **점수가 높다고 자동 확정** | 고객이 확정한 분류 규칙은 예산과목 3건뿐. 0.97 도 **후보**일 뿐 |
| 이중 매칭이면 자동 제외 | 담당자가 봐야 할 건을 숨기는 것 |
| 임계값을 임의로 정함 | 실측 근거 없이 정하면 조용히 잘못 분류됨 |

**이번 단계의 결론**: 명확하든 애매하든 **후보와 점수를 보여주고 담당자가
고른다.** `is_ambiguous` 는 담당자가 **우선 볼 건을 정렬**하는 데만 씁니다.

# 5. 데이터 흐름에서의 위치

```text
DB-1 purchase.description  (원본 · ⛔ 불변)
        │  읽기만
        ▼
DescriptionClassifier.classify()
        │  ClassificationResult (후보 + 점수 + 근거)
        ▼
DB-2 purchase_review
   analysis_status / analyzer_name / analyzer_version
   candidates_json / top_type / top_score / is_ambiguous
        │
        ▼
검토 화면 → 담당자 선택 → final_purchase_type
```

| 규칙 | 강제 방법 |
|---|---|
| 분석기가 원본을 수정하지 않음 | 입력이 문자열 하나. Repository 를 주입받지 않음 |
| 분석기가 확정값을 덮지 않음 | 쓰기 대상이 **분석 컬럼뿐**. `final_purchase_type` 을 쓰지 않음 |
| 재분석해도 확정값 유지 | 위와 동일 (DB-2 §3.2) |

# 7. 테스트 계획 (설계만)

| # | 항목 | 기대 |
|---|---|---|
| 1 | 단일 후보 | 후보 1개 · `is_ambiguous = False` |
| 2 | 복수 후보 (이중 매칭) | 후보 2개 이상 · `is_ambiguous = True` · ⛔ 자동 확정 없음 |
| 3 | 낮은 유사도 | 후보는 있으나 점수 낮음 · 확정하지 않음 |
| 4 | 미분류 | `candidates == []` · `top is None` |
| 5 | 동일 적요 | 같은 입력 → 같은 출력 (결정적) |
| 6 | 유사 적요 | 유사한 입력 → 유사한 후보 |
| 7 | 빈 문자열 · `None` | 오류 없이 후보 0개 |
| 8 | ⛔ 결과에 최종값 없음 | `ClassificationResult` 에 `final_*` 필드 부재 (AST 검사) |
| 9 | ⛔ 원본 미수정 | 분석기가 Repository 를 참조하지 않음 (AST 검사) |
| 10 | 재분석 | 담당자 확정값이 덮이지 않음 |
