# 2. 담당자가 보는 정보 (지시 8번)

화면은 **네 블록**으로 나뉩니다. 블록이 섞이면 "원본 적요가 공사로 바뀌었다"
같은 오해가 생기므로, 응답 스키마 수준에서 분리해 둡니다.

## 2.1 원본 (DB-1 · ⛔ 전부 읽기 전용)

| 화면 라벨 | 출처 |
|---|---|
| 적요 | `purchase.description` |
| 신고기준일 | `purchase.issue_date` |
| 결의일자 | `purchase.resolution_date` |
| 거래처명 | `purchase.company_name` |
| 사업자번호 | `purchase.business_no` |
| 금액(VAT 포함) | `purchase.amount` |
| 예산과목 | `purchase.budget_account` |

> ⚠️ **공급가액은 DB-1 에 별도로 보관되지 않습니다.** 원본 엑셀에는 공급가액 ·
> 세액 · 계 세 컬럼이 있으나, 표준 양식은 **VAT 포함 총액 한 값**만 받습니다
> (`DECISIONS.md` 금액 기준). 공급가액을 화면에 따로 보여주려면 스키마 변경이
> 필요하며, 이는 **결정 대기 항목**입니다.

## 2.2 분석 결과 (DB-2 · ⛔ 읽기 전용 · **확정이 아님**)

| 화면 라벨 | 출처 |
|---|---|
| 분석 방법 | `analyzer_name` + `analyzer_version` |
| 후보 유형 · 후보 순위 | `candidates_json[].purchase_type` (점수 내림차순) |
| 후보 점수 | `candidates_json[].score` |
| 후보 개수 | 후보 목록에서 계산 |
| 1·2순위 점수차 | 후보 1·2번 점수의 차. 후보가 1개 이하면 **`null`** |
| 근거 | `candidates_json[].evidence` |
| 확인 권장 표시 | `is_ambiguous` |

> ⛔ **점수차에 기준이 없습니다.** "차이가 크면 확정" 같은 임계값을 만들지
> 않았습니다(고객 미확정). 숫자를 그대로 보여줄 뿐입니다.

## 2.3 같은 적요의 과거 확정 이력 (DB-1 + DB-2 · ⛔ 추천이 아님)

| 화면 라벨 | 뜻 |
|---|---|
| 과거 N건 + 유형별 건수 | 같은 적요를 과거에 어떻게 확정했는지 |
| **일관성** | `이력 없음` / `한 유형으로만 확정됨` / `여러 유형으로 갈림` |
| **최다 유형 + 비율** | 가장 많이 고른 유형과 그 비율(%) |
| **유형 수** | 과거에 붙은 서로 다른 유형의 개수 |
| "과거 판단이 갈렸던 적요입니다" | 같은 적요가 **여러 유형**으로 확정된 적 있음 |
| "1순위 후보가 과거 최다 유형과 다릅니다" | 분석과 과거 판단이 갈림 |
| **"과거 확정 이력 없음 (처음 보는 적요)"** | 이력이 없음. ⛔ **오류가 아니며** 임의 유형을 붙이지 않음 |

> ⛔ **일관성은 등급이 아닙니다.** "높음/보통/낮음" 처럼 비율을 잘라 만든 값이
> 아니라, **"이력이 있는가 · 갈렸는가" 라는 구조적 사실** 세 가지뿐입니다.
> 갈린 **정도**는 최다 유형 비율로 원시값 그대로 보여주며, 그 값을 어디서
> 자를지는 🔴 고객 확인 사항입니다.

> **왜 별도 블록인가**: `review` 블록 안에 넣으면 "확정값" 으로 오인됩니다.
> 과거 기록을 **세어서 보여줄 뿐**이며, 어떤 유형이 맞다고 말하지 않습니다.
>
> **판단 보류(`None`)는 이력에 세지 않습니다** — 사람이 결론을 내지 않은
> 것이기 때문입니다.

## 2.4 담당자 결정 (DB-2 · ✅ **여기서만 편집**)

| 선택지 | 값 |
|---|---|
| 공사 | `CONSTRUCTION` |
| 용역 | `SERVICE` |
| 물품 | `GOODS` |
| **판단 보류** | `null` — 새 유형이 아니라 **값 없음** |
| 메모 | `review_note` |

**화면 전체에서 편집 가능한 것은 유형 선택과 메모 두 개뿐입니다.**

> ⛔ **어떤 선택지도 미리 눌려 있지 않습니다.** 분석 1순위가 100% 여도
> 마찬가지이며, 화면에 "선택된 항목이 없습니다" 라고 명시합니다. 미리 눌러
> 두면 담당자가 그대로 확정을 눌러 **사실상 자동 확정**이 됩니다.

# 3. 담당자가 할 수 있는 동작

| 동작 | 결과 |
|---|---|
| 유형 선택 | `final_purchase_type` 설정 (아직 미확정) |
| **확정** | `review_status = CONFIRMED` · `reviewed_by/at` 기록 · 이력 추가 |
| **판단 보류** | `final_purchase_type = NULL` · `review_status = PENDING` 유지 |
| 다시 검토 | `review_status = REOPENED` · 이전 값은 이력에 남음 |
| 메모 | `review_note` |
| 이력 보기 | `purchase_review_history` 조회 |

⛔ **원본 수정 · 행 삭제 동작은 제공하지 않습니다.**

**"판단 보류"** 를 넣은 이유: 담당자가 정말 모를 때 아무 값이나 고르게
만들면 안 됩니다. 미확정으로 남기는 것이 정직한 상태입니다.

# 4. API 설계 (개념 · 미구현)

기존 FastAPI 패턴(`app.py`)을 그대로 따릅니다. UI 프레임워크에 종속되지 않도록
**모든 동작은 HTTP API** 로만 제공합니다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/reviews` | 검토 목록 (필터·정렬·페이징) |
| `GET` | `/reviews/{purchase_id}` | 한 건 상세 (원본 + 후보 + 확정) |
| `PUT` | `/reviews/{purchase_id}` | 유형 확정 · 메모 |
| `POST` | `/reviews/{purchase_id}/reopen` | 재검토 |
| `GET` | `/reviews/{purchase_id}/history` | 변경 이력 |
| `GET` | `/reviews/summary` | 진행률 (확정/미확정/확인 필요) |
| `POST` | `/final-datasets` | **최종 확정** — DB-3 생성 |
| `GET` | `/final-datasets` | 생성 이력 (ACTIVE / SUPERSEDED) |

## 4.1 응답 예 (`GET /reviews/{purchase_id}`)

```json
{
```

# 5. 상계 검토와의 통합 (지시 10번)

## 5.1 현재 상태

`core/offsetting.py` 는 이미 **담당자 확인 대상**을 만들어 냅니다.

```python
@dataclass(frozen=True, kw_only=True)
class NeedsManualReviewGroup:
    key: MatchKey                       # 기업 · 사업자번호 · 금액
    negative: Purchase
    candidates: list[Purchase]          # 후보 전부
    reason: ReviewReason                # MULTIPLE_CANDIDATES | CONTESTED_CANDIDATE
    sibling_negatives: list[Purchase]
    def candidate_lines(self) -> tuple[str, ...]: ...
```

실측(2026년 2,292행): 자동 상계 42쌍 · **담당자 확인 84건** · 짝 없음 3건.

## 5.2 구조가 이미 같습니다

| | 구매유형 검토 | 상계 검토 |
|---|---|---|
| 후보 제시 | `ClassificationResult.candidates` | `NeedsManualReviewGroup.candidates` |
| 자동 확정 | ⛔ 안 함 | ⛔ 안 함 |
| 담당자 선택 | 유형 3택 | 후보 양수 중 1택 |
| 결과 저장 | DB-2 `final_purchase_type` | DB-2 `offset_review.chosen_purchase_id` |

**같은 검토 화면에 탭으로 넣을 수 있습니다.**

```text
구매유형 검토          상계 검토 (84건)
─────────────────────────────────────────
┌───────────────────────────────────────────────────────────┐
│ (−) 16,900원  엘지전자(주)  107-86-14075  발행 2026-01-05  │
│ 어느 (+) 거래와 상계할까요?                                 │
│  ○ 발행 2026-01-05 | 적요 01/05 물품대 외 | 예산과목 (공란) │
│  ○ 발행 2026-01-05 | 적요 01/05 물품대 외 | 예산과목 (공란) │
│  ○ 발행 2026-01-05 | 적요 수도권…정산 건 | 예산과목 각종수수료│
│  ○ 상계하지 않음                                           │
│  ℹ️ G20 지출결의서(세금계산서·비고란)를 확인해 판단하세요.  │
│                                              [ 확정 ]      │
└───────────────────────────────────────────────────────────┘
```

## 5.3 ⛔ 이번에 하지 않는 것

# 9. 목록 다루기 — 검색 · 필터 · 정렬 · 페이지 (STEP 8)

## 9.1 ✅ 확정된 기술사항

| 기능 | 값 | 비고 |
|---|---|---|
| **적요 검색** | 부분 문자열 · 대소문자·띄어쓰기 무시 | 빈 값이면 전체 |
| **상태 필터** | `ALL` · `PENDING` · `CONFIRMED` · `REOPENED` | ⛔ 새 상태를 만들지 않음 |
| **확정 여부** | `ALL` · `DECIDED` · `UNDECIDED` | 재검토(`REOPENED`)는 **미확정** |
| **과거 이력** | `ALL` · 이력 있음 · 이력 없음 · 혼재 · 1순위=과거최다 · 1순위≠과거최다 | |
| **후보 수** | `ALL` · 0개 · 1개 · 2개 이상 | `candidate_count` 그대로 |
| **정렬 기준** | 구매ID · 결의일자 · 신고기준일 · 금액 · 적요 · 상태 · 후보 수 · 점수차 · 과거 확정 건수 · 과거 최다 비율 | 담당자가 고름 |
| **정렬 방향** | 오름차순 · 내림차순 | |
| **페이지 크기** | 기본 20 · 최대 200 | 화면 성능용 값 |

**정렬에서 "값 없음" 은 방향과 무관하게 늘 뒤로** 갑니다. 후보가 1개면 점수차라는
것이 **존재하지 않으므로**, 내림차순으로 바꿨다고 빈 값이 앞으로 몰려오면
담당자가 빈 칸부터 보게 됩니다.

> ⛔ **`score_gap` · `dominant_ratio` 로 줄을 세울 수는 있지만, 그것이 "먼저 봐야
> 할 순서" 라는 뜻은 아닙니다.** 위험도·우선순위·자동검토 대상 같은 개념을
> 만들지 않았습니다.

## 9.2 ✅ 처리 위치 — 서버

```text
담당자가 고른 조건
      ↓  쿼리 문자열
GET /reviews?search=…&status=…&sort=…&page=…
      ↓
ReviewService.search()   ← 거르고 · 줄 세우고 · 잘라낸다
      ↓
해당 페이지만 응답        ← 전체를 브라우저로 보내지 않는다
```

**왜 브라우저에서 거르지 않는가**: 2,292건이면 견딜 수 있어도, 몇 만 건이 되면
첫 화면에서 전부 내려받느라 느려지고 메모리도 그만큼 씁니다. 화면이 받는 양을
**페이지 크기로 고정**해 두면 건수가 늘어도 첫 화면 비용이 일정합니다.

**아직 SQL 로 내리지 않은 이유**: `score_gap` 과 과거 이력 관련 조건은
**컬럼이 아니라 계산값**입니다. `score_gap` 은 후보 JSON 을 풀어야 나오고, 과거
이력은 DB-1(적요)과 DB-2(확정)를 묶어야 나옵니다. 지금은 서비스 계층에서
계산하며, 다음 항목이 필요해지면 SQL 로 내립니다.

| 조건 | 현재 | SQL 로 내릴 수 있는가 |
|---|---|---|
| 적요 검색 · 상태 · 확정 여부 | 서비스 | 🟢 가능(정규화 컬럼 추가 시) |
| 후보 수 · 점수차 | 서비스 | 🟡 후보를 컬럼으로 펴야 함 |
| 과거 이력 조건 | 서비스 | 🟡 DB-1 · DB-2 조인 + 집계 필요 |

> 🟡 **성능 개선은 필요해질 때 합니다.** 지금 데이터로는 체감되지 않으며,
> 미리 최적화하면 조인 구조를 고객 답변 전에 굳히게 됩니다.

## 9.3 ✅ 과거 이력 색인의 수명 (PastLabelIndex)

**바뀐 것**: 예전에는 한 건을 조회할 때마다 색인을 처음부터 다시 만들었습니다
(구매 전체 + 검토 전체를 매번 읽음).

```text
[이전]  get_target() → 색인 새로 생성 (전체 2회 스캔) → 조회
[현재]  get_target() → 지문 조회(집계 1회) → 같으면 재사용 / 다르면 재생성
```

**낡은 값을 주지 않는 방법**: 서비스가 기억하는 상태가 아니라 **DB 의 지문**으로
판단합니다.

```sql
SELECT COUNT(*), MAX(reviewed_at) FROM purchase_review WHERE review_status = 'CONFIRMED'
```

| 상황 | 지문 변화 | 결과 |
|---|---|---|
| 새 확정 | 건수 ↑ | 재생성 |
| `CONFIRMED` → `REOPENED` | 건수 ↓ | 재생성 |
| 같은 건을 다른 유형으로 재확정 | 확정 시각 변경 | 재생성 |
| 판단 보류로 변경 | 확정 시각 변경 | 재생성 |
| **Repository 를 직접 고침**(테스트 등) | 위와 동일 | 재생성 |
| 재분석 | **변화 없음** | 재사용 |

`updated_at` 이 아니라 `reviewed_at` 을 보는 이유: `updated_at` 은 **재분석에도**
바뀌는데, 분석은 확정 이력을 건드리지 않으므로 그걸로 판단하면 아무 이유 없이
색인을 다시 만들게 됩니다.

## 10.5 ✅ 진행률 — 두 가지를 나란히

```text
전체 확정 17 / 46 · 확인 권장 23        ← 필터와 무관
현재 조건 확정 0 / 29 (0.00%)          ← 지금 걸어 둔 조건 안에서
```

**조건이 전체와 같으면** 같은 숫자가 두 번 나오므로 두 번째 줄을
`현재 조건 = 전체` 로 대신합니다. 숫자를 중복해 보여주면 어느 쪽을 봐야
하는지 오히려 헷갈리기 때문입니다.

⚠️ **미확정 필터에서는 조건 진행률이 항상 0% 입니다.** 확정하는 순간 그 건이
필터에서 빠지기 때문이며, 정상입니다. 이때 의미 있는 값은 **분모(남은 건수)**
이고, 실제로 확정할 때마다 줄어듭니다(29 → 28 → 27 …).

> ⛔ **평가 기준이 아닙니다.** "50% 미만이면 위험" 같은 판정을 붙이지 않으며,
> `ConditionProgress` 에 그런 필드를 만들 수 없도록 테스트가 막습니다.

# 11. 확정 취소(Undo) (STEP 10)

## 11.1 ✅ 현재 구현

| 항목 | 내용 |
|---|---|
| 진입 | 확정된 카드의 **[확정 취소]** 버튼 |
| 동작 | 확인창 → 확인 시 `POST /reviews/{id}/reopen` |
| 결과 상태 | `CONFIRMED` → `REOPENED` |
| API | **기존 것 그대로** — 새 엔드포인트를 만들지 않음 |

## 11.2 ✅ 되돌리기는 **지우기가 아니다**

`reopen` 은 `review_status` 와 `updated_at` **두 컬럼만** 갱신합니다.

| 컬럼 | Undo 후 |
|---|---|
| `review_status` | `REOPENED` 로 변경 |
| `final_purchase_type` | ✅ **그대로** |
| `reviewed_by` | ✅ **그대로** |
| `reviewed_at` | ✅ **그대로** |
| `review_note` | ✅ **그대로** |
| 분석 컬럼(`analyzer_name` · 후보) | ✅ **그대로** |
| `purchase_review` 행 | ✅ **삭제하지 않음** |
| 변경 이력 | ✅ `REOPENED` 한 줄이 **추가**됨 |

⛔ 다음 구현은 금지되어 있고, 테스트로 막혀 있습니다.

* `DELETE FROM purchase_review`
* `final_purchase_type = NULL` · `reviewed_by = NULL` · `reviewed_at = NULL`

**이유.** 담당자가 무엇을 골랐었는지 화면에서 계속 보여야 하고, "확정한 적
있다" 는 사실이 사라지면 감사·재현이 불가능해집니다.

## 11.3 ✅ 이력에 남는 모양

`REOPENED` 항목은 `before_type == after_type` 입니다. 값을 바꾼 것이 아니라
**상태를 되돌린** 것이므로 앞뒤 유형이 같습니다.

```
ANALYZED  (-    → -   )
CONFIRMED (-    → 공사)
REOPENED  (공사 → 공사)   ← 값이 아니라 상태가 바뀐 줄
CONFIRMED (공사 → 물품)
```

## 11.4 ✅ 확정된 건만 되돌린다

| 현재 상태 | 결과 |
|---|---|
| `CONFIRMED` | 200 — `REOPENED` 로 |
| `REOPENED` | **409** |
| `PENDING` / 검토 행 없음 | **409** |
| 존재하지 않는 구매 | **404** |

확정한 적 없는 건을 "되돌린다" 는 것은 뜻이 통하지 않고, 허용하면 확정 이력이
없는데 상태만 `REOPENED` 인 행이 생깁니다. 409 로 거부하므로 버튼을 여러 번
눌러도 상태가 어긋나지 않습니다.

## 11.5 ✅ 확인창

⛔ 버튼을 누르자마자 되돌리지 않습니다. 연속 검토 중 잘못 눌러 확정이 풀리면
담당자가 알아채기 어렵기 때문입니다.

| 항목 | 내용 |
|---|---|
| 표시 | 현재 확정 유형 · 확정자 · 확정일시 (**참고용 표시**) |
| 기본 포커스 | **[취소]** — 안전한 쪽 |
| 닫기 | [취소] · `Esc` · 바깥 클릭 (**모두 취소**) |
| 확인 전 | 요청 0건 · 상태 변화 없음 |
| 새 유형 선택 | ⛔ 없음 — 되돌린 뒤 평소대로 고른다 |

## 11.6 ✅ 오류 처리 — ⛔ 자동 재시도 없음

확정·취소는 상태를 바꾸는 요청이라, 조용히 다시 보내면 담당자가 모르는 사이에
두 번 처리될 수 있습니다. 다시 시도할지는 **사람이** 정합니다.

| 상황 | 화면 |
|---|---|
| 409 | "이미 처리된 상태입니다. 새로고침 후 확인해 주세요." |
| 404 | "대상을 찾을 수 없습니다. 목록을 새로고침해 주세요." |
| 5xx | "(서버 오류 500). 저장되지 않았습니다. 다시 시도해 주세요." |
| 네트워크 단절 | "서버와 연결할 수 없습니다. 네트워크 연결을 확인한 후…" |

실패 시에는 확인창이 **닫히지 않고**, 완료 안내도 뜨지 않으며, 목록을 다시
불러오지 않습니다. 버튼만 되살아나 담당자가 직접 다시 누를 수 있습니다.
확정이 실패하면 다음 건으로 넘어가지 않고 고른 값도 그대로 둡니다.

## 11.7 ✅ 중복 요청 방지

* 혼재 적요 — 유형 수·최다 유형·비율이 **판정 없이** 사실로만 표시됨
* 확정값과 과거 이력이 서로 다른 칸에 분리되어 보임
* Undo 후에도 확정값·확정자·확정시각이 남고 이력이 보존됨
* 검색·필터·정렬·페이지가 전부 서버에서 처리되어 브라우저에는 한 쪽만 옴
* 조건을 바꿔도 요청은 1건, 커서 이동은 0건

## 12.8 🔴 이번에도 정하지 않은 것

임계값 · 그룹핑 키 · 그룹 일괄 확정 · 구매유형 업무규칙 · DB-3 · Calculator
연결 — §10.8 · §11.11 과 동일하게 **전부 미정**입니다.

# 13. 원본 행 추적 (STEP 12)

## 13.1 🔴 무엇이 문제였나

STEP 11 실데이터 리허설(§12)에서 **원본 2,292행 중 130행이 DB-1 에 적재되지
않아 검토 화면에 아예 나타나지 않았습니다.** 담당자가 목록을 끝까지 보고
"전체를 검토했다" 고 판단해도, 실제로는 보지 못한 행이 남습니다.

이것을 다음과 같이 분류합니다.

| 분류 | 판단 |
|---|---|
| 기술 버그인가 | ❌ 아닙니다. 규칙대로 동작했고, 실패한 행은 적재 결과에 남았습니다. |
| 현재 import 정책인가 | ⭕ 부분적으로 — `PurchaseRepository` 가 `amount > 0` 을 요구합니다. |
| **고객 업무규칙 미확정 사항인가** | ⭕ **여기에 해당합니다** — 음수 거래를 어떻게 볼지가 정해지지 않았습니다(Q5-8). |
| 화면에서 사라진 것은 문제인가 | ⭕ **예.** 기록이 응답에만 있고 남지 않는 것은 고쳐야 합니다. |

STEP 12 에서 고친 것은 **마지막 하나뿐**입니다. 업무규칙은 그대로 대기시킵니다.

## 13.2 ✅ 금액 ≤ 0 행의 현재 처리 흐름

| 단계 | 무엇이 일어나는가 | 코드 |
|---|---|---|
| 업로드 검증 | **경고**로만 표시하고 통과시킴 — 여기서 오류로 단정하면 확정되지 않은 규칙을 만드는 셈 | `uploads/validation.py` (금액 파싱 분기) |
| 행 적재 | `Purchase` 를 만들어 저장 시도 | `importers/purchase_importer.py` `_import_row` |
| **DB-1 저장** | **거부** — `구매금액은 0 보다 커야 합니다` | `database/purchase_repository.py` `_validate` |
| 실패 처리 | 예외를 잡아 그 행만 `FAILED` 로 두고 **다음 행을 계속 처리** | `importers/purchase_importer.py` |
| **기록 (STEP 12 신규)** | 실패한 행을 원본 값·사유와 함께 저장 | `importers/rejection_trace.py` → `import_rejection` |
| 검토 목록 · CSV | DB-1 에 없으므로 나오지 않음 (변경 없음) | — |
| **화면 안내 (STEP 12 신규)** | 원본 대비 건수와 미적재 목록을 표시 | `GET /imports/trace` → 검토 화면 상단 |

⚠️ `amount > 0` 규칙은 **음수 상계가 아직 계산에 연결되지 않았기 때문**에
있는 것입니다(`core/offsetting.py` 경고 참조). STEP 12 에서 이 규칙을 바꾸지
않았습니다.

## 13.3 ✅ 추적 구조 — 신규 테이블 하나

```
import_rejection
  rejection_id · batch_id · row_number · reason · message
  business_no · company_name · description · budget_account
  amount (원본 그대로 — 음수도 그대로) · resolution_date · issue_date · created_at
```

| 원칙 | 지킨 방법 |
|---|---|
| DB-1 불변 | `purchase` 테이블·컬럼을 건드리지 않음. 신규 테이블만 추가 |
| 계산 무영향 | Calculator 는 `purchase` 만 읽으므로 이 테이블을 보지 않음 |
| 업무 판단 없음 | "제외" 를 뜻하는 상태값을 만들지 않음. 사유 코드는 **무슨 일이 있었는지**만 적음 |
| 하위 호환 | `BatchImportService` 의 저장소 인자는 **선택** — 넣지 않으면 기존과 동일하게 동작 |
| 원본 되짚기 | `row_number` 로 원본 파일의 같은 행을 찾을 수 있음 |

사유 코드는 4가지입니다 — `NON_POSITIVE_AMOUNT` · `MISSING_REQUIRED` ·
`UNPARSABLE` · `OTHER`. 모르는 사유도 `OTHER` 로 **남깁니다**(버리지 않습니다).

## 13.4 ✅ 숫자 대조

```
원본 행 수 = 적재된 행 수 + 사유와 함께 기록된 행 수
```

`ImportTrace.unexplained` 가 0 이 아니면 **어딘가에서 행이 사라진 것**입니다.
`ImportTrace.source_rows` 는 Importer 에 넘긴 행을 **세어서** 기록한 값이며,
적재/미적재 합계로 계산한 값이 아닙니다 — 그래야 둘을 맞대어 볼 수 있습니다.

## 13.5 ✅ 실데이터 재검증 (2,292행)

| 항목 | STEP 11 (Before) | STEP 12 (After) |
|---|---:|---:|
| 원본 행 | 2,292 | 2,292 |
| 적재 | 2,162 | 2,162 |
| 미적재 | 130 | 130 |
| **미적재 행의 기록** | ❌ 없음(응답에만 잠깐) | ✅ **130건 전부 DB 에 기록** |
| **설명되지 않는 행** | 확인 불가 | **0** |
| 화면에서 확인 가능 | ❌ | ✅ 안내 + 130행 목록 |
| 사유 분류 | — | `NON_POSITIVE_AMOUNT` 130 |

숫자를 억지로 2,292 로 맞추지 않았습니다. **2,292행이 어디로 갔는지 전부
설명됩니다.**

## 13.6 ✅ 화면 표시 — 무엇을 쓰고, 무엇을 쓰지 않았나

표시 문구:

> 원본 2,292행 중 2,162행이 검토 대상입니다. 나머지 130행은 원본에는 있으나
> 현재 검토 대상에 포함되지 않았습니다 — 처리 방식 확인이 필요합니다.
> 사유: 금액이 0 이하 (처리 방식 확인 필요) 130건

⛔ **쓰지 않은 표현** — "130건은 제외되었습니다" · "실적에서 제외합니다" ·
"검토할 필요가 없습니다". 고객이 Q5-8 에 답하기 전이므로 셋 다 사실이
아닙니다. 테스트로도 막아 두었습니다.

미적재 행은 **원본 행 번호 · 적요 · 거래처 · 금액(음수 그대로) · 예산과목 ·
사유** 로 표에 나옵니다. 목록을 자를 경우 자른 사실을 함께 표시합니다 —
조용히 줄이면 "다 봤다" 는 오해가 다시 생깁니다.

## 13.7 ✅ 담당자명이 비어 있을 때 (STEP 11 §12.6 B 항목)

| 항목 | 처리 |
|---|---|

나중에 계정 체계가 생겨도 과거 기록을 잘못 해석하지 않도록, **기록은 비어
