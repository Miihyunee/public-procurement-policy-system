# 2. 담당자가 보는 정보 (지시 8번)

화면은 **네 블록**으로 나뉩니다. 블록이 섞이면 "원본 적요가 공사로 바뀌었다"
같은 오해가 생기므로, 응답 스키마 수준에서 분리해 둡니다.

## 2.1 원본 (DB-1 · ⛔ 전부 읽기 전용)

| 화면 라벨 | 출처 |
|---|---|
| 적요 | `purchase.description` |
| 신고기준일 | `purchase.issue_date` |
| 결의일자 | `purchase.resolution_date` |
| 거래처명 | `purchase.company_name` |
| 사업자번호 | `purchase.business_no` |
| 금액(VAT 포함) | `purchase.amount` |
| 예산과목 | `purchase.budget_account` |

> ⚠️ **공급가액은 DB-1 에 별도로 보관되지 않습니다.** 원본 엑셀에는 공급가액 ·
> 세액 · 계 세 컬럼이 있으나, 표준 양식은 **VAT 포함 총액 한 값**만 받습니다
> (`DECISIONS.md` 금액 기준). 공급가액을 화면에 따로 보여주려면 스키마 변경이
> 필요하며, 이는 **결정 대기 항목**입니다.

## 2.2 분석 결과 (DB-2 · ⛔ 읽기 전용 · **확정이 아님**)

| 화면 라벨 | 출처 |
|---|---|
| 분석 방법 | `analyzer_name` + `analyzer_version` |
| 후보 유형 · 후보 순위 | `candidates_json[].purchase_type` (점수 내림차순) |
| 후보 점수 | `candidates_json[].score` |
| 후보 개수 | 후보 목록에서 계산 |
| 1·2순위 점수차 | 후보 1·2번 점수의 차. 후보가 1개 이하면 **`null`** |
| 근거 | `candidates_json[].evidence` |
| 확인 권장 표시 | `is_ambiguous` |

> ⛔ **점수차에 기준이 없습니다.** "차이가 크면 확정" 같은 임계값을 만들지
> 않았습니다(고객 미확정). 숫자를 그대로 보여줄 뿐입니다.

## 2.3 같은 적요의 과거 확정 이력 (DB-1 + DB-2 · ⛔ 추천이 아님)

| 화면 라벨 | 뜻 |
|---|---|
| 과거 N건 + 유형별 건수 | 같은 적요를 과거에 어떻게 확정했는지 |
| **일관성** | `이력 없음` / `한 유형으로만 확정됨` / `여러 유형으로 갈림` |
| **최다 유형 + 비율** | 가장 많이 고른 유형과 그 비율(%) |
| **유형 수** | 과거에 붙은 서로 다른 유형의 개수 |
| "과거 판단이 갈렸던 적요입니다" | 같은 적요가 **여러 유형**으로 확정된 적 있음 |
| "1순위 후보가 과거 최다 유형과 다릅니다" | 분석과 과거 판단이 갈림 |
| **"과거 확정 이력 없음 (처음 보는 적요)"** | 이력이 없음. ⛔ **오류가 아니며** 임의 유형을 붙이지 않음 |

> ⛔ **일관성은 등급이 아닙니다.** "높음/보통/낮음" 처럼 비율을 잘라 만든 값이
> 아니라, **"이력이 있는가 · 갈렸는가" 라는 구조적 사실** 세 가지뿐입니다.
> 갈린 **정도**는 최다 유형 비율로 원시값 그대로 보여주며, 그 값을 어디서
> 자를지는 🔴 고객 확인 사항입니다.

> **왜 별도 블록인가**: `review` 블록 안에 넣으면 "확정값" 으로 오인됩니다.
> 과거 기록을 **세어서 보여줄 뿐**이며, 어떤 유형이 맞다고 말하지 않습니다.
>
> **판단 보류(`None`)는 이력에 세지 않습니다** — 사람이 결론을 내지 않은
> 것이기 때문입니다.

## 2.4 담당자 결정 (DB-2 · ✅ **여기서만 편집**)

| 선택지 | 값 |
|---|---|
| 공사 | `CONSTRUCTION` |
| 용역 | `SERVICE` |
| 물품 | `GOODS` |
| **판단 보류** | `null` — 새 유형이 아니라 **값 없음** |
| 메모 | `review_note` |

**화면 전체에서 편집 가능한 것은 유형 선택과 메모 두 개뿐입니다.**

> ⛔ **어떤 선택지도 미리 눌려 있지 않습니다.** 분석 1순위가 100% 여도
> 마찬가지이며, 화면에 "선택된 항목이 없습니다" 라고 명시합니다. 미리 눌러
> 두면 담당자가 그대로 확정을 눌러 **사실상 자동 확정**이 됩니다.

# 3. 담당자가 할 수 있는 동작

| 동작 | 결과 |
|---|---|
| 유형 선택 | `final_purchase_type` 설정 (아직 미확정) |
| **확정** | `review_status = CONFIRMED` · `reviewed_by/at` 기록 · 이력 추가 |
| **판단 보류** | `final_purchase_type = NULL` · `review_status = PENDING` 유지 |
| 다시 검토 | `review_status = REOPENED` · 이전 값은 이력에 남음 |
| 메모 | `review_note` |
| 이력 보기 | `purchase_review_history` 조회 |

⛔ **원본 수정 · 행 삭제 동작은 제공하지 않습니다.**

**"판단 보류"** 를 넣은 이유: 담당자가 정말 모를 때 아무 값이나 고르게
만들면 안 됩니다. 미확정으로 남기는 것이 정직한 상태입니다.

# 4. API 설계 (개념 · 미구현)

기존 FastAPI 패턴(`app.py`)을 그대로 따릅니다. UI 프레임워크에 종속되지 않도록
**모든 동작은 HTTP API** 로만 제공합니다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/reviews` | 검토 목록 (필터·정렬·페이징) |
| `GET` | `/reviews/{purchase_id}` | 한 건 상세 (원본 + 후보 + 확정) |
| `PUT` | `/reviews/{purchase_id}` | 유형 확정 · 메모 |
| `POST` | `/reviews/{purchase_id}/reopen` | 재검토 |
| `GET` | `/reviews/{purchase_id}/history` | 변경 이력 |
| `GET` | `/reviews/summary` | 진행률 (확정/미확정/확인 필요) |
| `POST` | `/final-datasets` | **최종 확정** — DB-3 생성 |
| `GET` | `/final-datasets` | 생성 이력 (ACTIVE / SUPERSEDED) |

## 4.1 응답 예 (`GET /reviews/{purchase_id}`)

```json
{
  "purchase_id": 1283,
  "source": {
```

| 규칙 | 방법 |

# 5. 상계 검토와의 통합 (지시 10번)

## 5.1 현재 상태

`core/offsetting.py` 는 이미 **담당자 확인 대상**을 만들어 냅니다.

```python
@dataclass(frozen=True, kw_only=True)
class NeedsManualReviewGroup:
    key: MatchKey                       # 기업 · 사업자번호 · 금액
    negative: Purchase
    candidates: list[Purchase]          # 후보 전부
    reason: ReviewReason                # MULTIPLE_CANDIDATES | CONTESTED_CANDIDATE
    sibling_negatives: list[Purchase]
    def candidate_lines(self) -> tuple[str, ...]: ...
```

실측(2026년 2,292행): 자동 상계 42쌍 · **담당자 확인 84건** · 짝 없음 3건.

## 5.2 구조가 이미 같습니다

| | 구매유형 검토 | 상계 검토 |
|---|---|---|
| 후보 제시 | `ClassificationResult.candidates` | `NeedsManualReviewGroup.candidates` |
| 자동 확정 | ⛔ 안 함 | ⛔ 안 함 |
| 담당자 선택 | 유형 3택 | 후보 양수 중 1택 |
| 결과 저장 | DB-2 `final_purchase_type` | DB-2 `offset_review.chosen_purchase_id` |

**같은 검토 화면에 탭으로 넣을 수 있습니다.**

```text
구매유형 검토          상계 검토 (84건)
─────────────────────────────────────────
┌───────────────────────────────────────────────────────────┐
│ (−) 16,900원  엘지전자(주)  107-86-14075  발행 2026-01-05  │
│ 어느 (+) 거래와 상계할까요?                                 │
│  ○ 발행 2026-01-05 | 적요 01/05 물품대 외 | 예산과목 (공란) │
│  ○ 발행 2026-01-05 | 적요 01/05 물품대 외 | 예산과목 (공란) │
│  ○ 발행 2026-01-05 | 적요 수도권…정산 건 | 예산과목 각종수수료│
│  ○ 상계하지 않음                                           │
│  ℹ️ G20 지출결의서(세금계산서·비고란)를 확인해 판단하세요.  │
│                                              [ 확정 ]      │
└───────────────────────────────────────────────────────────┘
```

## 5.3 ⛔ 이번에 하지 않는 것

# 8. 테스트 계획 (설계만)

| # | 항목 | 기대 |
|---|---|---|
| 1 | 목록 조회 | 원본 + 후보 + 확정 상태가 **분리되어** 반환 |
| 2 | 후보 선택 | `final_purchase_type` 설정 |
| 3 | 확정 | `CONFIRMED` · `reviewed_by/at` 기록 |
| 4 | 판단 보류 | `final_purchase_type = NULL` · `PENDING` 유지 |
| 5 | 수정 | 이전 값이 이력에 남음 |
| 6 | 재검토 | `REOPENED` 후 재확정 가능 |

| 10 | ⛔ 자동 선택 없음 | 응답의 `final_purchase_type` 이 초기에 `null` |

| 12 | 진행률 | 확정/미확정/확인 필요 건수 정확 |
