# 1. 목적

실제 운영데이터가 들어왔을 때 **업무 규칙 확인 후 바로 구현에 착수할 수 있는 상태**를 만든다.

| 이 문서가 하는 것 | 이 문서가 하지 않는 것 |
|---|---|
| 파일을 어떻게 **읽을 것인가**(기술적 처리) 정의 | 어떤 값이 **무슨 뜻인가**(업무 의미) 확정 |
| 행 유형·거래 구분 판별 규칙 정의 | 날짜/금액을 어느 업무 필드에 넣을지 결정 |
| 오류·경고 정책 정의 | DB 스키마 확정 |
| 수신 시 사전검증 항목 정의 | Parser 코드 작성 |

## 1.1 핵심 설계 원칙

> **형식 처리(파싱)와 의미 매핑(업무 필드 배정)을 분리한다.**

파싱은 지금 확정할 수 있지만, 매핑은 W-1~W-4·W-6 이 확정되어야 한다.
분리해 두면 **매핑이 확정될 때 파서를 다시 만들지 않아도 된다.**

```text
[1단계] 파일 → 구조화된 행(원본 컬럼명 그대로)     ← 지금 확정 가능
[2단계] 구조화된 행 → 업무 필드(Purchase 등)      ← 업무 규칙 확정 후
```

# 2. 입력 파일 형식

## 2.1 샘플에서 확인된 형식 `[샘플-확정]`

| 항목 | `.xls` (정본 후보) | `.txt` (보조) |
|---|---|---|
| 형식 | BIFF (`.xls`) | 텍스트 |
| 인코딩 | Code page 949 | **UTF-16LE** (BOM 있음) |
| 줄바꿈 | — | CRLF |
| 구분자 | — | 쉼표 |
| 헤더 | ✅ 1행 | ❌ **없음** |
| 컬럼 수 | **88** | 19 (잘림) |
| 금액 표기 | 숫자값 | **천단위 쉼표 + 따옴표 없음** |
| 날짜 표기 | `YYYY/MM/DD` | `YYYY/MM/DD` |

## 2.2 `.txt` 처리 방침 — **거부 또는 경고**

금액의 천단위 쉼표가 따옴표로 감싸져 있지 않아 **필드 경계가 무너진다.**
샘플에서 줄당 필드 수가 20~30개로 제각각이었다.

| 방침 | 내용 |
|---|---|
| 기본 | **읽지 않는다.** 파일 단위 오류로 처리하고 사유를 명시 |
| 대안 | 고객에게 **따옴표 처리된 CSV** 또는 `.xls` 재요청 |
| ⛔ 금지 | 자릿수 추론·재조합 등 **휴리스틱 복원** — 금액을 잘못 읽을 위험 |

## 2.3 지원 형식 판단 — **[운영-확인필요]**

실제 운영데이터가 `.xls` / `.xlsx` / CSV 중 무엇으로, 항상 동일하게 오는지는 확인이 필요하다(**W-9**).
**Parser 는 파일 형식을 자동 판별하고, 지원하지 않는 형식은 명확히 거부**하도록 설계한다.

# 3. 컬럼 처리 원칙

## 3.1 컬럼명 기반 접근 — **확정**

> ⛔ **컬럼 위치(index)에 의존하지 않는다.**

| 이유 |
|---|
| 실제 운영파일에서 컬럼 **순서가 바뀔 수 있다** |
| 컬럼이 **추가될 수 있다** (예: 구매유형) |
| 컬럼이 **삭제될 수 있다** |
| 샘플의 88개 중 21개는 전 행이 비어 있어, 파일마다 포함 여부가 다를 수 있다 |

접근은 `row["사업자번호"]` 형태로 하며, `row[7]` 같은 위치 접근은 금지한다.

## 3.2 컬럼 구조 차이 탐지 — **확정**

Parser 는 **기대 컬럼 목록과 실제 파일 컬럼**을 비교해 다음을 보고해야 한다.

| 항목 | 내용 |
|---|---|
| **추가 컬럼** | 실제 파일에만 있는 컬럼 → **정보로 보고**(구매유형이 추가되었을 수 있음) |
| **삭제 컬럼** | 기대 목록에만 있는 컬럼 → 필수/선택에 따라 오류 또는 경고 |
| **이름 변경 가능성** | 삭제·추가가 동시에 발생하면 **이름 변경 후보로 함께 제시** |

> ⚠️ **이름 변경을 자동으로 판정해 매핑하지 않는다.** 후보만 제시하고 사람이 확인한다.
> 유사 문자열 자동 매핑은 **엉뚱한 컬럼을 연결할 위험**이 있다.

## 3.3 필수 컬럼 누락 — 파일 단위 오류

| 항목 | 방침 |
|---|---|
| 처리 단위 | **행 단위로 무시하지 않고 파일 단위 오류** |
| 이유 | 필수 컬럼이 없으면 **모든 행이 동일하게 실패**한다. 행마다 실패를 반복 보고하는 것은 의미가 없고, 부분 적재는 더 위험하다 |
| 필수 컬럼 목록 | 🔴 **미확정** — 업무 규칙(W-1~W-3) 확정 후 결정 |

> 현재 확실히 필수인 것은 **사업자등록번호**뿐이다. 날짜·금액은 **어느 컬럼을 쓸지가
> 정해지지 않아** 필수 목록을 확정할 수 없다.

## 3.4 컬럼 값 접근 시 원본 보존

| 원칙 |
|---|
| 비교·판정을 위한 **정규화는 사본에 적용**한다 |
| **원본값은 변경하지 않는다** (제외 사유 추적·재판정에 필요) |

# 4. 행 유형 판별

## 4.1 행 유형

| 유형 | 정의 | 처리 |
|---|---|---|
| **데이터행** | 실제 거래 | 후속 단계 진행 |
| **집계행** | 소계·합계 등 | 계산 대상에서 제외 (5장) |
| **빈 행** | 전 컬럼이 비어 있음 | 건너뛰되 **건수 보고** |
| **의심 행** | 집계행으로 의심되나 알려진 표기가 아님 | **데이터행 유지 + Warning** (5.3) |

## 4.2 판별 순서

```text
빈 행 판별 → 집계행 판별 → 나머지는 데이터행
```

> 집계행 판별을 **금액 크기·행 위치 같은 휴리스틱으로 하지 않는다.**
> "마지막 행이니 합계일 것", "금액이 크니 소계일 것" 같은 추론은 **거래행을 지울 수 있다.**

---

# 5. 집계행 처리

## 5.1 구조

```text
원본값
  → 비교용 문자열 정규화   (공백 제거 등)
  → 알려진 집계행 표기 목록과 대조
  → 판정
```

> ⚠️ **정규화는 "비교용"이며 원본값 자체를 변경하지 않는다.**

## 5.2 알려진 표기 `[샘플-관찰]`

| 표기 | 판별 컬럼 |
|---|---|
| `[소    계]` | `세무구분` |
| `[누    계]` | `세무구분` |
| `[분 기 계]` | `세무구분` |
| `합계` | `번호` |

> 🔴 **`[소    계]` 처럼 표기 내부에 공백이 들어 있다.** 단순 문자열 비교로는 놓치므로
> **공백 정규화 후 비교**해야 한다.
>
> **[운영-확인필요]**: 실제 운영데이터에 다른 표기가 있을 수 있다.

## 5.3 알려지지 않은 표기 — **자동 삭제 금지**

| 상황 | 처리 |
|---|---|
| 알려진 집계행 표기 | **제외 + 사유 기록** |
| 알려지지 않은 의심 값 | **데이터행 유지 + Warning** |

**근거**: 누락은 조용하지만 과대 계상은 총액에서 눈에 띈다.
자동 패턴 매칭(`[...계]` 형태 등)으로 거래행을 잘못 제거하는 것은 **금지**한다.

→ **PM 결정 D-18**

## 5.4 보고 항목

| 항목 |
|---|
| 집계행 제외 건수·금액 |
| 판별 규칙별 적중 건수 (`세무구분` 기준 / `번호` 기준) |
| **의심 값 목록** (Warning) |

# 6. 매출 / 매입 구분

## 6.1 두 개념 분리 — **핵심**

```text
거래 구분(transaction kind)   ≠   정책 계산 대상 여부(eligible)
```

| 구분 | 판정 근거 | 확정 여부 |
|---|---|---|
| 거래 구분 (매출/매입/미분류) | `세무구분` 문자열 | ✅ **Parser 에서 지원 가능** |
| **정책 계산 대상 여부** | **업무 기준** | 🔴 **[운영-확인필요] W-7** |

> ⛔ **`매입 = 우선구매 실적` 이라고 확정하지 않는다.**
> 부가세 신고 대상이 아닌 지출이 원장에서 빠져 있을 수 있다.

## 6.2 판정 규칙

| # | 조건 | 거래 구분 | 계산 대상 |
|---|---|---|---|
| K-1 | 집계행 | — | 제외 |
| K-2 | `세무구분` 에 `매출` 포함 | 매출 | 제외 |
| K-3 | `세무구분` 에 `매입` 포함 | 매입 | **대상 후보** |
| K-4 | 그 외 / 빈값 | **미분류** | **판정 보류 + Warning** |

> **K-4 를 임의로 매입·매출로 분류하지 않는다.** → **D-21**

## 6.3 샘플에서 관찰된 값 `[샘플-관찰]`

`[13]면세매출` · `[24]매입불공제` · `[21]과세매입` · `[23]면세매입`

> **[운영-확인필요]**: 다른 기간·기관에서 새로운 구분값이 나올 수 있다.
> 그래서 **값 목록 고정이 아니라 `매출`/`매입` 포함 여부**로 판정한다.

# 7. 사업자등록번호 정규화

## 7.1 기존 로직 재사용 — **확정**

> ⛔ **Parser 에서 별도 사업자번호 규칙을 만들지 않는다.**
> `procurement.matchers.business_no.normalize_business_no()` 를 **그대로 호출**한다.

## 7.2 적용되는 기존 규칙 (변경 없음)

| 규칙 |
|---|
| 하이픈·공백 제거 후 **10자리 문자열**로 정규화 |
| **9자리 자동 0 보정 금지** → `INVALID_FORMAT` |
| 10자리 초과·문자 포함 → `INVALID_FORMAT` |
| 빈값·`None` → `MISSING` |
| **체크섬 오류는 Warning** — 저장을 자동 차단하지 않음 |
| **원본값 추적 가능** (`NormalizedBusinessNo.original`) |

## 7.3 샘플 적용 결과 `[샘플-관찰]`

샘플 2,903행 전부 `VALID`, 9자리 0건, 체크섬 오류 0건 → **규칙과 충돌하는 데이터 없음**.

> **[운영-확인필요]**: 실제 데이터에서 9자리가 나타날 수 있다(Excel 저장 시 앞자리 0 손실).
> 나타나면 **보정하지 않고 리포트**하며, 원본 재확보를 요청한다.

# 8. 날짜 파싱

## 8.1 확정 가능 — 형식 파싱

| 항목 | 내용 |
|---|---|
| 지원 형식 | `YYYY/MM/DD` (샘플 확인) — 기존 `_parse_date` 가 이미 지원 |
| 확장 후보 | `YYYY-MM-DD`, `YYYYMMDD`, Excel 날짜 셀 |
| 실패 처리 | 파싱 실패 행은 **사유와 함께 보고** |

## 8.2 ⛔ 확정하지 않는 것 — 업무 매핑

```text
어떤 날짜 → payment_date     ← 미확정 (W-1)
어떤 날짜 → contract_date    ← 미확정 (W-2)
```

샘플에는 날짜 컬럼이 **4개**(`신고기준일`·`기표일자`·`결의일자`·`발행일`) 있고,
**계약일로 볼 수 있는 컬럼은 확인되지 않았다.**

## 8.3 설계 방침

Parser 는 **날짜 컬럼을 원본 컬럼명 그대로 파싱해 보관**하고,
**업무 필드 배정은 별도 매핑 단계에서 수행**한다.

```text
[파싱]  "신고기준일" → date 객체
        "기표일자"   → date 객체 (또는 None)
        "결의일자"   → date 객체
             ↓
[매핑]  ??? → payment_date        ← W-1 확정 후 주입
        ??? → contract_date       ← W-2 확정 후 주입
```

> 이렇게 분리하면 **W-1·W-2 가 확정될 때 매핑만 바꾸면 된다.**

# 9. 금액 파싱

## 9.1 확정 가능 — 형식 파싱

| 항목 | 내용 |
|---|---|
| 입력 형태 | 숫자값(`.xls`), 천단위 쉼표 문자열, 통화기호 |
| 처리 | **`Decimal`** 로 변환 (부동소수 금지) — 기존 `_parse_amount` 규칙과 동일 |
| 음수 | **파싱은 성공시킨다** (거부하지 않음) |
| 결측·파싱 실패 | 사유와 함께 보고 |

## 9.2 ⛔ 확정하지 않는 것

```text
공급가액  vs  계        →  어느 것을 Purchase.amount 로 쓸지 미확정 (W-3)
음수 금액의 의미                                        미확정 (W-4)
```

> 샘플에서 두 값의 차이는 8.9% 였다. **달성률에 직접 반영되는 차이**이므로
> 공식 기준 확인 전에는 선택하지 않는다.

## 9.3 정합성 검증 (파싱 단계에서 가능)

| 검증 | 내용 |
|---|---|
| `공급가액 + 세액 = 계` | 불일치 건수를 **리포트**. 자동 보정하지 않음 |

## 9.4 음수 처리 방침

| 단계 | 처리 |
|---|---|
| **파싱** | 음수를 그대로 읽는다 |
| **분류** | 음수 건수·금액을 **별도 집계해 보고** |
| **저장** | 🔴 **미확정** — 현재 `PurchaseRepository` 가 `amount <= 0` 을 거부 (W-4 · Issue #49) |
| ⛔ 금지 | **자동 상계**, 의미 추정, 절대값 변환 |

# 10. Validation

## 10.1 지금 정의할 수 있는 검증

| # | 검증 | 실패 시 |
|---|---|---|
| V-1 | 파일 형식 지원 여부 | **파일 단위 오류** |
| V-2 | 헤더 존재·컬럼 구조 | **파일 단위 오류** (필수 컬럼 누락 시) |
| V-3 | 컬럼 구조 차이(추가/삭제) | 보고 |
| V-4 | 사업자번호 정규화 결과 | 상태별 분류 |
| V-5 | 사업자번호 체크섬 | **Warning** (차단 안 함) |
| V-6 | 날짜 **형식** 파싱 | 행 오류 보고 |
| V-7 | 금액 **형식** 파싱 | 행 오류 보고 |
| V-8 | `공급가액 + 세액 = 계` | 보고 |
| V-9 | 집계행 식별 | 제외 + 사유 |
| V-10 | 거래 구분 판정 | 미분류는 보류 + Warning |
| V-11 | **원본 = 제외 + 보류 + 대상** 건수·금액 합 일치 | **파일 단위 오류** |

> V-11 이 어긋나면 **어딘가에서 행이 조용히 사라졌다는 뜻**이므로 반드시 실패 처리한다.

## 10.2 아직 정의할 수 없는 검증

| # | 검증 | 미확정 사유 |
|---|---|---|
| X-1 | 지급일 필수 여부 / 결측 허용 여부 | W-1 |
| X-2 | 계약일 필수 여부 | W-2 |
| X-3 | 금액 부호 규칙(음수 허용 여부) | W-4 |
| X-4 | 구매유형 유효값 | W-6 |
| X-5 | `계약일 ≤ 지급일` 논리 검증 | W-1·W-2 확정 후 |

> **X-1~X-5 를 임의로 정의하지 않는다.**

# 11. 오류 / Warning 정책

## 11.1 3단계 구분

| 수준 | 의미 | 처리 |
|---|---|---|
| **파일 오류** | 파일 전체를 읽을 수 없음 | **처리 중단**. 아무것도 저장하지 않음 |
| **행 오류** | 해당 행을 사용할 수 없음 | 행 제외 + 사유 기록. 나머지는 진행 |
| **Warning** | 사용은 하되 확인 필요 | 진행 + 사유 기록 |

## 11.2 수준별 사례

| 수준 | 사례 |
|---|---|
| **파일 오류** | 지원하지 않는 형식 / `.txt`(따옴표 없음) / 필수 컬럼 누락 / **합계 정합성 불일치(V-11)** |
| **행 오류** | 날짜 형식 파싱 실패 / 금액 파싱 실패 / 사업자번호 `MISSING`·`INVALID_FORMAT` |
| **Warning** | 체크섬 오류 / 미분류 거래 구분 / **알려지지 않은 집계 의심 값** / 금액 정합성 불일치 / 컬럼 구조 차이 / 음수 금액 |

## 11.3 원칙

| 원칙 |
|---|
| **조용한 실패 금지** — 제외된 행은 반드시 건수·금액과 사유가 남는다 |
| **부분 적재보다 명시적 실패** — 파일 오류는 중단하고 사람이 판단한다 |
| **Warning 은 막지 않는다** — 기존 체크섬 정책과 동일 |

# 12. Raw / Cleansed / Eligible

## 12.1 개념 (유지)

```text
① Raw       고객 제공 원본 그대로
② Cleansed  집계행 배제 + 거래 구분 부여
③ Eligible  정책 계산에 투입할 행
```

## 12.2 추적 요구사항 — **확정**

전처리에서 **행을 조용히 삭제하지 않는다.** 최소한 다음을 추적할 수 있어야 한다.

| 항목 |
|---|
| 원본 행 (또는 원본 행 식별자) |
| 제외 여부 |
| **제외 사유** |
| 처리 결과 (정상 / 경고 / 오류) |
| 단계별 **건수** |
| 단계별 **금액** |

## 12.3 ⛔ 아직 확정하지 않는 것

| # | 미결 사항 |
|---|---|
| 1 | Raw 데이터를 DB 에 저장할지 |
| 2 | 제외 행을 별도 테이블에 저장할지 |
| 3 | `Purchase` 에 상태 필드를 추가할지 |
| 4 | 전처리 결과를 파일/리포트로 관리할지 |
| 5 | 원본 행 ID 를 어떻게 관리할지 |

> **DB 스키마를 확정하지 않는다.** 실제 운영데이터의 **규모·적재 주기·재판정 방식**이
> 확인된 뒤 결정한다. 설계안 비교는 `docs/PREPROCESSING_DECISION_ANALYSIS.md` 5장 → **D-19**
