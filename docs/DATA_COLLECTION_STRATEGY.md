# 1. 목적과 범위

## 1.1 목적

본 문서는 시스템이 정책별 우선구매 달성률을 계산하기 위해 **외부에서 확보해야 하는 데이터**와
그 **수집 전략**을 정의한다.

시스템의 계산 구조는 다음과 같다.

```
고객 구매(지출) 데이터  +  기업 인증정보(외부 수집)
        └────────── 사업자등록번호로 결합 ──────────┘
                            ↓
                  정책별 달성률 계산
```

즉 **외부 데이터 없이는 계산 자체가 성립하지 않으며**, 본 문서는 그 확보 방안을 다룬다.

## 1.2 범위

- 포함: 필요 데이터 목록, 제공기관·제공방식 조사, 수집 방식 제안, Collector 구조 설계
- 제외: 실제 Collector 구현, API 연동, DB 변경, Bootstrap 구현 (본 작업은 **설계 문서 작성만** 수행)

## 1.3 조사 신뢰도 표기 (중요)

본 문서의 조사 결과는 **공개된 웹 정보 기반**이며, 다음 한계가 있다.

- 공공데이터포털(data.go.kr) 상세 페이지는 자동 조회가 차단(HTTP 403)되어
  **응답 필드 단위까지는 직접 확인하지 못했다.**
- 따라서 각 항목에 **신뢰도**를 함께 표기한다.

| 표기 | 의미 |
|---|---|
| ✅ 확인 | 제공기관·제공방식이 복수 출처로 확인됨 |
| 🔶 추정 | 데이터셋 존재는 확인되나 세부 필드·조건은 미확인 |
| ❓ 미확인 | 존재 여부·조건 모두 추가 조사 필요 |

> **원칙**: 🔶·❓ 항목은 실제 활용신청 후 응답 스펙을 확인하기 전까지 구현에 착수하지 않는다.

### 3.1 조사 결론 요약

- **가장 중요한 발견**: SMPP 인증서 API(15062581) 하나로 **여성기업·장애인기업**을 사업자번호 기준으로
  조회할 수 있어, 프로젝트의 계산 모델과 정합성이 가장 높다.
- **가장 큰 제약**: **중소기업**은 5대 MVP 정책 중 비중이 가장 크지만, 인증키가 **심사·승인제**여서
  발급 가능 여부가 프로젝트 리스크의 핵심이다.
- **분석 필요**: **녹색제품**은 조사한 데이터셋이 제품 단위 중심이어서, **판정 단위를
  기업 인증으로 볼지 제품 인증으로 볼지 업무 분석이 선행**되어야 한다. 현 시점에서
  자동수집 가능/불가를 단정하지 않는다.

# 4. 수집 방식 제안

## 4.1 방식 선택 기준

| 방식 | 선택 기준 |
|---|---|
| **OpenAPI** | 사업자번호로 조회 가능하고 인증키 확보가 가능한 경우 (최우선) |
| **파일 다운로드** | 전수 데이터가 파일로 공개되며 갱신 주기가 길거나 부정기인 경우 |
| **웹 조회** | 공식 자동 수집 수단이 없고 건별 확인만 가능한 경우 (보조 수단) |
| **수기 입력** | 자동화가 불가하거나 건수가 적어 운영자가 직접 관리하는 편이 합리적인 경우 |

## 4.2 데이터별 권장 방식

| 정책 | 1차 권장 | 대체(Fallback) | 근거 |
|---|---|---|---|
| 중소기업 | **OpenAPI** (중소벤처24) | 고객이 확인서 사본 제출 → 수기/일괄 입력 | 인증키 심사 결과에 따라 대체안 필요 |
| 여성기업 | **OpenAPI** (SMPP) | — | 사업자번호 조회 지원, 대체 불필요 |

| 창업기업 | **OpenAPI** (창업진흥원) | 파일 다운로드 | 유효기간 필드 확인 후 확정 |
| 녹색제품 | **업무 분석 후 확정** | — | 판정 단위(기업/제품) 미확정 → 분석 완료 후 방식 결정 |
| 기관 구매실적 | **파일 업로드(고객)** | — | 고객 보유 데이터 |

## 4.3 수집 주기 제안

| 유형 | 주기 | 비고 |
|---|---|---|
| 인증 조회형 API (SMPP 등) | **구매 데이터 업로드 시점에 조회** | 판정 기준일 기준으로 조회해야 정확 |
| 전수 파일형 | 월 1회 또는 분기 1회 | 원본 파일과 수집 이력 보관 |
| 부정기 데이터 | 운영자 수동 갱신 | 갱신 알림 절차 필요 |

> **설계 유의점**: 이 시스템은 "현재 인증 보유 여부"가 아니라
> **"판정 기준일에 인증이 유효했는가"** 로 실적을 판정한다(`POLICY_DEFINITION.md`).
> 따라서 수집 시 **유효기간(valid_from ~ valid_to)을 반드시 함께 확보**해야 하며,
> 기준일자 파라미터를 지원하는 API가 유리하다.

# 5. Collector 구조 제안

## 5.1 설계 원칙

1. **계층 원칙 유지** — Collector는 외부 데이터를 표준 형태로 변환하는 것까지만 담당하고,
   저장은 Repository에 위임한다. Calculator·Dashboard와 직접 결합하지 않는다.
2. **원본 보존** — 수집 원본(raw)을 그대로 보관하고, 변환(normalize) 결과를 별도로 만든다.
   외부 데이터 오류 발생 시 원인 추적이 가능해야 한다.
3. **정책별 격리** — 정책마다 제공기관·형식·조건이 모두 다르므로 정책 단위로 모듈을 나눈다.
4. **공통 규약** — 모든 Collector는 동일한 인터페이스를 따라 교체·추가가 쉬워야 한다.
   (`Rule Engine`에서 적용한 Strategy 방식과 동일한 사상)

## 5.2 권장 디렉터리 구조

```
src/procurement/collectors/
├── __init__.py
├── base.py                  # Collector 공통 인터페이스(추상) + 수집 결과 DTO
├── common/
│   ├── __init__.py
│   ├── http_client.py       # 공공데이터포털 공통 호출(인증키·재시도·타임아웃)
│   ├── file_loader.py       # CSV/XLSX 로더(인코딩·헤더 정규화)
│   ├── normalizer.py        # 사업자번호 정규화, 날짜 파싱, 기업명 정제
│   └── errors.py            # 수집 계층 예외 정의
```

> 미구현 모듈이 늘어나 유지보수 부담만 커진다.

### 구조 설명

- **`smpp/`를 별도로 둔 이유**: 여성기업·장애인기업이 **같은 API**로 제공되므로,
  정책별로 디렉터리를 쪼개면 동일 코드가 중복된다. **제공기관(데이터 소스) 기준**으로 묶는 것이 합리적이다.
  → 즉 디렉터리는 *정책*이 아니라 **데이터 소스** 단위로 나눈다.
- **`common/normalizer.py`**: 사업자등록번호 표기(`123-45-67890` vs `1234567890`)가 기관마다 달라
  **정규화가 필수**다. 이 규칙은 `DATA_MAPPING.md`의 표준 컬럼 규약과 연결된다.
- **MVP 우선순위**: `common/` → `smpp/` → `sme/` → `startup/` → `green/` 순으로 구현할 것을 제안한다.

# 6. 리스크 (Risk)

> 아래 3건은 **현재 코드 구조와 외부 데이터의 실제 구조가 어긋나는 지점**으로,
> 수집 구현 전에 결정이 필요하다.

## R-1. 녹색제품 — 판정 단위 미확정 (추가 업무 분석 필요) 🔴 높음

> **현 상태: 자동수집 가능/불가를 단정하지 않는다.** 업무 분석이 선행되어야 한다.

- 조사한 데이터셋(녹색제품정보시스템)은 **제품 단위**(EL번호·모델명·인증상태) 중심이었고,
  해당 데이터셋에서는 사업자등록번호를 확인하지 못했다.
- 그러나 본 시스템은 **사업자등록번호를 모든 결합의 기준 키**로 사용하며(`DATA_MAPPING.md`),
  `POLICY_DEFINITION.md`는 녹색제품을 **"MVP는 기업 기준"** 으로 정의하고 있다.
  → **문서상 정의(기업 기준)와 조사된 데이터 형태(제품 단위)가 어긋난다.**

### 선행 분석 과제

| # | 확인 사항 |
|---|---|
| 1 | 녹색제품 실적의 **법적·업무적 판정 단위**가 기업인가 제품인가 |
| 2 | 기업 단위 확인 경로(예: 인증 보유 업체 목록, 조달청 공공녹색구매 통합정보망)가 존재하는가 |
| 3 | 제품 단위라면 구매 데이터에 **물품목록번호·품목 정보**가 필요한가 (`PURCHASE_DATA_SPEC.md` 선택 컬럼과 연결) |
| 4 | 고객 기관이 실제로 녹색제품 실적을 **어떤 근거로 집계**하고 있는가 |

### 분석 결과별 대응 방향

| 분석 결과 | 대응 |
|---|---|
| 기업 단위로 확인 가능 | 다른 MVP 정책과 동일하게 `Certification` 적재 |
| 제품 단위로만 가능 | 구매 데이터에 품목 정보 확보 필요 + Rule Engine에 제품 기준 규칙 추가 |
| 자동 확보 불가 | 고객이 녹색제품 구매분을 별도 표기하는 운영 절차로 대체 |

> **연관**: 이 분석 결과에 따라 `PURCHASE_DATA_SPEC.md`의 선택 컬럼(물품목록번호·수량)이
> **필수로 승격될 수 있다.** 고객 데이터 요청 전에 분석을 마치는 것이 바람직하다.

## R-2. 중소기업 API — 인증키 승인제 🔴 높음

- 중소벤처24 Open API 인증키는 **신청 후 심사**를 거쳐 발급되며, 자동 승인이 아니다.
- **영향**: 5대 정책 중 가장 비중이 큰 중소기업 데이터를 확보하지 못할 수 있다.
- **대응 후보**: ① 조기 신청(리드타임 확보), ② 고객이 확인서를 제출하는 수기 경로 병행 설계.

## R-3. 인증 유효기간이 없는 데이터 🟡 중간

- `Certification` 모델은 `valid_from`·`valid_to`가 **필수(NOT NULL)** 이다.
- 그러나 **자활기업·사회적기업·자활용사촌** 데이터는 유효기간 개념이 없거나 제공되지 않는다.
- **영향**: 해당 정책은 현재 구조에 그대로 적재할 수 없다.
- **대응 후보**: ① 유효기간 nullable 허용(스키마 변경), ② 수집일 기준 기간을 부여하는 규칙 수립,
  ③ Rule Engine에서 "기간 무관" 규칙으로 처리(`ISSUE17-rule-engine-design.md`의 확장 방향과 연결).

## R-4. 대표자명 필수 제약 🟡 중간

- `Company.representative_name`이 **필수**이나, 인증 조회 API가 대표자명을 제공하지 않을 수 있다.
- **영향**: 수집 데이터만으로 `Company` 생성이 불가능할 수 있다.
- **대응 후보**: nullable 허용 또는 구매 데이터의 업체명으로 대체 후 보완.

## R-5. 개인정보·이용약관 🟡 중간

- 기업 인증정보는 사업자 정보이나, **API 이용약관상 재배포·저장 제한**이 있을 수 있다.
- **대응**: 각 API 활용신청 시 이용범위 확인 및 문서화 필요.

## R-6. 조사 미검증 항목 🟡 중간

- 3장 표의 🔶·❓ 항목은 **응답 필드 수준 검증이 되지 않았다**(포털 자동조회 차단).
- **대응**: 활용신청 후 실제 응답 샘플을 확보해 본 문서를 v1.1로 갱신한다.
